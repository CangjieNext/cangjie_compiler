## 一、安全审查概述

### 攻击面分析

本次变更引入了编译器流水线中的 AST 内存释放机制，涉及两个核心攻击面：

1. **Use-After-Free 攻击面**：AST 释放后，任何残留的 AST 指针访问都会导致 UAF。变更涉及 20+ 个 AST 指针持有者的清理，遗漏任何一个都是潜在漏洞。
2. **状态一致性攻击面**：释放操作改变了编译器内部状态机，`cacheWritten`/`resultsSaved`/`astReleased` 三个守卫标志的时序错误可导致数据丢失或崩溃。

### 总体风险评级：低（可合入）

核心架构设计正确（CHIR IR 不持有 AST 指针已验证），5 阶段清理顺序合理，ADR-009 缓存前移方案有效。历史 P0/P1 Bug 均已修复。迭代 4 全路径深度审计未发现新问题，其余为 P2 级别的防御性编程和代码质量建议。

### VULN-02: 全局注解信息使用非线程安全的全局变量

- **文件**: `src/CHIR/Checker/AnnotationChecker.cpp:14-58`
- **严重程度**: Low（预存问题，非本次引入）
- **CWE**: CWE-362 (Concurrent Execution using Shared Resource with Improper Synchronization)
- **类型**: 竞态条件（预存）

**描述**:

`g_annoInfo`、`g_typeAnnoInfo`、`g_valueAnnoInfo` 是匿名命名空间中的全局变量，非 `thread_local`。`ClearGlobalAnnotationInfo()` 对这些全局变量执行 `clear()` 操作。在多实例场景（如 LSP 服务器并发编译多个文件）中，一个编译实例的 `ClearGlobalAnnotationInfo()` 可能与另一个实例的注解收集操作产生数据竞争。

源码注释已承认此问题：
> "in case packages need compile in parallel, record g_annoInfo as member variable of class AnnotationTranslator, store it somewhere else"

**本次变更的影响**: 新增了一个写入点（`clear()`），增加了竞态窗口，但根因是预存的架构问题。

**修复建议**: 长期方案是将这些全局变量改为 `CompilerInstance` 或 `CHIRData` 的成员变量。短期可标记为 `// TODO: thread-safety`。

**优先级**: P2 — 预存问题，建议作为后续技术债务处理

## 四、C++ 代码质量问题

### CQ-01: const_cast 使用合理但缺少断言守卫

- **文件**: `src/CHIR/AST2CHIR/AST2CHIR.cpp:358-362`
- **严重程度**: Low（代码异味）

```cpp
auto& funcDecl = const_cast<AST::FuncDecl&>(static_cast<const AST::FuncDecl&>(decl));
```

`const_cast` 在此处是安全的（AST 节点是堆分配的可变对象，`const` 仅为逻辑标注），但缺少运行时断言来验证前置条件。建议添加：

```cpp
void AST2CHIR::ReleaseFuncBody(const AST::Decl& decl)
{
    if (decl.astKind != AST::ASTKind::FUNC_DECL) {
        return;
    }
    assert(dynamic_cast<const AST::FuncDecl*>(&decl) != nullptr && "astKind/type mismatch");
    auto& funcDecl = const_cast<AST::FuncDecl&>(static_cast<const AST::FuncDecl&>(decl));
    if (funcDecl.funcBody != nullptr && funcDecl.funcBody->body != nullptr) {
        funcDecl.funcBody->body.reset();
    }
}
```

注：如果项目禁用 RTTI（`-fno-rtti`），则 `dynamic_cast` 不可用，可改用 `assert(decl.astKind == AST::ASTKind::FUNC_DECL)`（已有守卫，但断言更明确）。

**优先级**: P2

### CQ-02: ReleaseTranslatedInitializers 中 DynamicCast + const_cast 组合

- **文件**: `src/CHIR/AST2CHIR/AST2CHIR.cpp:389-397`
- **严重程度**: Low（代码异味）

```cpp
if (auto* varDecl = DynamicCast<AST::VarDeclAbstract*>(const_cast<AST::Decl*>(decl.get()))) {
    ReleaseVarInitializer(*varDecl);
}
```

`DynamicCast` 是项目自定义的基于 `astKind` 的类型转换，不依赖 C++ RTTI，在 `const_cast` 后使用是安全的。但 `const_cast` 可以通过修改 `ReleaseVarInitializer` 的签名来避免：

```cpp
void ReleaseVarInitializer(const AST::VarDeclAbstract& decl)  // 内部再 const_cast
```

这样调用点更干净。当前实现功能正确，属于风格优化。

**优先级**: P2

### CQ-03: 析构函数中 packageManager 和 mangler 的清理路径不一致

- **文件**: `src/Frontend/CompilerInstance.cpp:84-106`
- **严重程度**: Low（代码异味）

```cpp
CompilerInstance::~CompilerInstance()
{
    if (!astReleased) {
        srcPkgs.clear();
        pkgCtxMap.clear();
        delete typeChecker; typeChecker = nullptr;
        delete typeManager; typeManager = nullptr;
        delete testManager; testManager = nullptr;
        delete gim; gim = nullptr;
    }
    // These resources must be cleaned regardless of AST release state.
    delete compileStrategy; compileStrategy = nullptr;
    delete packageManager; packageManager = nullptr;
    // mangler is unique_ptr, auto-destructed.
    // importManager is a stack member, auto-destructed.
}
```

当 `astReleased == true` 时，`packageManager` 在析构函数中被 `delete`，但其内部数据已在 `ReleaseASTMemory()` 的 Phase 3g 中被 `ClearASTReferences()` 清空。这是安全的，但存在不一致：`mangler` 在 `ReleaseASTMemory()` 中被 `reset()`（完全释放），而 `packageManager` 只是清空数据但保留对象直到析构。

建议统一策略：要么在 `ReleaseASTMemory()` 中也 `delete packageManager`（并在析构函数中加守卫），要么在注释中明确说明为何 `packageManager` 需要保留到析构。

**优先级**: P2
