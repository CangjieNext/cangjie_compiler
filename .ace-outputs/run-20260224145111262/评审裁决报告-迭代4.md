## 三、新发现缺陷逐条裁决

### F-01 [High] WriteCachedInfo 在 AST 释放后执行 — 确认，维持 High，P0

**裁决：确认，严重程度 High，P0 阻塞**

这是本轮最关键的发现。代码验证完全支持攻击方的分析：

1. `UpdateAndWriteCachedInfoToDisk()` 在 `FrontendTool.cpp:214-217` 中，**在 `ExecuteCompile()` 返回后**调用。`ExecuteCompile()` 内部执行整个 `Compile()` 主循环（包括 `RELEASE_AST` 阶段），因此 `WriteCachedInfo()` 必定在 AST 释放后执行。

2. `WriteCachedInfo()`（CompilerInstance.cpp:478）访问 `*srcPkgs[0]`，但 `srcPkgs` 在 `ReleaseASTMemory()` Phase 4a 已被 clear — **use-after-free**。

3. `order`（`std::vector<const AST::Decl*>`，CompilerInstance.h:519）在 Phase 2b 被 clear，且即使不 clear，Phase 4a 后裸指针全部悬空。`WriteCachedAST()`（CachedDataSerialization.cpp:91-95）解引用 `order` 中的指针读取 `rawMangleName` — **use-after-free**。

4. `semaInfo.usages` 的物化代码确实缺失（最终方案 §4.5 仅有注释占位 `// semaInfo.usages 同理物化...`）。`DependencySerialization.cpp:59` 解引用 `Ptr<const AST::Decl>` 键读取 `rawMangleName` — **use-after-free**。

5. `GlobalDeclAnalysis.cpp:490` 在 CHIR 阶段重写 `cachedInfo.varAndFuncDep`，意味着物化必须在 CHIR 完成后执行。最终方案的 `MaterializeCachedASTReferences()` 在 `ReleaseASTMemory()` Phase 0c 中调用，时序正确（CHIR 之后、释放之前），但 `varAndFuncDep` 物化后 `WriteCachedInfo()` 的 `SetVarAndFuncDependency()` 需要适配物化后的数据结构。

**根因分析**：前三轮迭代聚焦于 `Compile()` 主循环内部的阶段时序，忽略了 `Compile()` 返回后仍有代码路径访问 AST 数据。`WriteCachedInfo()` 是增量编译的核心路径，此缺陷影响所有启用增量编译的场景。

**修复方向**（二选一）：
- 方案 A：将 `WriteCachedInfo()` 移到 `RELEASE_AST` 的 Phase 0 中执行（在 AST 释放前完成缓存写入）
- 方案 B：完整物化所有 AST 引用（`varAndFuncDep`、`semaInfo.usages`、`order`、`srcPkgs[0]` 的 `fullPackageName`），`WriteCachedInfo()` 适配物化后的数据结构

推荐方案 A——将缓存写入前移到释放前执行，改动集中且不需要修改序列化层的数据结构。

### F-02 [High] PerformResultsSaving 在 RELEASE_AST 之后执行 — 确认，维持 High，P0

**裁决：确认，严重程度 High，P0 阻塞**

代码验证确认：

1. `PerformResultsSaving()`（IncrementalCompilerInstance.cpp:519-538）通过 `GetSourcePackages()` 遍历 `srcPkgs`，调用 `SaveCjo(*srcPkg)` 和 `ExportASTSignature(*srcPkg)`。AST 释放后 `srcPkgs` 已 clear，`GetSourcePackages()` 返回空（最终方案 §4.8 的保护机制），导致缓存保存静默跳过。

2. `resultsSaved` 标志在现有代码中不存在。最终方案 §4.6 引用了 `resultsSaved` 但未在 `IncrementalCompilerInstance.h` 或 `CompilerInstance.h` 中定义。这是设计文档的遗漏。

3. CHIR 输出模式下的 `SaveCjo` 依赖：当 `outputMode == CHIR` 时，`PerformCjoSaving()` 跳过，CJO 保存被推迟到 `PerformResultsSaving()` 中。但 `RELEASE_AST` 在 `CODEGEN` 之前，`SAVE_RESULTS`（调用 `PerformResultsSaving()`）在 `CODEGEN` 之后，此时 `srcPkgs` 已被清空。

4. 最终方案 §4.3 Phase 0d 确实设计了 CHIR 模式下提前保存 CJO 的逻辑，但 `PerformResultsSaving()` 中的 `ExportASTSignature` 仍然需要 `srcPkgs` 存活。

**与 F-01 的关系**：F-01 和 F-02 是同一根因的不同表现——最终方案对"AST 释放后谁还需要 AST 数据"的分析不完整。

**修复方向**：
1. 在 `IncrementalCompilerInstance::PerformASTRelease()` 中，释放前完成 `ExportASTSignaturesForIncremental()`（最终方案 §4.6 已设计此逻辑）
2. 定义 `resultsSaved` 成员变量（bool，默认 false）
3. `PerformResultsSaving()` 检查 `astReleased` 标志，跳过已完成的操作
4. CHIR 输出模式下的 `SaveCjo` 在 Phase 0d 中完成（最终方案已设计，但需确保 `PerformResultsSaving()` 不重复执行）

### F-03 [Medium] g_annoInfo 中 AST 指针在异常退出时残留 — 确认，降级为 Low，P2

**裁决：确认风险，严重程度降级为 Low，P2**

代码验证确认：
- `g_annoInfo` 键类型为 `const ClassDef*`（CHIR 指针，非 AST 指针），`AnnotationInfo::anno` 为 `AST::Annotation*`
- `BuildCheckMap()`（AnnotationChecker.cpp:394）解引用 `anno->target`
- `g_typeAnnoInfo` 和 `g_valueAnnoInfo` 在 line 471-472 被 clear

降级理由：
1. `BuildCheckMap()` 在 CHIR 阶段内部执行（`ToCHIR::Run()` 的 step 1），在 `RELEASE_AST` 之前，此时 AST 存活。正常流程中不存在 use-after-free。
2. 攻击方指出的风险仅存在于**异常退出 + 同进程复用**场景（如 LSP）。但 LSP 子类可 override `PerformASTRelease()` 为 no-op（最终方案 §4.9 注释已提及），此时 AST 不释放，不存在悬空指针。
3. `ClearGlobalAnnotationInfo()` 未清除 `g_typeAnnoInfo` 和 `g_valueAnnoInfo` 的问题确实存在，但这两个变量在正常流程中已被清空（line 471-472），仅在异常退出时可能残留。

**修复建议**：`ClearGlobalAnnotationInfo()` 应同时清除全部三个全局变量。改动量极小（加两行 `.clear()`），属于防御性编程改进。

### F-04 [Medium] semaInfo.usages 物化代码缺失 — 确认，升级为 High，P0

**裁决：确认，严重程度升级为 High，P0 阻塞**

升级理由：这不是独立的 Medium 问题，而是 F-01 的核心组成部分。`semaInfo.usages` 的键是 `Ptr<const AST::Decl>`，`DependencySerialization.cpp:59` 在序列化时解引用这些键读取 `rawMangleName`。最终方案仅有注释占位（`// semaInfo.usages 同理物化...`），没有实际实现代码。

如果采用 F-01 的方案 A（将 `WriteCachedInfo()` 移到释放前执行），则 `semaInfo.usages` 无需物化（序列化在 AST 存活时完成）。如果采用方案 B（物化所有引用），则必须补全此代码。

**修复方向**：取决于 F-01 的修复方案选择。方案 A 下此问题自动消解；方案 B 下需补全物化代码。

### F-05 [Medium] order 向量未物化 — 确认，升级为 High，P0

**裁决：确认，严重程度升级为 High，P0 阻塞**

升级理由：与 F-04 同理，这是 F-01 的核心组成部分。`order`（`std::vector<const AST::Decl*>`）在 `WriteCachedAST()`（CachedDataSerialization.cpp:91-95）中被解引用，读取 `rawMangleName` 和执行 `Is<MainDecl>(decl)` 类型检查。Phase 2b 中 `order.clear()` 导致 `WriteCachedInfo()` 收到空向量；即使不 clear，Phase 4a 后指针悬空。

**修复方向**：同 F-04，取决于 F-01 的修复方案选择。

### F-06 [Medium] PerformASTRelease 与 ReleaseASTMemory 重复执行 — 确认，维持 Medium，P1

**裁决：确认，严重程度 Medium，P1**

攻击方正确指出 `PerformASTRelease()`（最终方案 §4.9）先调用 `PrepareCodeGenInfo()` 和 `MaterializePackageDependence()`，然后 `ReleaseASTMemory()` Phase 0 中再次调用这两个方法。

代码分析：
- `PrepareCodeGenInfo()` 先 clear `codeGenPkgInfos` 再重新填充——重复执行不会导致错误，但浪费遍历时间
- `MaterializePackageDependence()` 内部调用 `packageManager->ResolveDependence()`，可能重复插入依赖关系。虽然 `MaterializePackageDependenceIfNeeded()` 有 `packageDependenceResolved` 守卫，但 `MaterializePackageDependence()` 本身没有

这是设计不一致，不是正确性问题。但重复执行 `ResolveDependence()` 可能有副作用（重复插入），需要确认。

**修复建议**：在 `ReleaseASTMemory()` Phase 0 中添加守卫：
```cpp
if (codeGenPkgInfos.empty()) { PrepareCodeGenInfo(); }
if (!packageDependenceResolved) { MaterializePackageDependence(); }
```
或者从 `PerformASTRelease()` 中移除直接调用，统一由 `ReleaseASTMemory()` Phase 0 执行。

### F-07 [Low] ReleaseFuncBody 中 const_cast 冗余 — 确认，维持 Low，P2

**裁决：确认，严重程度 Low，P2**

攻击方的分析过程虽然曲折（先认为编译失败，后自我修正），但最终结论正确：`OwnedPtr::get()` 是 const 方法（SafePointer.h:96），返回 `Ptr<T>`，通过 `Ptr<FuncBody>` 访问 `body` 成员得到 `OwnedPtr<Block>&`（非 const），调用 `reset()` 合法。`const_cast` 确实冗余。

**修复建议**：移除 `const_cast`，直接写 `funcDecl->funcBody->body.reset()`。改动量极小，提升代码可读性。

### F-08 [Medium] ReleaseTranslatedNominalBodies 遗漏 EnumDecl — 确认，维持 Medium，P1

**裁决：确认，严重程度 Medium，P1**

代码验证确认：
- `EnumDecl` 继承 `InheritableDecl`（Node.h:1170），**不继承** `ClassLikeDecl`
- `EnumDecl` 有 `members` 字段（Node.h:1181）：`std::vector<OwnedPtr<Decl>> members`
- `InterfaceDecl` 继承 `ClassLikeDecl`（Node.h:1428），被 `DynamicCast<ClassLikeDecl*>` 覆盖
- `StructDecl` 继承 `InheritableDecl`（Node.h:1375），最终方案已单独处理

因此 `EnumDecl` 的方法体确实不会被释放。对于有方法的枚举类型（仓颉语言支持枚举方法），这会降低 A-3 的内存收益。

**修复建议**：在 `releaseMethodBodies` lambda 中增加 `EnumDecl` 分支。改动量极小（4 行代码）。

### F-09 [Low] CachedMangleMap 浅拷贝传播悬空指针 — 确认，降级为 Info，P3

**裁决：确认风险，严重程度降级为 Info（信息级），P3**

降级理由：攻击方自己在分析中已确认此风险**实际已被时序保护**：
1. `ClearASTPointers()` 在 Phase 3h 执行
2. CodeGen 拷贝 `cacheMangles` 在 `CODEGEN` 阶段执行
3. `RELEASE_AST`（包含 Phase 3h）在 `CODEGEN` 之前
4. 因此拷贝时 `importedInlineDeclsPtr` 已被 clear

代码验证确认 `CachedMangleMap` 无自定义拷贝构造函数，但由于时序保证，拷贝时不会传播悬空指针。

**修复建议**：可选的防御性改进——为 `CachedMangleMap` 添加自定义拷贝构造函数，不复制 `importedInlineDeclsPtr`。优先级最低。

### F-10 [Low] TranslateNominalDecls 访问 paramLists 未在安全性验证表中记录 — 确认，维持 Low，P2

**裁决：确认，严重程度 Low，P2**

代码验证确认 `ASTPackage2CHIR.cpp:1308-1312` 中 `TranslateNominalDecls` 访问 `funcBody->paramLists`。A-3 只释放 `funcBody->body`，不释放 `funcBody` 本身和 `paramLists`，因此当前设计安全。

但最终方案 §3.2 安全性验证表中确实未列出此访问。如果未来有人将释放粒度扩大到整个 `funcBody`（`funcBody.reset()`），会导致崩溃。

**修复建议**：在安全性验证表中补充 `TranslateNominalDecls` 对 `funcBody->paramLists` 的访问说明，并在代码注释中标注"只释放 body，不释放 funcBody 本身"。

## 四、F-01/F-02/F-04/F-05 根因分析与统一修复方案

### 4.1 根因

F-01、F-02、F-04、F-05 本质上是同一个根因：**最终方案对 `Compile()` 主循环外部的 AST 数据消费者分析不完整**。

前三轮迭代建立了一个隐含假设：所有 AST 数据消费都发生在 `Compile()` 主循环内部的各个 `CompileStage` 中。但实际上：
- `WriteCachedInfo()` 在 `FrontendTool.cpp:214-217` 中，`Compile()` 返回后调用
- `PerformResultsSaving()` 在 `SAVE_RESULTS` 阶段调用，但其内部通过 `GetSourcePackages()` 访问 `srcPkgs`

### 4.2 推荐修复方案

**推荐方案 A：将缓存写入前移到 AST 释放前**

```
RELEASE_AST 阶段的 PerformASTRelease() 执行顺序：
1. ExportASTSignaturesForIncremental()  — 增量编译 AST 签名导出
2. WriteCachedInfo()                     — 增量编译缓存写入（前移）
3. SaveCjo() (CHIR 模式)                — CJO 保存（前移）
4. PrepareCodeGenInfo()                  — CodeGen 元信息提取
5. MaterializePackageDependence()        — 包依赖物化
6. ReleaseASTMemory()                    — 实际释放
```

方案 A 的优势：
- 不需要修改序列化层的数据结构（`WriteCache`、`SetVarAndFuncDependency`、`SetSemanticInfo` 等）
- 不需要物化 `semaInfo.usages` 和 `order`（序列化在 AST 存活时完成）
- `FrontendTool.cpp:217` 的 `UpdateAndWriteCachedInfoToDisk()` 需要适配（检查 `cachedInfoWritten` 标志，跳过已完成的写入）
- 改动集中在 `PerformASTRelease()` 和 `FrontendTool.cpp`

方案 B（完整物化）的劣势：
- 需要修改 `CompilationCache` 数据结构、`WriteCache()` 签名、`HashedASTWriter` 的多个 Set 方法
- `order` 的物化需要在 `WriteCachedAST()` 中适配字符串键查找（当前通过指针直接查找 `ast.at(mangled)`）
- 改动分散在序列化层多个文件中

### 4.3 ADR-009（新增）：增量编译缓存写入前移到 RELEASE_AST 阶段

- **状态**：建议批准
- **决策**：`WriteCachedInfo()` 和 `ExportASTSignaturesForIncremental()` 在 `PerformASTRelease()` 中、`ReleaseASTMemory()` 之前执行
- **理由**：避免修改序列化层数据结构，改动集中，风险可控
- **约束**：`FrontendTool.cpp` 的 `UpdateAndWriteCachedInfoToDisk()` 需要幂等性守卫

## 七、最终裁决

### 裁决：需修改（Revise Required）— 需补全增量编译缓存写入路径设计后方可编码

本轮发现的 4 个 P0 阻塞项（F-01/F-02/F-04/F-05）揭示了最终设计方案的一个关键盲区：**增量编译的缓存写入路径在 AST 释放后仍需访问 AST 数据**。这是前三轮迭代未覆盖的攻击面。

**不通过的原因**：
1. `WriteCachedInfo()` 在 `Compile()` 返回后执行，访问已释放的 `srcPkgs[0]`、`order`、`semaInfo.usages` — 必定 crash
2. `PerformResultsSaving()` 的 `ExportASTSignature` 和 `SaveCjo` 依赖 `srcPkgs` — 必定静默失败或 crash
3. `semaInfo.usages` 物化代码完全缺失（仅有注释占位）
4. `resultsSaved` 标志未定义

**修复要求**（进入编码的前提条件）：
1. 采纳 ADR-009：将 `WriteCachedInfo()` 前移到 `PerformASTRelease()` 中、`ReleaseASTMemory()` 之前执行
2. 在 `IncrementalCompilerInstance::PerformASTRelease()` 中完成 `ExportASTSignaturesForIncremental()` 和 CHIR 模式下的 `SaveCjo`
3. 定义 `resultsSaved` / `cachedInfoWritten` 标志，确保幂等性
4. `FrontendTool.cpp:217` 的 `UpdateAndWriteCachedInfoToDisk()` 添加幂等性守卫

**预计修复成本**：方案 A 的改动集中在 `PerformASTRelease()` 和 `FrontendTool.cpp`，约 30-40 行代码，不涉及序列化层修改。修复后无需额外设计迭代，可直接进入编码。
