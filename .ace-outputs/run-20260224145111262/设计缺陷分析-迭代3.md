## 二、迭代 2 评审决策复核

### 2.1 N-05 驳回复核：GlobalDeclAnalysis 不访问 funcBody->body

**评审裁决**：驳回（GlobalDeclAnalysis.cpp:46-48 确认只访问 paramLists）

**复核结果**：✅ 驳回正确。`GlobalDeclAnalysis::Run()` 分析全局变量初始化依赖时，遍历的是 `VarWithPatternDecl::initializer`（独立于 `funcBody->body`），不访问函数体代码块。A-3 释放 `funcBody->body` 不影响 GlobalDeclAnalysis。

### 2.2 N-06 驳回复核：CHIR lowering 不执行内联

**评审裁决**：驳回（FunctionInline.cpp 是独立优化 pass）

**复核结果**：✅ 驳回正确。`@inline` 函数的内联在 CHIR 优化阶段（`FunctionInline.cpp`）执行，不在 lowering 阶段。lowering 阶段只翻译函数签名和 body 到 CHIR IR，不做跨函数内联。A-3 在 lowering 中释放 body 不会影响内联。

### 2.3 N-02 确认复核：RELEASE_AST 独立阶段决策

**评审裁决**：确认，保持 RELEASE_AST 独立阶段

## 三、新发现的架构风险

### R-01 [Medium] A-3 批量释放 ReleaseTranslatedNominalBodies 的遍历成本和遗漏风险

**类别**：设计未到位

**问题描述**：

架构优化报告提出在 `TranslateNominalDecls` 返回后批量释放 nominal 类型的方法体：

```cpp
TranslateNominalDecls(pkg);
ReleaseTranslatedNominalBodies(pkg);  // 批量释放
```

但 `ReleaseTranslatedNominalBodies` 的实现需要遍历所有 nominal 类型（class/struct/enum/interface）的所有方法声明，找到其 `funcBody->body` 并 reset。这涉及：

1. `nominalDecls`（普通 nominal 类型）
2. `genericNominalDecls`（泛型 nominal 类型）
3. `importedNominalDecls`（imported nominal 类型 — 不应释放）
4. `importedGenericInstantiatedNominalDecls`（imported 泛型实例化）

遍历逻辑需要区分哪些 nominal 类型的方法体被翻译了（只有当前包的 nominal 类型），哪些没有（imported 的不翻译方法体）。如果遍历逻辑不精确，可能：
- 遗漏某些方法体（内存未释放）
- 错误释放 imported 类型的方法体（这些方法体可能被其他包的 lowering 使用）

**触发输入**：

```cangjie
// 多包编译，包含泛型实例化
package lib
public class Container<T> {
    var value: T
    init(v: T) { value = v }
    func get(): T { return value }
    func set(v: T) { value = v }
}

package app
import lib.*
func main() {
    let c = Container<Int64>(42)
    println(c.get().toString())
}
```

**影响范围**：A-3 Phase 0 的 nominal 类型方法体释放的正确性和完整性。

**修复方向**：
1. `ReleaseTranslatedNominalBodies` 应只遍历 `nominalDecls` 和 `genericNominalDecls`，跳过 imported 类型
2. 需要明确 `TranslateNominalDecls` 内部哪些方法体被实际翻译了（通过 `NeedTranslate` 过滤）
3. 建议在 `TranslateNominalDecls` 内部收集已翻译的方法列表，而非事后遍历

### R-02 [Medium] A-3 的 ReleaseTranslatedInitializers 与 GlobalVarInitializer 的内部状态耦合

**类别**：设计未到位

**问题描述**：

架构优化报告提出在 `TranslateInitOfGlobalVars` 返回后批量释放 initializer：

```cpp
TranslateInitOfGlobalVars(pkg, initOrder);
ReleaseTranslatedInitializers(initOrder);  // 批量释放
```

但 `TranslateInitOfGlobalVars` 委托给 `GlobalVarInitializer::Run()`，其内部逻辑复杂：

```cpp
// GlobalVarInitializer.cpp:537
auto vd = DynamicCast<const AST::VarDecl*>(&decl);
if (vd == nullptr || !vd->initializer || NeedInitGlobalVarByInitFunc(*vd)) {
    return false;
}
```

`NeedInitGlobalVarByInitFunc` 检查 initializer 是否需要通过 init 函数初始化。如果 `ReleaseTranslatedInitializers` 在 `Run()` 返回后释放 `vd->initializer`，但 `initOrder` 中的某些变量的 initializer 实际上没有被翻译（被 `NeedVarLiteralInitFunc` 过滤掉了），释放这些未翻译的 initializer 不会导致 crash，但会浪费遍历时间。

更关键的是，`initializer` 的类型是什么？如果是 `OwnedPtr<Expr>`，reset 后 `VarDecl::initializer` 变为 null。但 `initOrder` 中的 `Decl*` 指针仍然指向 `VarDecl`，后续如果有代码检查 `vd->initializer` 是否为 null 来判断变量是否有初始化，逻辑会被破坏。

**触发输入**：

```cangjie
package test
// 混合：有 initializer 和无 initializer 的全局变量
let a: Int64 = 42                    // literal init
let b: Int64 = computeB()            // func init
var c: Int64                         // no initializer
let d: String = "hello" + "world"    // expr init

func computeB(): Int64 { return a + 1 }
func main() { println(d) }
```

**影响范围**：A-3 的 initializer 释放逻辑的正确性。

**修复方向**：
1. `ReleaseTranslatedInitializers` 应只释放已被 `GlobalVarInitializer` 实际翻译的 initializer
2. 或者在 `GlobalVarInitializer::Run()` 内部，翻译完每个 initializer 后立即释放（更精确）
3. 需要确认 `VarDecl::initializer` 的类型和 reset 后的影响

### R-03 [Low] 混合方案的并行批量释放与串行逐个释放的内存峰值差异未量化

**类别**：可优化项

**问题描述**：

混合方案对串行和并行模式采用不同的释放策略：
- 串行：逐个释放（翻译一个释放一个）
- 并行：批量释放（全部翻译完后统一释放）

并行模式下，所有函数体在翻译期间同时存活，翻译完成后才批量释放。这意味着并行模式的峰值内存 = 所有函数体 AST + 所有函数体 CHIR IR，而串行模式的峰值内存 ≈ 单个函数体 AST + 累积的 CHIR IR。

对于大型包（数百个函数），并行模式的峰值内存可能比串行模式高 30-50%。

**触发输入**：

```cangjie
// 大型包，数百个函数
package large_pkg
func f001(): Int64 { /* 大量代码 */ }
func f002(): Int64 { /* 大量代码 */ }
// ... 500 个函数
func f500(): Int64 { /* 大量代码 */ }
func main() { /* ... */ }
```

**影响范围**：并行编译模式下的峰值内存优化效果。

**修复方向**：
1. 当前方案可接受（并行翻译本身就是短时间内完成的，峰值窗口小）
2. 如果需要优化，可以在 `ParallelUtil` 的 worker 线程中添加翻译后回调（Alpha P4 方案），但会增加接口复杂度
3. 建议在 Phase 2 测试中量化差异，再决定是否优化

### R-04 [Medium] CompileStage 枚举插入 RELEASE_AST 可能影响现有的阶段编号依赖

**类别**：编译器设计缺陷

**问题描述**：

`Compile()` 主循环通过 `CompileStage` 枚举的整数值驱动：

```cpp
for (; i <= endStageNum; i++) {
    if (!performMap[static_cast<CompileStage>(i)](this)) {
        success = false;
        break;
    }
}
```

在 `CHIR` 和 `CODEGEN` 之间插入 `RELEASE_AST` 会改变 `CODEGEN` 及后续阶段的枚举值。如果代码中存在对 `CompileStage` 枚举值的硬编码比较（如 `i < static_cast<int>(CompileStage::CODEGEN)`），插入新阶段会导致这些比较的语义变化。

已知的枚举值比较：
```cpp
// CompilerInstance.cpp:200
if (invocation.globalOptions.NeedDumpASTToScreen() && i < static_cast<int>(CompileStage::MANGLING)) {
    DumpASTToScreen(GetSourcePackages());
}
```

这个比较使用 `MANGLING`（在 CHIR 之前），不受影响。但需要全量搜索是否有其他使用 `CODEGEN` 或后续阶段枚举值的比较。

**触发输入**：任何编译任务，如果存在硬编码的阶段值比较。

**影响范围**：编译流水线的正确性。

**修复方向**：
1. 全量 grep `CompileStage::CODEGEN`、`CompileStage::SAVE`、`CompileStage::LINK` 等后续阶段的使用
2. 确认没有基于枚举整数值的硬编码比较
3. 如果有，需要同步更新

### R-05 [Low] A-3 的 ReleaseFuncBody 实现需要处理 FuncDecl 的多种子类型

**类别**：设计未到位

**问题描述**：

`ReleaseFuncBody` 需要找到 `FuncDecl` 的函数体并释放。但 `FuncDecl` 的函数体存储方式可能因子类型而异：
- 普通函数：`funcBody->body`（`OwnedPtr<Block>`）
- 构造函数（`InitDecl`）：可能有额外的 `initializerList`
- 属性 getter/setter：可能有隐式生成的 body
- 运算符重载：与普通函数相同

`ReleaseFuncBody` 的实现需要统一处理这些情况，或者只处理 `funcBody->body` 这个公共字段。

**修复方向**：
1. 确认所有 `FuncDecl` 子类型的 body 都存储在 `funcBody->body` 中
2. 如果是，`ReleaseFuncBody` 只需 `if (decl.funcBody) decl.funcBody->body.reset();`
3. 如果不同子类型有不同的 body 存储，需要分别处理

## 六、总体评估

经过三轮设计-攻击-评审迭代，方案已充分收敛：

1. **v1 的 4 个 P0 阻塞项**：全部修复，经两轮验证确认
2. **v2 的 8 个新风险点**：2 个驳回（经代码验证正确），6 个已有修复方案
3. **v3 的 5 个新风险点**：0 个 Critical/High，3 个 Medium + 2 个 Low，全部可在编码阶段解决

方案的核心架构决策已稳定：
- RELEASE_AST 独立流水线阶段（规避 ccTys 时序冲突）
- CodeGen 统一单路径（消除双路径维护负担）
- A-3 混合释放策略（串行逐个 + 并行批量 + nominal 批量）
- 5 阶段清理 checklist（Phase 0-4）
- ReleaseASTMemory 设为 protected

方案可以进入编码阶段。剩余 5 个风险点均为实现细节级别，不需要额外的设计迭代。
