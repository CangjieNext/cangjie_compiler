# AST 内存释放方案 — 架构迭代优化报告

## 一、架构问题分析

经过两轮设计-攻击-评审迭代，当前方案（v2 + A-3）已通过评审进入可编码状态。本报告聚焦于实施前的架构瓶颈识别和针对性优化，确保编码阶段不走弯路。

### 1.1 问题 P1：CodeGen 双路径是过度设计

**根因**：v2 方案为兼容 `--no-release-ast` 设计了 `CodegenOnePackage` / `CodegenOnePackageV2` 双路径，引入了不必要的维护负担（N-01）。

**影响范围**：`DefaultCompilerInstance.cpp` 的 `PerformCodeGen`、`CodegenOnePackage`、`EmitLLVMSimilarBytecode` 三个函数各需要 V2 副本。

**代码证据**：`CodegenOnePackage`（DefaultCompilerInstance.cpp:222-254）对 `AST::Package` 的实际依赖仅为 `pkg.IsEmpty()` 和 `pkg.fullPackageName`。`GenPackageModules()` 签名接收 `CHIRData&`，完全不依赖 AST。这意味着 `PackageCodeGenInfo` 的提取成本极低（两个字段），没有理由保留旧路径。

**结论**：双路径是对 `--no-release-ast` 兼容性的过度设计。即使 AST 未释放，也可以统一走 `PackageCodeGenInfo` 路径。

### 1.2 问题 P2：RELEASE_AST 阶段插入点的流水线耦合

**根因**：`Compile()` 主循环（CompilerInstance.cpp:175-213）通过 `CompileStage` 枚举驱动，每个阶段对应一个 `Perform*()` 虚方法。新增 `RELEASE_AST` 阶段需要修改枚举、`Compile()` 循环、以及 `CompileStrategy` 的阶段映射。

**影响范围**：
- `CompileStage` 枚举（CompilerInstance.h:45-65）：需在 `CHIR` 和 `CODEGEN` 之间插入
- `Compile()` 循环（CompilerInstance.cpp:175-213）：需添加 `case RELEASE_AST`
- `CompileStrategy`：需注册新阶段
- `IncrementalCompilerInstance`：需 override `PerformASTRelease()`

**结论**：这是必要的架构改动，但插入点选择需要精确。N-02 已证明不能在 `PerformCHIRCompilation()` 内部释放（ccTys 时序冲突），必须作为独立阶段。

### 1.3 问题 P3：A-3 方案与 TranslateNominalDecls 的释放粒度不匹配

**根因**：A-3 方案的释放逻辑在 `TranslateAllDecls` 的三个子步骤中各不相同：
- `TranslateNominalDecls`（ASTPackage2CHIR.cpp:1286-1339）：通过 `TranslateVecDecl()` 批量翻译 nominal 类型，方法体的翻译嵌套在类型翻译内部，释放点不在顶层循环
- `TranslateInitOfGlobalVars`（AST2CHIR.cpp:274-281）：委托给 `GlobalVarInitializer::Run()`，释放点在 `Run()` 内部
- `TranslateTopLevelDecls`（AST2CHIR.cpp:371-395）：顶层循环直接可见，释放点清晰

**影响范围**：A-3 在 `TranslateNominalDecls` 中的实现比预期复杂——需要深入 `TranslateVecDecl` 和 `Translator::TranslateASTNode` 的调用链才能找到合适的释放点。

**结论**：A-3 应分两步实施：先在 `TranslateTopLevelDecls`（串行和并行）中实现（释放点清晰），再扩展到 `TranslateNominalDecls` 和 `TranslateInitOfGlobalVars`。

### 1.4 问题 P4：并行翻译的 A-3 释放需要修改 ParallelUtil 接口

**根因**：`TranslateInParallel()`（AST2CHIR.cpp:409-415）将翻译委托给 `ParallelUtil::RunAST2CHIRInParallel()`，该方法的签名（ParallelUtil.h:32-79）不包含翻译后回调。A-3 需要在每个函数翻译完成后执行 `funcBody->body.reset()`，但当前接口不支持。

**影响范围**：`ParallelUtil.h` 和 `ParallelUtil.cpp` 需要扩展接口。

**结论**：需要为 `RunAST2CHIRInParallel` 添加可选的 post-translate 回调参数，或者在 `ParallelUtil` 内部的翻译循环中直接添加释放逻辑。

### 1.5 问题 P5：annoFactoryFuncs 的串行翻译遗漏

**根因**：`TranslateAllDecls` 在并行/串行翻译之后，还有一个单独的 `annoFactoryFuncs` 串行翻译循环（AST2CHIR.cpp:391-395）。A-3 方案的 `incremental-release-analysis-v2.md` 未提及此循环的释放处理。

**代码证据**：
```cpp
// AST2CHIR.cpp:391-395
for (auto decl : annoFactoryFuncs) {
    auto trans = CreateTranslator();
    trans.SetTopLevel(*decl.first);
    trans.TranslateAnnoFactoryFuncBody(*decl.first, *decl.second);
}
```

**结论**：`annoFactoryFuncs` 翻译完成后同样可以释放函数体，需要补充到 A-3 实现中。

## 二、优化方案对比

针对上述 5 个架构问题，提出两套优化方案。

### 方案 Alpha：渐进式实施（局部优化优先）

**核心思路**：保持 v2 架构框架不变，逐个修补问题点。

| 问题 | 处理方式 |
|------|---------|
| P1 双路径 | 编码时直接实现单路径，始终提取 `PackageCodeGenInfo`，删除旧 `CodegenOnePackage` |
| P2 流水线插入 | 在 `CompileStage` 枚举的 `CHIR` 和 `CODEGEN` 之间插入 `RELEASE_AST` |
| P3 NominalDecls 释放 | A-3 第一阶段仅在 `TranslateTopLevelDecls` 中释放，NominalDecls 延后 |
| P4 并行接口 | 为 `RunAST2CHIRInParallel` 添加 `postTranslateCallback` 可选参数 |
| P5 annoFactory 遗漏 | 在 annoFactoryFuncs 循环中添加 `ReleaseFuncBody` 调用 |

**实施路径**：
```
Phase 0: A-3 串行模式（仅 TranslateTopLevelDecls 串行循环）
  ├─ 在 globalAndMemberFuncs 循环中添加 body.reset()
  ├─ 在 localConstFuncs 循环中添加 body.reset()
  └─ 在 annoFactoryFuncs 循环中添加 body.reset()
  改动量：~20 行，风险极低

Phase 1: A-3 并行模式
  ├─ ParallelUtil::RunAST2CHIRInParallel 添加回调参数
  └─ 回调中执行 funcBody->body.reset()
  改动量：~30 行，需验证线程安全

Phase 2: v2 基础设施
  ├─ CompileStage 枚举添加 RELEASE_AST
  ├─ Compile() 循环添加 case 分支
  ├─ CompilerInstance 添加 PerformASTRelease() 虚方法
  ├─ ReleaseASTMemory() 设为 protected
  └─ --no-release-ast 开关
  改动量：~80 行

Phase 3: v2 核心清理
  ├─ PackageCodeGenInfo 提取 + CodeGen 单路径
  ├─ 5 阶段清理 checklist 实现
  ├─ IncrementalCI::PerformASTRelease() override
  └─ cacheMangles.ClearASTPointers()
  改动量：~200 行

Phase 4: 测试验证
  ├─ ASan 全量回归
  ├─ 增量编译专项测试
  └─ 内存峰值对比
```

**优势**：
- 每个 Phase 独立可测试、可回退
- Phase 0 立即见效（释放 40-60% AST 内存，仅覆盖顶层函数）
- 不破坏现有模块接口稳定性

**劣势**：
- Phase 总数多，需要 4 次独立提交和验证
- NominalDecls 的方法体释放延后，Phase 0 的内存收益不完整

### 方案 Beta：整合式实施（A-3 + v2 一次到位）

**核心思路**：将 A-3 和 v2 合并为一个完整的实施方案，减少中间状态。

| 问题 | 处理方式 |
|------|---------|
| P1 双路径 | 同 Alpha |
| P2 流水线插入 | 同 Alpha |
| P3 NominalDecls 释放 | 在 `TranslateVecDecl` 返回后批量释放已翻译 nominal 类型的方法体 |
| P4 并行接口 | 不修改 ParallelUtil 接口，改为在 `TranslateTopLevelDeclsInParallel` 返回后批量释放 |
| P5 annoFactory 遗漏 | 同 Alpha |

**关键差异**：P4 的处理方式不同。方案 Beta 不在并行翻译过程中逐个释放，而是在并行翻译全部完成后批量释放所有已翻译函数的 body。

```cpp
// 方案 Beta 的 TranslateAllDecls 修改
void AST2CHIR::TranslateAllDecls(const AST::Package& pkg, const InitOrder& initOrder)
{
    // step 1: translate nominal decls
    TranslateNominalDecls(pkg);
    ReleaseTranslatedNominalBodies(pkg);  // 批量释放 nominal 方法体

    // step 2: translate global var init
    TranslateInitOfGlobalVars(pkg, initOrder);
    ReleaseTranslatedInitializers(initOrder);  // 批量释放 initializer

    // step 3: translate function bodies
    if (opts.GetJobs() > 1) {
        TranslateTopLevelDeclsInParallel();
    } else {
        // 串行翻译（同 Alpha Phase 0）
    }
    // 批量释放所有已翻译函数体（串行和并行统一处理）
    ReleaseAllTranslatedFuncBodies();

    // annoFactoryFuncs
    for (auto decl : annoFactoryFuncs) { /* ... */ }
    ReleaseAnnoFactoryBodies();

    // step 4: set CompileTimeValue for lambda
    // ...
}
```

**实施路径**：
```
Phase 0: A-3 完整实现（串行 + 并行 + NominalDecls + GlobalVarInit）
  改动量：~80 行，集中在 AST2CHIR.cpp

Phase 1: v2 完整实现（基础设施 + 核心清理 + CodeGen 单路径）
  改动量：~280 行

Phase 2: 测试验证
```

**优势**：
- Phase 数量少（3 个），提交次数少
- A-3 一次覆盖所有翻译路径，内存收益完整（60-80%）
- 不需要修改 ParallelUtil 接口（批量释放在并行完成后执行）

**劣势**：
- Phase 0 改动量较大，回退粒度粗
- 并行模式下的批量释放比逐个释放的峰值内存收益略低（需等待所有并行任务完成）
- NominalDecls 的方法体释放需要额外遍历 nominal 类型列表

## 三、推荐方案及理由

### 推荐：方案 Beta（整合式实施），但对 P4 采用 Alpha 的逐个释放策略

**混合方案**：取两者之长。

```
Phase 0: A-3 完整实现
  ├─ 串行模式：在 TranslateTopLevelDecls 循环中逐个释放（Alpha P0）
  ├─ 并行模式：在 TranslateTopLevelDeclsInParallel 返回后批量释放（Beta P4）
  ├─ NominalDecls：在 TranslateNominalDecls 返回后批量释放方法体（Beta P3）
  ├─ GlobalVarInit：在 TranslateInitOfGlobalVars 返回后批量释放 initializer（Beta P3）
  └─ annoFactoryFuncs：在循环中逐个释放
  改动量：~60 行，集中在 AST2CHIR.cpp 的 TranslateAllDecls

Phase 1: v2 完整实现
  ├─ RELEASE_AST 流水线阶段 + astReleased 标记 + --no-release-ast
  ├─ PackageCodeGenInfo + CodeGen 单路径（消除双路径）
  ├─ 5 阶段清理 checklist（Phase 3 析构顺序修正为 typeChecker → typeManager）
  ├─ IncrementalCI::PerformASTRelease() override
  ├─ cacheMangles.ClearASTPointers()
  └─ ReleaseASTMemory() 设为 protected
  改动量：~280 行

Phase 2: 测试验证
  ├─ ASan 全量回归（Debug 构建）
  ├─ 增量编译专项测试（closure 类型变化场景）
  ├─ 内存峰值对比（大型项目 before/after）
  └─ --no-release-ast 回退验证
```

**选择理由**：

1. **并行模式用批量释放而非逐个释放**：避免修改 `ParallelUtil` 接口。`ParallelUtil::RunAST2CHIRInParallel` 是通用并行工具，为 AST 释放添加回调会污染其接口。批量释放在并行完成后执行，峰值内存差异可忽略（并行翻译本身就是短时间内完成的）。

2. **NominalDecls 用批量释放**：`TranslateNominalDecls` 内部的翻译逻辑复杂（涉及泛型实例化、extends 处理），在其内部插入释放逻辑侵入性高。在其返回后批量遍历 nominal 类型列表释放方法体，侵入性低。

3. **串行模式用逐个释放**：串行循环结构简单，逐个释放的代码改动最小（每个循环体末尾加一行 `ReleaseFuncBody`），且峰值内存收益最大。

4. **CodeGen 统一为单路径**：消除 N-01 双路径风险，`--no-release-ast` 模式下同样提取 `PackageCodeGenInfo` 但不释放 AST，CodeGen 始终走同一路径。

## 四、迁移路径和风险评估

### 4.1 Phase 0（A-3）迁移路径

**修改文件**：仅 `src/CHIR/AST2CHIR/AST2CHIR.cpp`（+ 头文件声明）

**具体改动**：

```cpp
// AST2CHIR.h — 新增辅助方法声明
private:
    void ReleaseFuncBody(const AST::Decl& decl);
    void ReleaseVarInitializer(AST::VarDeclAbstract& decl);
    void ReleaseTranslatedNominalBodies(const AST::Package& pkg);
    void ReleaseTranslatedInitializers(const InitOrder& initOrder);
    void ReleaseAllTranslatedFuncBodies();
```

```cpp
// AST2CHIR.cpp — TranslateAllDecls 修改
void AST2CHIR::TranslateAllDecls(const AST::Package& pkg, const InitOrder& initOrder)
{
    // step 1: translate nominal decls
    TranslateNominalDecls(pkg);
    ReleaseTranslatedNominalBodies(pkg);  // +++ 新增

    // step 2: translate global var init
    TranslateInitOfGlobalVars(pkg, initOrder);
    ReleaseTranslatedInitializers(initOrder);  // +++ 新增

    // step 3: translate function bodies
    if (opts.GetJobs() > 1) {
        TranslateTopLevelDeclsInParallel();
        ReleaseAllTranslatedFuncBodies();  // +++ 新增：并行完成后批量释放
    } else {
        for (auto decl : globalAndMemberFuncs) {
            if (!NeedTranslate(*decl)) { continue; }
            auto trans = CreateTranslator();
            trans.SetTopLevel(*decl);
            Translator::TranslateASTNode(*decl, trans);
            if (decl->TestAttr(AST::Attribute::GLOBAL)) {
                trans.CollectValueAnnotation(*decl);
            }
            ReleaseFuncBody(*decl);  // +++ 新增：逐个释放
        }
        for (auto decl : std::as_const(localConstFuncs.stableOrderValue)) {
            auto trans = CreateTranslator();
            trans.SetTopLevel(*decl);
            Translator::TranslateASTNode(*decl, trans);
            ReleaseFuncBody(*decl);  // +++ 新增
        }
    }
    // annoFactoryFuncs
    for (auto decl : annoFactoryFuncs) {
        auto trans = CreateTranslator();
        trans.SetTopLevel(*decl.first);
        trans.TranslateAnnoFactoryFuncBody(*decl.first, *decl.second);
        ReleaseFuncBody(*decl.first);  // +++ 新增
    }
    // step 4: set CompileTimeValue for lambda — 不受影响，操作 CHIR IR
    // ...
}
```

```cpp
// AST2CHIR.cpp — 辅助方法实现
void AST2CHIR::ReleaseFuncBody(const AST::Decl& decl)
{
    if (auto* funcDecl = DynamicCast<const AST::FuncDecl*>(&decl)) {
        if (funcDecl->funcBody && funcDecl->funcBody->body) {
            const_cast<AST::FuncBody*>(funcDecl->funcBody.get())->body.reset();
        }
    }
}

void AST2CHIR::ReleaseAllTranslatedFuncBodies()
{
    for (auto decl : globalAndMemberFuncs) {
        if (NeedTranslate(*decl)) {
            ReleaseFuncBody(*decl);
        }
    }
    for (auto decl : std::as_const(localConstFuncs.stableOrderValue)) {
        ReleaseFuncBody(*decl);
    }
}
```

**接口稳定性**：不修改任何现有公开接口。`ReleaseFuncBody` 是 private 方法。`TranslateAllDecls` 的签名和语义不变。

### 4.3 风险矩阵

| 风险 | 概率 | 影响 | Phase | 缓解措施 |
|------|------|------|-------|---------|
| A-3 释放后仍有代码路径访问 body | 低 | 高（crash） | 0 | ASan 全量测试；`body.reset()` 后为 null，解引用立即暴露 |
| NominalDecls 批量释放遗漏某些方法体 | 中 | 低（内存未完全释放） | 0 | 内存对比测试验证收益；遗漏不影响正确性 |
| 并行翻译后批量释放的时序安全 | 低 | 高（crash） | 0 | 批量释放在 `TranslateTopLevelDeclsInParallel()` 返回后执行，所有线程已 join |
| CodeGen 单路径遗漏旧路径的某些逻辑 | 中 | 高（编译产出错误） | 1 | 对比新旧路径的代码差异；.bc 文件 diff 验证 |
| IncrementalCI 缓存保存遗漏 | 中 | 高（增量编译错误） | 1 | 增量编译专项测试（closure 类型变化、泛型实例化） |
| 析构函数与 ReleaseASTMemory 交互 | 低 | 中（退出时 crash） | 1 | `astReleased` 标记 + 析构函数 `if (!astReleased)` 守卫 |
| `const_cast` 修改 const AST 节点 | 低 | 低（代码规范） | 0 | A-3 的 `const_cast` 仅用于 `body.reset()`，语义上是释放而非修改 |

### 4.4 回退策略

- **Phase 0 回退**：删除 `ReleaseFuncBody` 调用和辅助方法，零副作用
- **Phase 1 回退**：`--no-release-ast` 命令行开关，运行时禁用整个 RELEASE_AST 阶段
- **紧急回退**：revert Phase 0 + Phase 1 的 git commits，恢复到释放前状态

### 4.5 关键决策确认

| ADR | 决策 | 理由 |
|-----|------|------|
| ADR-001 | RELEASE_AST 作为独立流水线阶段（不在 PerformCHIRCompilation 内部） | N-02 证明 A-2 与增量编译 ccTys 时序冲突 |
| ADR-002 | CodeGen 统一为单路径 | N-01 双路径维护成本不可接受 |
| ADR-004 | A-3 优先实施，并行模式用批量释放 | 避免修改 ParallelUtil 通用接口 |
| ADR-005 | ReleaseASTMemory 设为 protected | 防止绕过 IncrementalCI 的前置保存逻辑 |
| ADR-006（新增） | Phase 3 析构顺序：typeChecker → typeManager | 与现有析构函数一致，N-03 修正 |
| ADR-007（新增） | A-3 的 NominalDecls 释放采用批量模式 | 避免侵入 TranslateNominalDecls 内部复杂逻辑 |
