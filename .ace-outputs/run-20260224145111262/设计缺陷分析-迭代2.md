# AST 内存释放方案 — 迭代攻击分析报告（v2 + A-3）

## 人工反馈回应

> **反馈 1 & 2**：TranslateToCHIR 执行完之后就释放，注意生命周期更长的变量保存的 AST 指针及时置空

**处理结果**：

1. **释放时机**：v2 方案已采纳，在 CHIR lowering 完成后释放。补充分析文档 `incremental-release-analysis.md` 论证了"边翻译边释放"不可行。迭代 2 进一步提出 A-3 方案（函数体粒度释放），本报告对 A-3 进行攻击验证。

2. **长生命周期指针置空**：v2 方案的 5 阶段清理 checklist 已覆盖绝大部分持有者。本轮迭代发现 **4 个新的遗漏点**（见 N-01 至 N-04），其中 `CachedMangleMap::importedInlineDeclsPtr` 和 `chirInfo.ccTys` 的时序问题是最关键的新发现。

## 二、新发现的架构风险

### N-01 [High] CodeGen 双路径设计引入维护负担和语义分歧风险

**类别**：设计未到位

**问题描述**：

v2 方案为 CodeGen 设计了双路径：

```cpp
bool DefaultCIImpl::PerformCodeGen()
{
    RearrangeImportedPackageDependenceV2();
    bool ret = true;
    if (ci.IsASTReleased()) {
        for (auto& info : ci.codeGenPkgInfos) {
            ret = ret && CodegenOnePackageV2(info, false);
        }
    } else {
        for (auto& srcPkg : ci.GetSourcePackages()) {
            ret = ret && CodegenOnePackage(*srcPkg, false);
        }
    }
    return ret;
}
```

这意味着：
1. `CodegenOnePackage` 和 `CodegenOnePackageV2` 是两个独立的代码路径，必须保持语义一致
2. `EmitLLVMSimilarBytecode` 和 `EmitLLVMSimilarBytecodeV2` 同理
3. 未来对 CodeGen 的任何修改都必须同步两个路径
4. `--no-release-ast` 走旧路径，正常编译走新路径 — 测试覆盖容易遗漏

**触发场景**：未来开发者修改 `CodegenOnePackage` 添加新功能，忘记同步到 `CodegenOnePackageV2`。

```cangjie
// 假设未来添加了 profile-guided optimization 支持
// 开发者在 CodegenOnePackage 中添加了 PGO 逻辑
// 但忘记在 CodegenOnePackageV2 中同步
package test
func main() {
    for (i in 0..1000000) { compute(i) }
}
func compute(x: Int64): Int64 { return x * x + 1 }
```

**影响范围**：长期维护成本。两个路径的语义分歧可能导致 `--no-release-ast` 模式下的编译结果与正常模式不一致。

**修复方向**：
1. 优选方案：统一为单一路径，始终使用 `PackageCodeGenInfo` 驱动（即使 AST 未释放也提取 info）
2. 如果保留双路径，添加 CI 测试确保两个路径产出相同的 .bc 文件

### N-02 [High] chirInfo.ccTys 在增量编译中的时序冲突 — v2 方案 A-2 与 IncrementalCI 不兼容

**类别**：编译器设计缺陷

**问题描述**：

`IncrementalCompilerInstance::PerformCHIRCompilation()` 的实现：

```cpp
// IncrementalCompilerInstance.cpp:450-466
bool IncrementalCompilerInstance::PerformCHIRCompilation()
{
    auto ret = CompilerInstance::PerformCHIRCompilation();
    for (auto ty : chirInfo.ccTys) {       // ← 读取 ccTys
        changedTypes.insert(ty);            // ← 复制到 changedTypes
    }
    // ...
    return ret;
}
```

v2 方案的 `ReleaseASTMemory()` Phase 2 清理 `chirInfo.ccTys.clear()`。

**关键冲突**：如果采用 A-2 方案（在 `PerformCHIRCompilation()` 末尾调用 `ReleaseASTMemory()`），则 `CompilerInstance::PerformCHIRCompilation()` 内部会调用 `ReleaseASTMemory()`，清空 `chirInfo.ccTys`。但 `IncrementalCompilerInstance::PerformCHIRCompilation()` 在基类方法返回后才读取 `chirInfo.ccTys` — 此时已被清空！

```
IncrementalCI::PerformCHIRCompilation()
  └─ CompilerInstance::PerformCHIRCompilation()
       └─ ... lowering ...
       └─ ReleaseASTMemory()     ← ccTys.clear() 在这里！
  └─ for (auto ty : chirInfo.ccTys)  ← 空集合，changedTypes 丢失！
```

**触发输入**：增量编译模式下任何包含 closure 的代码。

```cangjie
// 增量编译，修改了 closure 相关代码
package test
func apply(f: () -> Int64): Int64 { return f() }
func main() {
    let x = 42
    println(apply({ => x }).toString())
}
```

第二次编译时修改 `x` 的类型，增量编译需要 `changedTypes` 来判断哪些 struct layout 需要重新生成。但 `changedTypes` 为空，导致 layout 不更新，生成错误的目标代码。

**影响范围**：增量编译的正确性。closure convert 产生的 struct 类型变化不会被检测到。

**修复方向**：
1. 如果采用 A-2（在 `PerformCHIRCompilation()` 末尾释放），必须在 `IncrementalCompilerInstance::PerformCHIRCompilation()` 中**先读取 ccTys，再调用基类方法**：
```cpp
bool IncrementalCompilerInstance::PerformCHIRCompilation()
{
    auto ret = CompilerInstance::PerformCHIRCompilation();
    // 此时 ccTys 可能已被清空！必须调整顺序
}
```
改为：
```cpp
bool IncrementalCompilerInstance::PerformCHIRCompilation()
{
    auto ret = CompilerInstance::PerformCHIRCompilation();
    // 在基类中，ReleaseASTMemory 不应清理 ccTys
    // 或者在 IncrementalCI::PerformASTRelease() 中处理
}
```
2. 更安全的方案：保持 `RELEASE_AST` 作为独立流水线阶段（v2 原方案），不采用 A-2

### N-03 [Medium] TypeChecker → TypeManager 析构顺序在 v2 中被反转

**类别**：编译器设计缺陷

**问题描述**：

v2 方案 Phase 3 的清理顺序：

```cpp
// Phase 3a
delete typeManager;    // 先删 TypeManager
typeManager = nullptr;

// Phase 3b
delete typeChecker;    // 后删 TypeChecker
typeChecker = nullptr;
```

但 v2 文档 §1.3 明确指出：

> `TypeChecker` 持有 `TypeManager&` 引用 → 必须先 delete `typeChecker`，再 delete `typeManager`

**代码中的实际顺序**（`CompilerInstance.cpp:85-100` 析构函数）：

```cpp
~CompilerInstance()
{
    srcPkgs.clear();
    pkgCtxMap.clear();
    delete typeChecker;   // 先删 TypeChecker ✅
    delete typeManager;   // 后删 TypeManager ✅
    delete testManager;
    delete gim;
    delete packageManager;
}
```

v2 方案的 Phase 3 代码将顺序写反了（先 typeManager 后 typeChecker），与文档描述和现有析构函数的顺序矛盾。

**触发输入**：任何正常编译。

**影响范围**：如果 `TypeChecker` 的析构函数访问 `TypeManager&` 引用（例如释放通过 TypeManager 分配的资源），先删 TypeManager 会导致 TypeChecker 析构时访问已释放内存。

**修复方向**：修正 Phase 3 的顺序为：
```cpp
// 3a. 先删 TypeChecker（持有 TypeManager& 引用）
delete typeChecker;    typeChecker = nullptr;
// 3b. 再删 TypeManager
delete typeManager;    typeManager = nullptr;
```

### N-04 [Medium] CachedMangleMap::importedInlineDeclsPtr 持有 AST 裸指针，v2 未清理

**类别**：编译器设计缺陷 — 遗漏清理

**问题描述**：

`CachedMangleMap` 有一个 private 成员：

```cpp
// CachedMangleMap.h:77
std::unordered_set<const Cangjie::AST::Decl*> importedInlineDeclsPtr;
```

这是 **AST 裸指针**（非 `Ptr<>`），在 `EmplaceImportedInlineDeclPtr` 中填充，在 `UpdateImportedInlineDeclsMangle` 中解引用读取 `mangledName`。

`UpdateImportedInlineDeclsMangle` 在 `PerformMangling()` 阶段调用（CHIR 之前），所以解引用时 AST 存活。但 `importedInlineDeclsPtr` 在 AST 释放后仍持有悬空指针。

`GenPackageModules`（CodeGen 入口）在 `EmitPackageIR.cpp:592` 复制 `cacheMangles`：

```cpp
cachedMangleMap = StaticCast<IncrementalCompilerInstance&>(compilerInstance).cacheMangles;
```

这个复制包含 `importedInlineDeclsPtr` 中的悬空指针。虽然 CodeGen 当前不访问 `importedInlineDeclsPtr`（只用 `importedInlineDecls` 字符串集合），但：
1. 复制操作本身是安全的（只复制指针值，不解引用）
2. 但如果未来有人在 CodeGen 中调用 `UpdateImportedInlineDeclsMangle()`，会触发 use-after-free
3. `Dump()` 方法不访问 `importedInlineDeclsPtr`，安全

v2 方案的 `IncrementalCompilerInstance::PerformASTRelease()` 清理了 `changedTypes` 和 `declsToBeReCompiled`，但**没有清理 `cacheMangles.importedInlineDeclsPtr`**。

**触发输入**：增量编译模式下导入 inline 函数的包。

```cangjie
// lib.cj（已编译为 .cjo）
package lib
public inline func fastAdd(a: Int64, b: Int64): Int64 { return a + b }

// app.cj（增量编译）
package app
import lib.*
func main() { println(fastAdd(1, 2).toString()) }
```

**影响范围**：当前无直接危害（CodeGen 不解引用），但属于悬空指针的潜在风险。

**修复方向**：在 `IncrementalCompilerInstance::PerformASTRelease()` 中添加：
```cpp
cacheMangles.importedInlineDeclsPtr.clear();
// 或者直接
cacheMangles.Clear();
```

### N-05 [High] A-3 方案（函数体粒度释放）的安全性存疑 — GlobalDeclAnalysis 访问 funcBody

**类别**：编译器设计缺陷（针对 A-3 新方案）

**问题描述**：

A-3 方案提出在 `TranslateAllDecls`（Step 4）中，每翻译完一个函数立即 `funcBody->body.reset()`。

但 `GlobalDeclAnalysis`（Step 2）的分析结果被 Step 4 使用。`GlobalDeclAnalysis::Run()` 构建的依赖图中，`varPatternDeclMap` 持有 `Ptr<const AST::VarWithPatternDecl>`：

```cpp
// GlobalDeclAnalysis.h
std::unordered_map<Ptr<const AST::Node>, Ptr<const AST::VarWithPatternDecl>> varPtternDeclMap;
```

Step 4 的 `TranslateInitOfGlobalVars` 使用 `initOrder`（来自 Step 2 的排序结果），其中包含 `const AST::Decl*` 指针。如果 A-3 在翻译全局变量初始化后释放 initializer，但 `initOrder` 中后续的变量依赖于已释放变量的初始化表达式（通过 `VarWithPatternDecl` 的 `initializer` 字段），则会 crash。

更关键的是，A-3 文档声称：

> `GlobalDeclAnalysis` 访问 `funcBody->paramLists`（参数列表），但不访问 `funcBody->body`（代码块）

这需要验证。`GlobalDeclAnalysis` 分析全局变量的初始化依赖时，需要遍历初始化表达式来发现引用关系。初始化表达式存储在哪里？如果在 `VarWithPatternDecl::initializer` 中（而非 `funcBody->body`），则 A-3 释放 `funcBody->body` 是安全的。但如果全局变量的初始化被包装在一个隐式函数的 body 中，释放 body 就会破坏依赖分析。

**触发输入**：

```cangjie
// 全局变量初始化依赖链
package test
let a: Int64 = compute()
let b: Int64 = a + 1        // b 依赖 a
let c: Int64 = b * 2        // c 依赖 b

func compute(): Int64 {
    return 42
}

func main() {
    println(c.toString())
}
```

**影响范围**：A-3 方案的正确性。如果全局变量初始化表达式在 `funcBody->body` 中，释放 body 会破坏 Step 4 的翻译。

**修复方向**：
1. 在实施 A-3 前，必须精确验证全局变量初始化表达式的存储位置
2. 如果初始化表达式在 `funcBody->body` 中，A-3 不能释放全局变量初始化函数的 body
3. 建议 A-3 只释放**用户定义函数**的 body，不释放编译器生成的初始化函数 body

### N-06 [Medium] A-3 方案并行翻译中的 funcBody->body.reset() 线程安全问题

**类别**：编译器设计缺陷（针对 A-3 新方案）

**问题描述**：

A-3 方案声称"并行翻译时每个函数的 body 只被一个线程读取，释放不存在竞争"。

但 `TranslateTopLevelDeclsInParallel` 的实现中，函数体翻译可能触发对其他函数的内联展开或常量折叠。如果函数 A 的翻译触发了对函数 B 的 body 的读取（例如通过 `@inline` 注解或编译器自动内联），而函数 B 的 body 已被另一个线程翻译后释放，则会 crash。

```cangjie
// 并行翻译中的交叉引用
package test

@inline
func helper(): Int64 { return 42 }

func foo(): Int64 { return helper() + 1 }  // 翻译 foo 时可能读取 helper 的 body
func bar(): Int64 { return helper() + 2 }  // 翻译 bar 时也可能读取 helper 的 body
```

如果 `helper` 的 body 在翻译完成后被释放，而 `foo` 或 `bar` 的翻译（在另一个线程中）需要读取 `helper` 的 body 进行内联，则会触发 use-after-free。

**影响范围**：A-3 方案在有 `@inline` 函数的场景下可能不安全。

**修复方向**：
1. 验证 CHIR lowering 阶段是否执行内联（如果内联在 CHIR 优化阶段而非 lowering 阶段，则 A-3 安全）
2. 如果 lowering 阶段有内联，A-3 需要标记 `@inline` 函数的 body 不可释放
3. 或者只在单线程模式下启用 A-3 的 body 释放

### N-07 [Medium] v2 方案 Phase 0d 的 PerformResultsSaving 在非 CHIR 模式下的增量编译遗漏

**类别**：设计未到位

**问题描述**：

v2 方案 Phase 0d：

```cpp
// 0d. CHIR 输出模式下提前保存 CJO
if (invocation.globalOptions.outputMode == GlobalOptions::OutputMode::CHIR) {
    PerformResultsSaving();
    resultsSaved = true;
}
```

这只处理了 CHIR 输出模式。但 `IncrementalCompilerInstance::PerformResultsSaving()` 在**所有模式下**都需要 AST（调用 `ExportASTSignature`）。

v2 方案 §1.4 设计了 `IncrementalCompilerInstance::PerformASTRelease()` override，在释放前调用 `PerformResultsSaving()`。但 Phase 0d 的条件判断只检查 CHIR 模式，不检查增量编译模式。

如果 `CompilerInstance::ReleaseASTMemory()` 被直接调用（而非通过 `PerformASTRelease()`），Phase 0d 不会为增量编译保存结果。

**触发场景**：如果有代码路径直接调用 `ReleaseASTMemory()` 而非 `PerformASTRelease()`。

**影响范围**：增量编译的 CJO 缓存丢失。

**修复方向**：
1. 确保 `ReleaseASTMemory()` 只能通过 `PerformASTRelease()` 调用（将其设为 private/protected）
2. 或者在 Phase 0d 中也检查增量编译模式

### N-08 [Low] PackageManager::ClearASTReferences() 的接口设计缺少具体实现说明

**类别**：设计未到位

**问题描述**：

v2 方案定义了：

```cpp
void PackageManager::ClearASTReferences()
{
    packageDependence.clear();
}
```

但 `PackageManager` 的实际定义和成员变量未在 v2 文档中审计。`packageDependence` 是否是唯一持有 AST 指针的字段？`PackageManager` 是否还有其他 AST 引用？

v2 方案在 Phase 3g 注释中提到"如果 CodeGen 仍需要 packageManager，则仅清理 AST 引用"，但没有明确 CodeGen 是否需要 packageManager。

**修复方向**：
1. 审计 `PackageManager` 的完整成员列表
2. 明确 CodeGen 是否依赖 `PackageManager`
3. 如果不依赖，直接 `delete packageManager; packageManager = nullptr;`

## 三、A-3 方案专项评估

### 3.1 A-3 方案概述

在 `TranslateAllDecls`（Step 4）中，每翻译完一个函数体，立即 `funcBody->body.reset()`。预期在 lowering 过程中逐步释放 60-80% 的 AST 内存。

### 3.2 A-3 方案风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| GlobalDeclAnalysis 依赖 funcBody（N-05） | 中 | 高 | 需精确验证初始化表达式存储位置 |
| 并行翻译中 @inline 函数交叉引用（N-06） | 低-中 | 高 | 验证 lowering 是否执行内联 |
| OwnedPtr<Block>::reset() 的析构级联 | 低 | 中 | Block 析构应只释放子节点，不影响父节点 |
| AST2CHIRCheck 访问 body | 低 | 高 | A-3 文档已声称不访问，需代码验证 |

### 3.3 A-3 方案建议

A-3 的思路有价值（在 lowering 过程中逐步释放内存），但需要更严格的安全性验证：
1. 必须用 ASan 全量测试验证，不能仅靠代码审计
2. 建议先在单线程模式下验证，再扩展到并行模式
3. 建议只释放用户定义函数的 body，不释放编译器生成的隐式函数 body

## 六、总体评估

v2 方案相比 v1 有显著改进，4 个 P0 阻塞项全部得到了合理的设计修复。5 阶段清理 checklist 覆盖面大幅提升。

本轮迭代发现 **8 个新风险点**（1 个条件性 P0 + 2 个 High + 3 个 Medium + 1 个 Low + 1 个条件性 P0），主要集中在：

1. **A-2 方案与增量编译的时序冲突**（N-02）— 如果采用 A-2（在 PerformCHIRCompilation 末尾释放），`chirInfo.ccTys` 会在 `IncrementalCI::PerformCHIRCompilation()` 读取前被清空。建议保持 `RELEASE_AST` 作为独立阶段。
2. **A-3 方案的安全性未充分验证**（N-05、N-06）— 函数体粒度释放的思路有价值，但需要 ASan 全量验证。
3. **v2 方案自身的小缺陷**（N-03 析构顺序反转、N-04 遗漏清理）— 修复成本低。

v2 方案的核心设计（5 阶段清理 + CodeGen 双路径 + 增量编译适配）是可行的，可以进入编码阶段。上述新发现的问题均可在编码过程中修复。
