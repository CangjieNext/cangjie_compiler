## 三、新发现的设计缺陷

### F-01 [High] WriteCachedInfo 在 AST 释放后执行，varAndFuncDep 和 semaInfo.usages 中的 AST 指针已悬空

**类别**：设计缺陷

**问题描述**：

最终方案 §4.5 `MaterializeCachedASTReferences()` 将 `cachedInfo.varAndFuncDep` 从 `Ptr<const AST::Decl>` 物化为 `RawMangledName` 字符串键。但方案存在两个关键遗漏：

1. **`WriteCachedInfo()` 的调用时机不在 Compile() 主循环内**。代码审计发现，`WriteCachedInfo()` 不是在 `SAVE_CJO` 阶段调用的，而是在 `FrontendTool.cpp:216` 中，**整个编译流水线完成后**才调用：

```cpp
// FrontendTool.cpp:214-217
if (ExecuteCompile(*instance)) {
    instance->UpdateAndWriteCachedInfoToDisk();  // 在 CODEGEN + SAVE_RESULTS 之后
}
```

这意味着 `WriteCachedInfo()` 在 `RELEASE_AST` 阶段之后执行。`WriteCachedInfo()` 内部调用 `WriteCache(pkg, std::move(cachedInfo), std::move(order), path)`（`CachedDataSerialization.cpp:199`），其中：
- 第一个参数 `pkg` 来自 `*srcPkgs[0]`（`CompilerInstance.cpp:478`），但 `srcPkgs` 在 Phase 4a 已被 clear
- `order` 是 `std::vector<const AST::Decl*>`，包含裸 AST 指针，Phase 4a 后全部悬空

2. **`semaInfo.usages` 的物化代码缺失**。最终方案 §4.5 仅写了 `// semaInfo.usages 同理物化...` 的注释，没有给出实际实现。`semaInfo.usages` 的键是 `Ptr<const AST::Decl>`，序列化时（`DependencySerialization.cpp:59`）会解引用读取 `decl->rawMangleName`：

```cpp
// DependencySerialization.cpp:59
for (auto& [decl, usage] : std::as_const(unorderedUsageMap)) {
    orderedUsages.emplace(decl->rawMangleName, &usage);  // 解引用 AST 指针
}
```

3. **`varAndFuncDep` 在 CHIR 阶段被 GlobalDeclAnalysis 重写**。`GlobalDeclAnalysis.cpp:490` 在 CHIR 阶段将新的依赖关系写回 `cachedInfo.varAndFuncDep`：

```cpp
// GlobalDeclAnalysis.cpp:490
cachedInfo.varAndFuncDep = funcsAndVarsDepMap.stableOrderValue;
```

这意味着即使在 Phase 0 物化了 `varAndFuncDep`，CHIR 阶段会用新的 AST 指针覆盖物化结果。物化必须在 CHIR 阶段完成之后、AST 释放之前执行。

**触发输入**：

```cangjie
// 增量编译场景，启用缓存
package app
var x: Int64 = computeValue()
func computeValue(): Int64 { return 42 }
func main() { println(x.toString()) }
```

编译命令：`cjc --incremental app.cj`

**影响范围**：增量编译缓存写入崩溃（use-after-free），影响所有启用增量编译的场景。

**严重程度**：High — 增量编译是核心功能路径，WriteCachedInfo 必定在 AST 释放后执行。

**修复方向**：
1. `MaterializeCachedASTReferences()` 必须同时物化 `semaInfo.usages`（将 `Ptr<const AST::Decl>` 键转为 `RawMangledName` 字符串键）
2. `order` 向量（`std::vector<const AST::Decl*>`）必须物化为 `std::vector<RawMangledName>`
3. `WriteCachedInfo()` 必须适配物化后的数据结构，不再访问 `srcPkgs[0]`（改用 `codeGenPkgInfos[0].fullPackageName`）
4. 物化时机必须在 CHIR 阶段完成之后（GlobalDeclAnalysis 重写 varAndFuncDep 之后）

### F-02 [High] PerformResultsSaving 在 RELEASE_AST 之后执行，ExportASTSignature 需要完整 AST

**类别**：设计缺陷

**问题描述**：

最终方案 §4.6 `IncrementalCompilerInstance::PerformASTRelease()` 中设计了 `ExportASTSignaturesForIncremental()` 在释放前保存 AST 签名。但存在以下问题：

1. **当前代码中不存在 `resultsSaved` 标志**。代码审计确认 `IncrementalCompilerInstance` 中没有 `resultsSaved` 成员变量。最终方案 §4.6 的代码引用了 `resultsSaved` 但未在任何地方定义它：

```cpp
// 最终方案 §4.6 代码
if (!resultsSaved) {
    ExportASTSignaturesForIncremental();  // resultsSaved 未定义
}
```

2. **`PerformResultsSaving()` 不仅仅做 AST 签名导出**。`IncrementalCompilerInstance::PerformResultsSaving()`（`IncrementalCompilerInstance.cpp:519-538`）还执行：
   - `SaveCjo(*srcPkg)`（当 outputMode == CHIR 时）— 需要完整 AST
   - `srcPkg->fullPackageName` 和 `srcPkg->IsEmpty()` — 需要 srcPkgs 存活

3. **双重导出风险**。如果 `PerformASTRelease()` 中调用了 `ExportASTSignaturesForIncremental()`，而 `PerformResultsSaving()` 又调用 `ExportASTSignature()`，会导致同一份 AST 签名被序列化两次，写入同一个文件路径，浪费 I/O。

4. **CHIR 输出模式下的 SaveCjo 依赖**。当 `outputMode == CHIR` 时，`PerformCjoSaving()` 跳过（`DefaultCompilerInstance.cpp:323`），CJO 保存被推迟到 `PerformResultsSaving()` 中的 `SaveCjo(*srcPkg)` 调用。但 `RELEASE_AST` 在 `CODEGEN` 之前，`SAVE_RESULTS` 在 `CODEGEN` 之后，此时 `srcPkgs` 已被清空，`SaveCjo` 无法执行。

**触发输入**：

```cangjie
// CHIR 输出模式 + 增量编译
package app
main() { println("hello") }
```

编译命令：`cjc --output-mode=chir --incremental app.cj`

**影响范围**：CHIR 输出模式下增量编译的 CJO 保存和 AST 签名导出失败。

**严重程度**：High — CHIR 输出模式是有效的编译配置，增量编译下会静默丢失缓存数据或崩溃。

**修复方向**：
1. 必须定义 `resultsSaved` 标志并在 `PerformASTRelease()` 中正确设置
2. `PerformResultsSaving()` 需要适配 AST 已释放的场景：检查 `astReleased` 标志，跳过已完成的操作
3. CHIR 输出模式下的 `SaveCjo` 必须在 `RELEASE_AST` 之前完成（移到 `PerformASTRelease()` 的 Phase 0 中）
4. `ExportASTSignaturesForIncremental()` 的结果应缓存，`PerformResultsSaving()` 直接使用缓存结果

### F-03 [High] g_annoInfo 中的 AST 指针在 BuildCheckMap 中被解引用，但 ClearGlobalAnnotationInfo 时机设计有误

**类别**：设计缺陷

**问题描述**：

最终方案 §4.3 Phase 1c 调用 `CHIR::ClearGlobalAnnotationInfo()` 清除全局 annotation 信息。但代码审计发现 `g_annoInfo` 的生命周期比设计预期更复杂：

1. **`g_annoInfo` 持有 AST 指针**。`AnnotationInfo` 结构体（`AnnotationChecker.cpp:16-22`）包含：
   - `const ClassDecl* decl` — AST 指针
   - `AST::Annotation* anno` — AST 指针（非 const，用于回写）
   - `std::vector<GlobalVar*> vars` — CHIR 指针（安全）
   - `std::vector<Func*> funcs` — CHIR 指针（安全）

2. **`BuildCheckMap()`（`AnnotationChecker.cpp:393-397`）解引用 `anno` 指针**：

```cpp
void BuildCheckMap()
{
    for (auto it = g_annoInfo.begin(); it != g_annoInfo.end();) {
        cmap.emplace(it->first, AnnotationTarget{it->second.anno->target});  // 解引用 AST::Annotation*
        ++it;
    }
}
```

3. **但 `BuildCheckMap` 和 `InsertAnnotationVarInitInto` 都在 CHIR 阶段内部执行**（`ToCHIR::Run()` 的 step 1 和 step 10），在 `RELEASE_AST` 之前。代码审计确认：
   - `InsertAnnotationVarInitInto`（`GlobalVarInitializer.cpp:840`）只读取 CHIR 指针（`info.second.funcs`），不读取 AST 指针
   - `g_typeAnnoInfo` 和 `g_valueAnnoInfo` 在 annotation checking 结束时已被 clear（`AnnotationChecker.cpp:471-472`）

4. **真正的风险**：`g_annoInfo` 在 annotation checking 中被**选择性 erase**（`AnnotationChecker.cpp:431`），但**不是全部清空**。如果某些 annotation 未被处理（例如编译错误导致提前退出），`g_annoInfo` 中残留的条目持有悬空 AST 指针。最终方案的 `ClearGlobalAnnotationInfo()` 只清除 `g_annoInfo`，但**未清除 `g_typeAnnoInfo` 和 `g_valueAnnoInfo`**（虽然正常流程中它们已被清空，但异常退出时可能残留）。

**触发输入**：

```cangjie
// annotation 检查失败导致提前退出
package app
@MyAnnotation(target: [])  // 空 target 数组，可能触发检查失败
class MyAnnotation <: Annotation { ... }
func main() {}
```

**影响范围**：编译错误场景下 `g_annoInfo` 残留悬空指针，后续编译（同进程多次编译，如 LSP）可能触发 use-after-free。

**严重程度**：Medium（降级理由：正常编译流程中 annotation checking 在 CHIR 阶段内完成，`ClearGlobalAnnotationInfo` 在 Phase 1c 清除残留；风险仅存在于异常退出 + 同进程复用场景）。

**修复方向**：
1. `ClearGlobalAnnotationInfo()` 应同时清除 `g_annoInfo`、`g_typeAnnoInfo`、`g_valueAnnoInfo` 三个全局变量
2. 在 `ToCHIR::Run()` 的异常退出路径中也调用 `ClearGlobalAnnotationInfo()`

### F-06 [Medium] PerformASTRelease 中 PrepareCodeGenInfo 和 MaterializePackageDependence 的重复执行

**类别**：设计缺陷

**问题描述**：

最终方案 §4.9 中 `PerformASTRelease()` 的实现：

```cpp
bool CompilerInstance::PerformASTRelease()
{
    PrepareCodeGenInfo();
    MaterializePackageDependence();
    if (invocation.globalOptions.noReleaseAST) {
        return true;
    }
    ReleaseASTMemory();  // 内部会跳过已完成的 PrepareCodeGenInfo 和 MaterializePackageDependence
    return true;
}
```

但 `ReleaseASTMemory()` 的 Phase 0（§4.3 lines 447-453）也调用了 `PrepareCodeGenInfo()` 和 `MaterializePackageDependence()`：

```cpp
// Phase 0a
PrepareCodeGenInfo();
// Phase 0b
MaterializePackageDependence();
```

设计注释说"内部会跳过已完成的"，但代码中没有任何守卫机制。`PrepareCodeGenInfo()` 会重复填充 `codeGenPkgInfos`（先 clear 再重新遍历 srcPkgs），`MaterializePackageDependence()` 会重复调用 `packageManager->ResolveDependence()`。

虽然重复执行不会导致崩溃（`PrepareCodeGenInfo` 先 clear 再填充，`MaterializePackageDependence` 的 `packageDependenceResolved` 守卫在 `MaterializePackageDependenceIfNeeded` 中但不在 `MaterializePackageDependence` 本身），但这是设计不一致。

**影响范围**：性能浪费（双重遍历），设计文档与代码不一致。

**严重程度**：Medium — 不会导致功能错误，但 `MaterializePackageDependence()` 内部的 `ResolveDependence` 可能有副作用（重复插入依赖关系）。

**修复方向**：
1. 从 `PerformASTRelease()` 中移除 `PrepareCodeGenInfo()` 和 `MaterializePackageDependence()` 的直接调用，统一由 `ReleaseASTMemory()` Phase 0 执行
2. 或者在 `ReleaseASTMemory()` 中添加守卫（检查 `codeGenPkgInfos.empty()` 和 `packageDependenceResolved`）
3. `--no-release-ast` 模式下仍需执行 Phase 0 的提取操作，可以将 Phase 0 提取为独立方法

### F-07 [Medium] const_cast 在 ReleaseFuncBody 中语义冗余但掩盖了 const 安全性问题

**类别**：实现建议

**问题描述**：

最终方案 §3.4 `ReleaseFuncBody` 使用 `const_cast`：

```cpp
void AST2CHIR::ReleaseFuncBody(const AST::Decl& decl)
{
    if (auto* funcDecl = DynamicCast<const AST::FuncDecl*>(&decl)) {
        if (funcDecl->funcBody && funcDecl->funcBody->body) {
            const_cast<AST::FuncBody*>(funcDecl->funcBody.get())->body.reset();
        }
    }
}
```

代码审计发现 `OwnedPtr<T>::get()` 返回 `Ptr<T>`（非 const），`Ptr<T>` 内部存储的是 `T*`（非 const 裸指针）。因此 `funcDecl->funcBody.get()` 已经返回非 const 的 `FuncBody*`，`const_cast` 是冗余的。

但更深层的问题是：`decl` 参数是 `const AST::Decl&`，通过 `DynamicCast` 得到 `const AST::FuncDecl*`，然后通过 `funcDecl->funcBody`（`OwnedPtr<FuncBody>` 是 `FuncDecl` 的非 const 成员）访问 `funcBody`。在 C++ 中，通过 const 指针访问非 const 成员是合法的（`OwnedPtr` 的 `get()` 不是 const 方法但通过 const 对象调用会编译失败）。

实际上，`globalAndMemberFuncs` 存储的是 `const AST::Decl*`（`AST2CHIR.h` 中的成员类型），所以 `ReleaseFuncBody` 接收 const 引用是正确的。但 `OwnedPtr::get()` 是非 const 方法，通过 const 对象调用会编译失败。这意味着**设计中的代码实际上无法编译**。

验证：`FuncDecl::funcBody` 类型是 `OwnedPtr<FuncBody>`（`Node.h:1268`），通过 `const FuncDecl*` 访问 `funcBody` 得到 `const OwnedPtr<FuncBody>&`，调用 `get()` 需要 `get()` 是 const 方法。查看 `OwnedPtr::get()`（`SafePointer.h:96`）：

```cpp
Ptr<T> get() const {  // 是 const 方法
    return Ptr<T>(*this);
}
```

`get()` 确实是 const 方法，返回 `Ptr<T>`。但 `body` 是 `OwnedPtr<Block>` 成员，通过 `Ptr<FuncBody>` 访问 `body` 得到的是 `OwnedPtr<Block>&`（非 const），调用 `reset()` 是合法的。所以代码可以编译，`const_cast` 确实冗余。

**影响范围**：代码可读性和维护性。

**严重程度**：Low — 功能正确，但冗余的 const_cast 会误导代码审查者。

**修复方向**：移除 `const_cast`，直接写 `funcDecl->funcBody->body.reset()`。

### F-08 [Medium] ReleaseTranslatedNominalBodies 遗漏 EnumDecl 和 InterfaceDecl 的方法体

**类别**：设计未到位

**问题描述**：

最终方案 §3.4 `ReleaseTranslatedNominalBodies` 的实现只处理了 `ClassLikeDecl` 和 `StructDecl`：

```cpp
auto releaseMethodBodies = [this](const auto& declList) {
    for (auto& decl : declList) {
        if (!NeedTranslate(*decl)) { continue; }
        if (auto* classLike = DynamicCast<const AST::ClassLikeDecl*>(decl.get())) {
            for (auto& member : classLike->members) {
                ReleaseFuncBody(*member);
            }
        }
        if (auto* structDecl = DynamicCast<const AST::StructDecl*>(decl.get())) {
            for (auto& member : structDecl->members) {
                ReleaseFuncBody(*member);
            }
        }
    }
};
```

代码审计发现 `nominalDecls` 中还包含：
- `EnumDecl` — 枚举类型，可以有方法（`members` 字段）
- `InterfaceDecl` — 接口类型，可以有默认方法实现

查看 AST 节点继承关系：
- `ClassDecl` 继承 `ClassLikeDecl`（有 `members`）
- `StructDecl` 不继承 `ClassLikeDecl`（独立的 `members`）
- `EnumDecl` 不继承 `ClassLikeDecl`（独立的 `members`）
- `InterfaceDecl` 继承 `ClassLikeDecl`（有 `members`）

`InterfaceDecl` 继承 `ClassLikeDecl`，所以被第一个 `DynamicCast<ClassLikeDecl*>` 覆盖。但 `EnumDecl` 不继承 `ClassLikeDecl` 也不是 `StructDecl`，其方法体不会被释放。

**触发输入**：

```cangjie
package app
enum Color {
    RED | GREEN | BLUE
    func describe(): String {
        // 这个方法体在翻译后不会被释放
        match (this) {
            case RED => "red"
            case GREEN => "green"
            case BLUE => "blue"
        }
    }
}
func main() { println(Color.RED.describe()) }
```

**影响范围**：EnumDecl 的方法体内存未被 A-3 释放，降低内存收益。

**严重程度**：Medium — 不会导致崩溃（只是遗漏释放），但对于方法较多的枚举类型会显著降低 A-3 的内存收益。

**修复方向**：在 `releaseMethodBodies` lambda 中增加 `EnumDecl` 的处理分支：

```cpp
if (auto* enumDecl = DynamicCast<const AST::EnumDecl*>(decl.get())) {
    for (auto& member : enumDecl->members) {
        ReleaseFuncBody(*member);
    }
}
```

### F-09 [Low] CachedMangleMap 浅拷贝将悬空的 importedInlineDeclsPtr 传播到 CodeGen

**类别**：可优化项

**问题描述**：

最终方案 §4.4 `CachedMangleMap::ClearASTPointers()` 在 Phase 3h 清除 `importedInlineDeclsPtr`。但 `GenPackageModules()`（`EmitPackageIR.cpp:592`）在 CodeGen 阶段**拷贝** `cacheMangles`：

```cpp
cachedMangleMap = StaticCast<Cangjie::IncrementalCompilerInstance&>(compilerInstance).cacheMangles;
```

`CachedMangleMap` 没有自定义拷贝构造函数，使用编译器生成的默认浅拷贝。拷贝后 `cachedMangleMap.importedInlineDeclsPtr` 包含与原始相同的裸指针集合。

代码审计确认：
- `UpdateImportedInlineDeclsMangle()` 只在 `PerformMangling()` 阶段调用（`IncrementalCompilerInstance.cpp:370`），CHIR 之前
- CodeGen 中只使用 `importedInlineDecls`（字符串集合），不使用 `importedInlineDeclsPtr`
- `IncrementalGen.cpp:214` 遍历 `cachedMangles.importedInlineDecls`（字符串），安全

当前不会触发 use-after-free，但拷贝中携带悬空指针是防御性编程的隐患。

**触发输入**：无法在当前代码中触发，属于防御性风险。

**影响范围**：未来维护风险 — 如果有人在 CodeGen 路径中调用 `UpdateImportedInlineDeclsMangle()` 会触发 use-after-free。

**严重程度**：Low — 当前安全，但违反"释放后不传播悬空指针"原则。

**修复方向**：
1. `ClearASTPointers()` 应在 Phase 3h 执行（已设计），确保在 CodeGen 拷贝之前完成
2. 但 Phase 3h 在 `ReleaseASTMemory()` 内部，而 CodeGen 在 `RELEASE_AST` 之后的 `CODEGEN` 阶段。时序上 Phase 3h 先于 CodeGen 拷贝，所以拷贝时 `importedInlineDeclsPtr` 已被 clear。**实际上此风险已被正确处理**。
3. 额外建议：为 `CachedMangleMap` 添加自定义拷贝构造函数，拷贝时不复制 `importedInlineDeclsPtr`

### F-10 [Low] TranslateNominalDecls 内部访问 funcBody->paramLists，A-3 释放 body 不影响但需明确文档

**类别**：可优化项

**问题描述**：

代码审计发现 `TranslateNominalDecls`（`ASTPackage2CHIR.cpp:1286-1339`）内部构建 `genericFuncMap` 时访问 `funcBody->paramLists`：

```cpp
// ASTPackage2CHIR.cpp:1308-1312
CJC_ASSERT(funcDecl->funcBody && !funcDecl->funcBody->paramLists.empty());
CJC_ASSERT(genericFunc->funcBody && !genericFunc->funcBody->paramLists.empty());
auto& funcParams = funcDecl->funcBody->paramLists[0]->params;
auto& genericParams = genericFunc->funcBody->paramLists[0]->params;
```

A-3 方案释放的是 `funcBody->body`（`OwnedPtr<Block>`），不是 `funcBody` 本身，也不是 `funcBody->paramLists`。所以 `ReleaseTranslatedNominalBodies` 在 `TranslateNominalDecls` 返回后执行是安全的。

但最终方案的安全性验证表（§3.2）中没有明确列出 `TranslateNominalDecls` 对 `funcBody->paramLists` 的访问。如果未来有人将释放粒度从 `body` 扩大到整个 `funcBody`（`funcBody.reset()`），会导致 `TranslateNominalDecls` 中的 `paramLists` 访问崩溃。

**影响范围**：文档完整性，防止未来误扩大释放范围。

**严重程度**：Low — 当前设计安全，仅需补充文档。

**修复方向**：在 §3.2 安全性验证表中增加 `TranslateNominalDecls` 对 `funcBody->paramLists` 的访问说明，并在代码注释中标注"只释放 body，不释放 funcBody 本身"。

### 6.2 分析

本轮缺陷数量回升（5→10）的原因是：前三轮聚焦于 AST 释放本身的正确性（指针清理、时序安全），而本轮深入审计了**释放后的下游消费者**（WriteCachedInfo、PerformResultsSaving），发现最终方案对"AST 释放后谁还需要 AST 数据"的分析不够完整。

核心问题集中在一个主题：**增量编译的缓存写入路径**。`WriteCachedInfo()` 和 `PerformResultsSaving()` 都在 `RELEASE_AST` 之后执行，但它们依赖的数据（`varAndFuncDep`、`semaInfo.usages`、`order`、`srcPkgs`）在释放后不可用。

F-01、F-02、F-04、F-05 本质上是同一个根因的不同表现：**最终方案的 Phase 0 "前置操作"清单不完整**，遗漏了 WriteCachedInfo 和 PerformResultsSaving 的数据依赖。

### 6.3 修复建议（按优先级）

**P0（必须在编码前补全设计）**：

1. **扩展 Phase 0 前置操作清单**：
   - 0d. 物化 `semaInfo.usages`（键从 `Ptr<const AST::Decl>` → `RawMangledName`）
   - 0e. 物化 `order`（从 `std::vector<const AST::Decl*>` → `std::vector<RawMangledName>`）
   - 0f. 执行 `WriteCachedInfo()`（在 AST 释放前完成缓存写入）
   - 或者：将 `WriteCachedInfo()` 的调用从 `FrontendTool.cpp:216` 移到 `PerformASTRelease()` 的 Phase 0 中

2. **处理 PerformResultsSaving 的 AST 依赖**：
   - 在 `PerformASTRelease()` 中预先完成 `ExportASTSignaturesForIncremental()` 并缓存结果
   - 定义 `resultsSaved` 标志
   - CHIR 输出模式下的 `SaveCjo` 必须在 `RELEASE_AST` 前完成

**P1（编码中修复）**：

3. `ClearGlobalAnnotationInfo()` 清除全部三个全局变量
4. `ReleaseTranslatedNominalBodies` 增加 `EnumDecl` 分支
5. 消除 `PerformASTRelease` 与 `ReleaseASTMemory` 的重复调用

**P2（编码中优化）**：

6. 移除 `ReleaseFuncBody` 中冗余的 `const_cast`
7. 补充 §3.2 安全性验证表中 `TranslateNominalDecls` 对 `paramLists` 的访问记录
8. 为 `CachedMangleMap` 添加自定义拷贝构造函数（不复制 `importedInlineDeclsPtr`）
