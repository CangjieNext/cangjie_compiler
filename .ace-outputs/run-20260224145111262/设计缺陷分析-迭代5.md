## 三、新发现的设计缺陷

### G-01 [High] DefaultCompilerInstance 的 PerformResultsSaving 在 CHIR 输出模式下访问 AST，但 Phase 0e 的 resultsSaved 守卫不覆盖 Default 路径

**类别**：设计缺陷

**问题描述**：

代码审计发现 `DefaultCIImpl::PerformResultsSaving()`（`DefaultCompilerInstance.cpp:329-336`）在 `outputMode == CHIR` 时调用 `SaveCjo(ci.GetSourcePackages())`，该调用链解引用 AST：

```cpp
// DefaultCompilerInstance.cpp:329-336
bool DefaultCIImpl::PerformResultsSaving()
{
    if (ci.invocation.globalOptions.outputMode != GlobalOptions::OutputMode::CHIR) {
        return true;  // 非 CHIR 模式直接返回，不访问 AST
    }
    Utils::ProfileRecorder recorder("Main Stage", "Save results");
    return SaveCjo(ci.GetSourcePackages());  // 解引用 srcPkgs → ExportAST(pkg)
}
```

编译流水线中 `SAVE_RESULTS` 阶段在 `RELEASE_AST` 之后执行。对于 `DefaultCompilerInstance`：

1. `DefaultCompilerInstance` **没有 override `PerformASTRelease()`**，使用基类 `CompilerInstance::PerformASTRelease()`
2. 基类 `PerformASTRelease()` 调用 `ReleaseASTMemory()`，其 Phase 0e 执行 `PerformResultsSaving()`
3. 但 Phase 0e 的代码是 `if (!resultsSaved) { PerformResultsSaving(); resultsSaved = true; }`
4. 对于 `DefaultCompilerInstance`，`PerformResultsSaving()` 通过虚方法分派到 `DefaultCIImpl::PerformResultsSaving()`
5. 在 CHIR 输出模式下，这会调用 `SaveCjo(ci.GetSourcePackages())`，此时 AST 尚未释放（Phase 0e 在 Phase 4a 之前），**所以 Phase 0e 的前移是安全的**

但问题在于：Phase 0e 设置 `resultsSaved = true` 后，`SAVE_RESULTS` 阶段的 `PerformResultsSaving()` 会被跳过。这意味着 `DefaultCompilerInstance` 在 CHIR 输出模式下的 CJO 保存时机从 `SAVE_RESULTS` 阶段提前到了 `RELEASE_AST` 阶段。

**时序变化的影响**：`PerformCjoSaving()`（`SAVE_CJO` 阶段）在 CHIR 输出模式下跳过（`DefaultCompilerInstance.cpp:323`），CJO 保存被推迟到 `PerformResultsSaving()`。现在 `PerformResultsSaving()` 在 `RELEASE_AST` 阶段的 Phase 0e 中执行，即在 `CODEGEN` 之前。但 CHIR 输出模式下可能不需要 CodeGen（`--output-mode=chir` 意味着只输出 CHIR，不生成目标代码）。所以提前保存 CJO 在语义上是正确的。

**真正的风险**：`DefaultCompilerInstance` 没有 override `PerformASTRelease()`，所以基类的 Phase 0e 会调用 `this->PerformResultsSaving()`（虚方法分派到 DefaultCIImpl）。但 `DefaultCIImpl::PerformResultsSaving()` 调用 `ci.GetSourcePackages()`，而 `GetSourcePackages()` 在 `astReleased == true` 时返回空向量（§4.8）。Phase 0e 在 `astReleased` 设置之前执行，所以 `GetSourcePackages()` 返回正常结果。**时序安全**。

但如果 `DefaultCompilerInstance` 在非 CHIR 输出模式下运行，`PerformResultsSaving()` 直接返回 true（不访问 AST），Phase 0e 设置 `resultsSaved = true`，`SAVE_RESULTS` 阶段跳过。这意味着**非 CHIR 模式下 `SAVE_RESULTS` 阶段变成空操作**。需要确认这是否正确——非 CHIR 模式下 `SAVE_RESULTS` 阶段是否有其他工作？

代码审计确认：`DefaultCIImpl::PerformResultsSaving()` 在非 CHIR 模式下直接返回 true，不做任何工作。所以跳过是安全的。

**降级理由**：经过完整时序分析，Phase 0e 的前移对 DefaultCompilerInstance 是安全的。但设计文档中没有明确说明 DefaultCompilerInstance 的 Phase 0e 行为，也没有说明 `PerformResultsSaving()` 的虚方法分派在 Phase 0e 中的语义。

**触发输入**：

```cangjie
// CHIR 输出模式 + 非增量编译
package app
main() { println("hello") }
```

编译命令：`cjc --output-mode=chir app.cj`

**影响范围**：DefaultCompilerInstance 在 CHIR 输出模式下的 CJO 保存时机提前，但功能正确。

**严重程度**：Medium（降级：经分析时序安全，但设计文档缺少对 Default 路径的显式说明）。

**修复方向**：
1. 在 §4.6 或 §4.9 中补充 DefaultCompilerInstance 的 Phase 0e 行为说明
2. 或者为 DefaultCompilerInstance 也添加 `PerformASTRelease()` override，明确其行为

### G-02 [Medium] MaterializeCachedASTReferences 中 order 物化的 MacroDecl 处理可能遗漏

**类别**：设计未到位

**问题描述**：

最终方案 §4.5 `MaterializeCachedASTReferences()` 步骤 3 物化 `order` 时，对 `MainDecl` 做了特殊处理：

```cpp
// 3. 物化 order（F-05）
for (auto* decl : order) {
    CJC_ASSERT(decl != nullptr);
    std::string name;
    if (Is<MainDecl>(decl)) {
        name = StaticCast<MainDecl>(*decl).desugarDecl->rawMangleName;
    } else {
        name = decl->rawMangleName;
    }
    matOrder.push_back(std::move(name));
}
```

代码审计确认 `WriteCachedAST`（`CachedDataSerialization.cpp:84-99`）中也有完全相同的 MainDecl 特殊处理：

```cpp
auto& mangled{(Is<MainDecl>(decl) ?
    *StaticCast<MainDecl>(*decl).desugarDecl : *decl).rawMangleName};
```

`MacroDecl` 也有 `desugarDecl` 字段（`Node.h:1308`），但 `WriteCachedAST` 中**没有**对 MacroDecl 做特殊处理，直接使用 `decl->rawMangleName`。物化代码与 `WriteCachedAST` 保持一致，所以**物化是正确的**。

但需要验证：`MacroDecl` 的 `rawMangleName` 是否在 Mangling 阶段被正确填充？如果 MacroDecl 的 `rawMangleName` 为空（像 MainDecl 一样被 move 到 desugarDecl），物化会产生空键。

代码审计发现 `WriteCachedAST` 使用 `ast.at(mangled)` 查找缓存条目。如果 MacroDecl 的 `rawMangleName` 为空，`ast.at("")` 会抛出 `std::out_of_range` 异常。但当前代码在没有 AST 释放的情况下正常工作，说明 MacroDecl 的 `rawMangleName` 不为空。

**结论**：物化代码与现有序列化代码一致，MacroDecl 不需要特殊处理。但设计文档应明确说明这一点。

**影响范围**：文档完整性。

**严重程度**：Low（降级：代码正确，仅需补充说明）。

### G-03 [Medium] WriteCachedInfoBeforeRelease 使用 std::move(cachedInfo) 后 Phase 0c 的物化数据被清空

**类别**：设计缺陷

**问题描述**：

最终方案 §4.5 `WriteCachedInfoBeforeRelease()` 的实现：

```cpp
void CompilerInstance::WriteCachedInfoBeforeRelease()
{
    // 物化 varAndFuncDep：Ptr<const AST::Decl> → rawMangleName 字符串
    MaterializeCachedASTReferences();

#ifdef CANGJIE_CODEGEN_CJNATIVE_BACKEND
    auto& pkg{*srcPkgs[0]};
    std::string path{invocation.globalOptions.GenerateCachedPathName(
        pkg.fullPackageName, CACHED_AST_EXTENSION)};
    WriteCache(pkg, std::move(cachedInfo), std::move(order), path);
#endif
}
```

注意 `WriteCache` 的签名是 `WriteCache(const Package& pkg, CompilationCache&& cachedInfo, std::vector<const AST::Decl*>&& order, const std::string& path)`。`std::move(cachedInfo)` 和 `std::move(order)` 将数据移走。

但 `WriteCachedInfoBeforeRelease()` 在 Phase 0d 中被调用，而 Phase 0c 的 `MaterializeCachedASTReferences()` 已经在步骤 4 中执行了：

```cpp
// 4. 替换原始数据
cachedInfo.varAndFuncDep.clear();
cachedInfo.materializedVarFuncDep = std::move(matDep);
cachedInfo.semaInfo.usages.clear();
cachedInfo.semaInfo.materializedUsages = std::move(matUsages);
order.clear();
materializedOrder = std::move(matOrder);
```

时序分析：
1. Phase 0c `MaterializeCachedASTReferences()`：清空 `cachedInfo.varAndFuncDep`、`cachedInfo.semaInfo.usages`、`order`，填充物化版本
2. Phase 0d `WriteCachedInfoBeforeRelease()`：调用 `MaterializeCachedASTReferences()`（**第二次调用**，但此时原始数据已被清空，物化操作在空数据上执行，产生空的物化结果）
3. 然后 `WriteCache(pkg, std::move(cachedInfo), std::move(order), path)`

**问题 1**：`WriteCachedInfoBeforeRelease()` 内部又调用了 `MaterializeCachedASTReferences()`，这是第二次调用。第一次在 Phase 0c，第二次在 Phase 0d 内部。第二次调用时 `cachedInfo.varAndFuncDep` 已被 clear，物化循环不执行，`matDep` 为空，然后 `cachedInfo.materializedVarFuncDep = std::move(matDep)` 覆盖了第一次物化的结果为空。

**问题 2**：`WriteCache` 接收 `std::move(order)`，但 `order` 在 Phase 0c 已被 clear。`WriteCache` 内部的 `WriteCachedAST` 遍历空的 `order`，不写入任何声明。

**问题 3**：设计注释说"WriteCachedInfoBeforeRelease() 直接使用原始的 cachedInfo、order、srcPkgs[0]（此时 AST 尚未释放），不需要使用物化后的数据"。但 Phase 0c 已经 clear 了原始数据。

**根因**：Phase 0c 和 Phase 0d 的执行顺序导致数据竞争。`MaterializeCachedASTReferences()` 在 Phase 0c 中清空了原始数据，Phase 0d 的 `WriteCachedInfoBeforeRelease()` 无法再使用原始数据。

**触发输入**：

```cangjie
// 任何增量编译场景
package app
var x: Int64 = 1
main() { println(x.toString()) }
```

编译命令：`cjc --incremental app.cj`

**影响范围**：增量编译缓存写入时 `varAndFuncDep`、`semaInfo.usages`、`order` 全部为空，导致下次增量编译无法正确判断依赖关系和声明顺序。

**严重程度**：High — 增量编译缓存数据丢失，导致后续增量编译行为不正确。

**修复方向**：
1. **方案 A（推荐）**：调换 Phase 0c 和 Phase 0d 的顺序。先执行 Phase 0d `WriteCachedInfoBeforeRelease()`（使用原始数据写入缓存），再执行 Phase 0c `MaterializeCachedASTReferences()`（物化后清空原始数据）。`WriteCachedInfoBeforeRelease()` 内部不再调用 `MaterializeCachedASTReferences()`。
2. **方案 B**：`MaterializeCachedASTReferences()` 不清空原始数据，只填充物化版本。Phase 4a `srcPkgs.clear()` 时原始数据中的 AST 指针自然悬空，但不会被访问（因为 `cacheWritten` 和 `resultsSaved` 标志已设置）。
3. **方案 C**：`WriteCachedInfoBeforeRelease()` 不调用 `MaterializeCachedASTReferences()`，Phase 0c 的物化在 `WriteCachedInfoBeforeRelease()` 之后执行（即当前 ReleaseASTMemory 中的顺序改为 0d → 0c）。

### G-04 [Medium] IncrementalCI::PerformASTRelease 中 WriteCachedInfoBeforeRelease 和 ReleaseASTMemory 的 Phase 0d 双重执行

**类别**：设计缺陷

**问题描述**：

`IncrementalCompilerInstance::PerformASTRelease()`（§4.6）的执行流程：

```
1. PrepareCodeGenInfo()
2. MaterializePackageDependence()
3. PerformResultsSaving()          → resultsSaved = true
4. WriteCachedInfoBeforeRelease()  → cacheWritten = true
5. changedTypes.clear()
6. cacheMangles.ClearASTPointers()
7. ReleaseASTMemory()              → Phase 0a-0e + Phase 1-4
```

`ReleaseASTMemory()` 内部的 Phase 0 执行：
- 0a: `PrepareCodeGenInfo()` — 被 `codeGenPkgInfos.empty()` 守卫跳过 ✅
- 0b: `MaterializePackageDependence()` — 被 `packageDependenceResolved` 守卫跳过 ✅
- 0c: `MaterializeCachedASTReferences()` — **无守卫，会执行**
- 0d: `WriteCachedInfoBeforeRelease()` — 被 `ShouldWriteCacheFile()` 条件控制，但 `cacheWritten` 标志在 `WriteCachedInfoBeforeRelease()` 内部没有检查（`if (ShouldWriteCacheFile())` 仍然为 true）

等等，重新审视代码：

```cpp
// Phase 0d
if (ShouldWriteCacheFile()) {
    WriteCachedInfoBeforeRelease();
    cacheWritten = true;
}
```

`IncrementalCI::PerformASTRelease()` 步骤 4 已经设置 `cacheWritten = true`。但 `ReleaseASTMemory()` Phase 0d 的条件是 `if (ShouldWriteCacheFile())`，**不检查 `cacheWritten`**。

所以 `WriteCachedInfoBeforeRelease()` 会被调用两次：
1. `IncrementalCI::PerformASTRelease()` 步骤 4
2. `ReleaseASTMemory()` Phase 0d

第二次调用时 `cachedInfo` 已被 `std::move` 移走（步骤 4 中），`WriteCache` 收到空的 `cachedInfo`。

**修复方向**：Phase 0d 的条件应改为 `if (ShouldWriteCacheFile() && !cacheWritten)`。

**影响范围**：增量编译路径下 `WriteCachedInfoBeforeRelease()` 双重执行，第二次写入空数据覆盖第一次的正确数据。

**严重程度**：Medium（降级理由：与 G-03 同源，修复 G-03 后此问题自然消失；且第二次 WriteCache 写入空数据到同一文件路径，覆盖了第一次的正确数据，但如果 Phase 0d 添加 `!cacheWritten` 守卫则可避免）。

### G-05 [Medium] PerformResultsSaving 在 ReleaseASTMemory Phase 0e 中被基类调用，但 IncrementalCI 已在 PerformASTRelease 中调用过

**类别**：设计缺陷

**问题描述**：

与 G-04 类似，`ReleaseASTMemory()` Phase 0e：

```cpp
// 0e. 增量编译结果保存前移
if (!resultsSaved) {
    PerformResultsSaving();
    resultsSaved = true;
}
```

Phase 0e **有** `!resultsSaved` 守卫。`IncrementalCI::PerformASTRelease()` 步骤 3 已设置 `resultsSaved = true`，所以 Phase 0e 会被跳过。✅

但对于 `DefaultCompilerInstance`（没有 override `PerformASTRelease()`），基类 `PerformASTRelease()` 直接调用 `ReleaseASTMemory()`，Phase 0e 会执行 `PerformResultsSaving()`。`DefaultCIImpl::PerformResultsSaving()` 在非 CHIR 模式下直接返回 true，在 CHIR 模式下调用 `SaveCjo(ci.GetSourcePackages())`。此时 AST 尚未释放（Phase 0e 在 Phase 4a 之前），所以是安全的。✅

**结论**：Phase 0e 的 `!resultsSaved` 守卫正确处理了 IncrementalCI 的双重调用。DefaultCI 的 Phase 0e 也是安全的。**此项无缺陷**。

### G-06 [Medium] MaterializeCachedASTReferences 缺少幂等性守卫

**类别**：设计未到位

**问题描述**：

`MaterializeCachedASTReferences()` 在以下位置被调用：
1. `ReleaseASTMemory()` Phase 0c
2. `WriteCachedInfoBeforeRelease()` 内部（§4.5 代码第一行）

如果 `IncrementalCI::PerformASTRelease()` 先调用 `WriteCachedInfoBeforeRelease()`（内部调用 `MaterializeCachedASTReferences()`），然后调用 `ReleaseASTMemory()`（Phase 0c 再次调用 `MaterializeCachedASTReferences()`），物化函数被执行两次。

第二次执行时：
- `cachedInfo.varAndFuncDep` 已被 clear → 物化循环不执行 → `matDep` 为空
- `cachedInfo.materializedVarFuncDep = std::move(matDep)` → **覆盖第一次物化的结果为空**
- 同理 `semaInfo.usages` 和 `order`

这与 G-03 是同一个根因的不同表现。

**修复方向**：为 `MaterializeCachedASTReferences()` 添加幂等性守卫：

```cpp
void CompilerInstance::MaterializeCachedASTReferences()
{
    if (cachedInfoMaterialized) { return; }  // 幂等性守卫
    cachedInfoMaterialized = true;
    // ... 物化逻辑 ...
}
```

**影响范围**：增量编译缓存物化数据被第二次空执行覆盖。

**严重程度**：Medium — 与 G-03 同源，但独立的修复点。

### G-07 [Low] --no-release-ast 模式下 IncrementalCI 的行为不一致

**类别**：可优化项

**问题描述**：

`IncrementalCompilerInstance::PerformASTRelease()`（§4.6）在 `--no-release-ast` 模式下：

```cpp
if (invocation.globalOptions.noReleaseAST) {
    return true;  // 直接返回，不执行 PerformResultsSaving 和 WriteCachedInfoBeforeRelease
}
```

这意味着 `--no-release-ast` 模式下：
- `resultsSaved` 保持 false → `SAVE_RESULTS` 阶段正常执行 `PerformResultsSaving()` ✅
- `cacheWritten` 保持 false → `FrontendTool.cpp` 正常执行 `UpdateAndWriteCachedInfoToDisk()` ✅

但 `PrepareCodeGenInfo()` 和 `MaterializePackageDependence()` 在 `noReleaseAST` 检查之前执行，这是正确的（CodeGen 单路径需要）。

§4.9 的文档说明："缓存写入和结果保存在原有位置执行（AST 存活，无需前移）"。这与代码一致。✅

**但**：基类 `CompilerInstance::PerformASTRelease()` 的 `noReleaseAST` 检查在 `PrepareCodeGenInfo()` 和 `MaterializePackageDependence()` 之后、`ReleaseASTMemory()` 之前。而 `IncrementalCI::PerformASTRelease()` 的 `noReleaseAST` 检查也在同样位置。两者行为一致。✅

**结论**：`--no-release-ast` 模式下行为正确。但 `IncrementalCI::PerformASTRelease()` 中 `changedTypes.clear()` 和 `cacheMangles.ClearASTPointers()` 在 `noReleaseAST` 检查之后执行，意味着 `--no-release-ast` 模式下这些清理不会执行。这是正确的（AST 存活，指针不悬空）。

**影响范围**：无功能影响。

**严重程度**：Low — 行为正确，仅建议在文档中明确说明。

### 6.2 分析

迭代 4 的 10 个缺陷全部得到修复。本轮发现的问题集中在 ADR-009 前移逻辑的**内部执行顺序**：Phase 0c（物化）和 Phase 0d（写入）的顺序导致物化操作清空了写入所需的原始数据。

G-03/G-04/G-06 本质上是同一个根因：`MaterializeCachedASTReferences()` 的"清空原始数据"操作与 `WriteCachedInfoBeforeRelease()` 的"使用原始数据写入"操作之间的时序冲突。

修复非常简单：
1. 调换 Phase 0c 和 Phase 0d 的顺序（先写入，后物化）
2. 为 `MaterializeCachedASTReferences()` 添加幂等性守卫
3. Phase 0d 添加 `!cacheWritten` 检查

这三个修改总计约 5 行代码，不涉及架构变更。

### 6.3 修复建议（按优先级）

**P0（必须在编码前修正）**：

1. **调换 Phase 0c/0d 顺序**：先执行 Phase 0d `WriteCachedInfoBeforeRelease()`（使用原始 AST 数据），再执行 Phase 0c `MaterializeCachedASTReferences()`（物化后清空原始数据）。`WriteCachedInfoBeforeRelease()` 内部不再调用 `MaterializeCachedASTReferences()`。

2. **添加幂等性守卫**：`MaterializeCachedASTReferences()` 开头检查 `if (cachedInfoMaterialized) { return; }`。
