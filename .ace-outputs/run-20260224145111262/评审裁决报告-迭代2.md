## 二、v1 P0 阻塞项修复验证

### D-01 CodeGen 入口重构 — ✅ 修复合理

v2 方案引入 `PackageCodeGenInfo` 结构体，在 AST 释放前提取 `fullPackageName` 和 `isEmpty`。`CodegenOnePackageV2` 通过此结构驱动 CodeGen，不再依赖 `AST::Package&`。

关键验证：`GenPackageModules()` 签名接收 `CHIRData&`，不依赖 AST。v2 方案正确识别了 `CodegenOnePackage` 对 AST 的实际依赖仅为 `fullPackageName` 和 `IsEmpty()`，提取成本极低。

`RearrangeImportedPackageDependence` 的物化方案（`MaterializePackageDependence`）同样合理——在释放前调用一次，CodeGen 阶段通过 `packageDependenceResolved` 标记跳过。

**裁决：P0 阻塞解除。**

### D-02/D-03 完整清理 Checklist + 管理器清理 — ✅ 修复合理

v2 方案的 5 阶段清理 checklist 覆盖面大幅提升：
- Phase 0：前置物化（CodeGenInfo、包依赖、Cache 引用、CJO 保存）
- Phase 1：CHIR 层反向引用清理（CHIRTypeCache、DiagAdapter、g_annoInfo）
- Phase 2：CompilerInstance 直接成员清理（7 个遗漏变量全部补充）
- Phase 3：管理器清理（TypeChecker/TypeManager delete、Mangler reset、ImportManager/PackageManager ClearASTReferences）
- Phase 4：AST 核心数据释放（srcPkgs → pkgCtxMap 严格顺序）

管理器清理策略合理：TypeManager 直接 delete（CodeGen 不依赖）、BaseMangler reset（Mangling 已完成）、ImportManager 提供 ClearASTReferences 方法。

**裁决：P0 阻塞解除。**

### D-05 增量编译适配 — ✅ 修复合理

`IncrementalCompilerInstance::PerformASTRelease()` override 设计合理：在释放前调用 `PerformResultsSaving()`（完成 ExportASTSignature 和 SaveCjo），清理增量编译特有的 AST 指针成员（`changedTypes`、`declsToBeReCompiled`），然后调用基类 `ReleaseASTMemory()`。

`resultsSaved` 幂等性标记防止重复保存。

**裁决：P0 阻塞解除。**

### 小结

**v1 的 4 个 P0 阻塞项全部得到合理修复。** v2 方案的核心设计可以进入编码阶段。

## 三、新发现缺陷逐条裁决

### N-01 [High] CodeGen 双路径维护负担 — 确认，降级为 Medium，P1

**裁决：确认风险，严重程度降级为 Medium，P1**

攻击方正确指出双路径（`CodegenOnePackage` / `CodegenOnePackageV2`）的维护成本。两个路径必须保持语义一致，未来修改容易遗漏同步。

降级理由：
1. 这是维护成本问题，不是正确性问题。当前设计两个路径都能正确工作。
2. 攻击方提出的统一方案（始终使用 `PackageCodeGenInfo` 驱动）是更优解，但不是阻塞项。
3. 可以在编码阶段直接采用统一路径方案，无需额外设计迭代。

**修复建议**：编码时直接采用统一路径——始终在 CHIR 完成后提取 `PackageCodeGenInfo`，CodeGen 统一使用 V2 路径。`--no-release-ast` 模式下同样提取 info 但不释放 AST。这样只有一个 CodeGen 路径，消除分歧风险。

---

### N-02 [High] chirInfo.ccTys 与 A-2 方案的时序冲突 — 确认，但条件性

**裁决：确认，严重程度 High，但仅在采用 A-2 方案时触发**

代码验证：`IncrementalCompilerInstance::PerformCHIRCompilation()`（IncrementalCompilerInstance.cpp:456-457）确实在基类调用返回后才读取 `chirInfo.ccTys`。如果基类方法内部调用了 `ReleaseASTMemory()` 清空 `ccTys`，增量编译的 closure struct layout 变化检测会失效。

**关键决策：v2 方案应保持 RELEASE_AST 作为独立流水线阶段，不采用 A-2（在 PerformCHIRCompilation 末尾释放）。** 这样 `ccTys` 在 CHIR 阶段结束时仍然存活，IncrementalCI 可以正常读取。`RELEASE_AST` 阶段在 CHIR 之后、CODEGEN 之前执行，此时 `ccTys` 已被 IncrementalCI 消费完毕。

**裁决：确认风险，但通过保持独立 RELEASE_AST 阶段完全规避。不构成阻塞。**

---

### N-03 [Medium] TypeChecker→TypeManager 析构顺序反转 — 确认，维持 Medium，P1

**裁决：确认，严重程度 Medium，P1**

代码验证：现有析构函数（CompilerInstance.cpp:92-94）的顺序是 typeChecker → typeManager。v2 设计文档 §1.3 也明确指出"必须先 delete typeChecker，再 delete typeManager"。但 Phase 3 的伪代码将顺序写反了（先 typeManager 后 typeChecker）。

这是文档中的笔误/代码错误，修复成本极低（交换两行代码），但如果不修正会导致 TypeChecker 析构时访问已释放的 TypeManager 引用。

**修复要求**：编码时确保 Phase 3 顺序为 typeChecker → typeManager，与现有析构函数一致。

---

### N-04 [Medium] cacheMangles.importedInlineDeclsPtr 遗漏清理 — 确认，维持 Medium，P1

**裁决：确认，严重程度 Medium，P1**

代码验证：`CachedMangleMap::importedInlineDeclsPtr`（CachedMangleMap.h:77）确实持有 `const AST::Decl*` 裸指针。v2 方案的 `IncrementalCompilerInstance::PerformASTRelease()` 中 `cacheMangles.clear()` 的注释写的是"如果包含 AST 指针"，说明设计者不确定是否需要清理。

实际分析：`importedInlineDeclsPtr` 在 Mangling 阶段填充，在 `UpdateImportedInlineDeclsMangle` 中解引用。CodeGen 阶段复制 `cacheMangles` 时会复制这些悬空指针，但当前不解引用。风险是防御性的——未来如果有人在 CodeGen 中调用 `UpdateImportedInlineDeclsMangle` 会触发 UAF。

**修复要求**：在 `IncrementalCompilerInstance::PerformASTRelease()` 中明确清理 `cacheMangles.importedInlineDeclsPtr`。由于是 private 成员，需要在 `CachedMangleMap` 中添加 `ClearASTPointers()` 方法。

---

### N-05 [High] A-3 方案 GlobalDeclAnalysis 可能依赖 funcBody — 驳回（条件性）

**裁决：驳回（针对 funcBody->body 的担忧）**

代码验证：`GlobalDeclAnalysis::CollectDepInCallExpr`（GlobalDeclAnalysis.cpp:46-48）访问的是 `funcBody->paramLists[0]->params[i]->desugarDecl`，即参数列表，不是 `funcBody->body`（代码块）。

A-3 方案只释放 `funcBody->body`（`OwnedPtr<Block>`），保留 `funcBody` 节点本身及其 `paramLists`。因此 GlobalDeclAnalysis 的访问不受影响。

更关键的是，GlobalDeclAnalysis 在 Step 2 执行，A-3 的释放在 Step 4 执行。时序上 Step 2 早于 Step 4，即使 GlobalDeclAnalysis 访问了 body 也不会有问题。

**裁决：驳回。A-3 方案在此场景下是安全的。**

---

### N-06 [Medium] A-3 并行翻译中 @inline 函数交叉引用 — 确认风险，降级为 Low

**裁决：确认理论风险，严重程度降级为 Low，P2**

代码验证：CHIR lowering（AST2CHIR）不执行函数内联。函数内联在独立的 CHIR 优化 pass（`FunctionInline.cpp`）中执行，该 pass 在 lowering 完成后运行，操作的是 CHIR IR 而非 AST。

因此，`TranslateTopLevelDeclsInParallel` 中翻译函数 A 时不会读取函数 B 的 AST body 来执行内联。每个函数的翻译只读取自己的 body，通过 `globalCache` 引用其他函数时只查找 CHIR 签名（`CHIR::Func*`），不读取 AST body。

攻击方的 `@inline` 交叉引用场景在 lowering 阶段不会发生。

**修复建议**：A-3 实施时添加 ASan 全量测试验证即可，无需特殊处理 `@inline` 函数。

---

### N-07 [Medium] Phase 0d 未覆盖非 CHIR 模式的增量编译 — 确认，维持 Medium，P1

**裁决：确认，严重程度 Medium，P1**

攻击方正确指出：`ReleaseASTMemory()` 的 Phase 0d 只在 CHIR 输出模式下调用 `PerformResultsSaving()`，但增量编译在所有模式下都需要 AST 来执行 `ExportASTSignature`。

v2 方案通过 `IncrementalCompilerInstance::PerformASTRelease()` override 解决了这个问题——在调用 `ReleaseASTMemory()` 之前先调用 `PerformResultsSaving()`。但如果有代码路径直接调用 `ReleaseASTMemory()` 绕过 `PerformASTRelease()`，增量编译的缓存会丢失。

**修复要求**：将 `ReleaseASTMemory()` 的访问级别设为 `protected`（或 `private`），确保外部只能通过 `PerformASTRelease()` 触发释放。这是低成本的防御性设计，消除误用风险。

---

### N-08 [Low] PackageManager::ClearASTReferences 缺少完整审计 — 确认，维持 Low，P2

**裁决：确认，严重程度 Low，P2**

v2 方案对 `PackageManager` 的审计确实不够完整。但 PackageManager 的主要职责是包依赖关系管理，其内部的 AST 引用主要是 `Ptr<AST::Package>` 类型的包指针。`MaterializePackageDependence()` 已在释放前完成依赖关系物化。

**修复建议**：编码阶段对 `PackageManager` 的成员变量做一次完整审计，确认 `packageDependence.clear()` 是否足够。如果 PackageManager 还有其他 AST 引用，补充清理。

## 四、A-3 方案评估

### 4.1 可行性判断：可行，推荐实施

A-3 方案（函数体粒度释放）经代码审计和验证，在以下条件下是安全的：

1. **只释放 `funcBody->body`（Block），保留 `funcBody` 节点及 `paramLists`** — GlobalDeclAnalysis 只访问 paramLists，不访问 body ✅
2. **释放在 Step 4 中执行，Step 1-3 不受影响** — 时序安全 ✅
3. **CHIR lowering 不执行函数内联** — 并行翻译中不存在交叉读取 body 的场景 ✅
4. **AST2CHIRCheck（Step 5）只检查签名级信息** — 不读取 body ✅

### 4.2 A-3 与 v2 的关系

A-3 和 v2 完全互补：
- A-3 在 CHIR lowering 的 Step 4 中逐步释放函数体（60-80% AST 内存）
- v2 在 CHIR 完成后释放剩余的声明骨架和管理器（额外 15-20%）
- 组合后总收益 95%+

### 4.3 实施建议

1. A-3 改动量小（~50 行），风险低，可回退性高，建议优先实施
2. 先在单线程模式下验证，再扩展到并行模式
3. 必须配合 ASan 全量测试
4. 建议只释放用户定义函数的 body，编译器生成的隐式函数 body 暂不释放（保守策略）

## 五、关键架构决策

### 决策 1：保持 RELEASE_AST 作为独立流水线阶段

**决策：采纳，不采用 A-2（PerformCHIRCompilation 末尾释放）**

理由：
- N-02 证明 A-2 与增量编译的 `chirInfo.ccTys` 读取存在时序冲突
- 独立阶段的语义更清晰，便于 `--no-release-ast` 开关控制
- 独立阶段便于 `IncrementalCompilerInstance` override

### 决策 2：CodeGen 统一为单一路径

**决策：采纳 N-01 的修复建议，不保留双路径**

理由：
- 始终提取 `PackageCodeGenInfo`，CodeGen 统一使用 V2 路径
- 消除双路径维护负担和语义分歧风险
- `--no-release-ast` 模式下同样提取 info，只是不释放 AST

### 决策 3：ReleaseASTMemory 设为 protected

**决策：采纳 N-07 的修复建议**

理由：
- 防止外部代码绕过 `PerformASTRelease()` 直接调用 `ReleaseASTMemory()`
- 确保增量编译的前置保存逻辑不被跳过
- 低成本高收益的防御性设计

### 决策 4：A-3 方案纳入实施计划

**决策：采纳，作为 Phase 1 优先实施项**

理由：
- 改动小、风险低、立即见效
- 与 v2 完全互补
- 可在 1-2 天内完成

## 八、最终裁决

### 裁决：有条件通过（Conditional Pass）— 可进入编码阶段

v2 方案已解决 v1 的全部 4 个 P0 阻塞项。本轮新发现的 8 个风险点中无新增 P0 阻塞项（2 个驳回、2 个降级、4 个 P1 可在编码中修复）。

**进入编码的前提条件**（均可在编码过程中满足，无需额外设计迭代）：
1. CodeGen 统一为单路径（消除 N-01 双路径风险）
2. Phase 3 析构顺序修正为 typeChecker → typeManager（修正 N-03）
3. cacheMangles 添加 ClearASTPointers 方法（修复 N-04）
4. ReleaseASTMemory 设为 protected（修复 N-07）

**推荐实施顺序**：
1. Phase 0：A-3 函数体粒度释放（1-2 天，立即见效）
2. Phase 1：v2 基础设施（RELEASE_AST 阶段、astReleased 标记、--no-release-ast 开关）
3. Phase 2：v2 核心实现（5 阶段清理 + CodeGen 单路径 + 增量编译适配）
4. Phase 3：测试验证（ASan 全量 + 增量编译专项 + 内存对比）

## 九、关键决策记录更新

- **理由**：防止绕过增量编译的前置保存逻辑
