## 三、新发现缺陷逐条裁决

### G-01 [High→Medium] DefaultCI 的 Phase 0e 虚方法分派 — 确认降级为 Low，P2

**裁决：确认风险，严重程度降级为 Low，P2**

攻击方自己在分析过程中已完成了完整的时序验证并得出结论：**Phase 0e 的前移对 DefaultCompilerInstance 是安全的**。具体推理链：

1. `DefaultCompilerInstance` 没有 override `PerformASTRelease()`，使用基类实现
2. 基类 `PerformASTRelease()` 调用 `ReleaseASTMemory()`，Phase 0e 通过虚方法分派调用 `DefaultCIImpl::PerformResultsSaving()`
3. CHIR 输出模式下：`SaveCjo(ci.GetSourcePackages())` 在 Phase 0e 执行，此时 AST 尚未释放（Phase 0e 在 Phase 4a 之前），时序安全
4. 非 CHIR 输出模式下：`PerformResultsSaving()` 直接返回 true，不访问 AST
5. `SAVE_RESULTS` 阶段被 `resultsSaved = true` 跳过，但 `DefaultCIImpl::PerformResultsSaving()` 在非 CHIR 模式下本身就是空操作

攻击方最终将此项从 High 降级为 Medium，评审方进一步降级为 Low。理由：功能完全正确，仅缺少文档说明。CJO 保存时机从 `SAVE_RESULTS` 提前到 `RELEASE_AST` 在语义上等价（CHIR 输出模式不需要 CodeGen）。

**修复建议**：在 §4.6 或 §4.9 中补充一段说明 DefaultCI 的 Phase 0e 行为。纯文档改动。

### G-03 [High] Phase 0c/0d 执行顺序导致物化清空写入所需数据 — 确认，维持 High，P0

**裁决：确认，严重程度 High，P0 阻塞**

这是本轮最关键的发现。设计文档验证完全支持攻击方的分析：

**执行路径 1（DefaultCI，通过 `ReleaseASTMemory()` 直接执行）**：
1. Phase 0c `MaterializeCachedASTReferences()`：物化 `varAndFuncDep`/`semaInfo.usages`/`order`，然后 **clear 原始数据**（§4.5 lines 764-769）
2. Phase 0d `WriteCachedInfoBeforeRelease()`：内部第一行调用 `MaterializeCachedASTReferences()`（§4.5 line 690），但此时原始数据已被 Phase 0c clear，物化循环在空数据上执行，`matDep` 为空，`cachedInfo.materializedVarFuncDep = std::move(matDep)` **覆盖第一次物化结果为空**
3. `WriteCache(pkg, std::move(cachedInfo), std::move(order), path)` 写入空数据

**执行路径 2（IncrementalCI，通过 `PerformASTRelease()` 先调用）**：
1. `WriteCachedInfoBeforeRelease()`：内部调用 `MaterializeCachedASTReferences()`（第一次，正确物化），然后 `std::move(cachedInfo)` 和 `std::move(order)` 写入缓存
2. `ReleaseASTMemory()` Phase 0c：`MaterializeCachedASTReferences()`（第二次，原始数据已被 clear + move），物化结果为空，**覆盖第一次物化结果**

两条路径都有问题。根因是 `MaterializeCachedASTReferences()` 的"清空原始数据"操作与 `WriteCachedInfoBeforeRelease()` 的"使用原始数据写入"操作之间存在时序冲突，且 `MaterializeCachedASTReferences()` 缺少幂等性守卫。

**修复方案评估**：

攻击方提出的方案 A（调换 Phase 0c/0d 顺序 + 移除 `WriteCachedInfoBeforeRelease()` 内部的 `MaterializeCachedASTReferences()` 调用）是最简洁的修复：

```
修复后的 Phase 0 执行顺序：
0a. PrepareCodeGenInfo()           — 有守卫
0b. MaterializePackageDependence() — 有守卫
0d. WriteCachedInfoBeforeRelease() — 使用原始 AST 数据写入（不再内部调用物化）
0c. MaterializeCachedASTReferences() — 物化后清空原始数据（有幂等性守卫）
0e. PerformResultsSaving()         — 有守卫
```

这样：
- DefaultCI 路径：Phase 0d 先写入（原始数据完整），Phase 0c 再物化（为 `--no-release-ast` 延迟写入准备）
- IncrementalCI 路径：`PerformASTRelease()` 中先写入（原始数据完整），`ReleaseASTMemory()` Phase 0c 物化被幂等性守卫跳过

**评审方推荐方案 A**，约 5 行代码改动。

### G-04 [Medium] Phase 0d 缺少 `!cacheWritten` 守卫 — 确认，维持 Medium，P1

**裁决：确认，严重程度 Medium，P1**

设计文档验证确认：`ReleaseASTMemory()` Phase 0d 的条件是 `if (ShouldWriteCacheFile())`（§4.3 line 480），**不检查 `cacheWritten`**。而 `IncrementalCI::PerformASTRelease()` 中有 `!cacheWritten` 守卫（§4.6 line 827）。

这意味着 IncrementalCI 路径下：
1. `PerformASTRelease()` 步骤 4：`WriteCachedInfoBeforeRelease()` + `cacheWritten = true`
2. `ReleaseASTMemory()` Phase 0d：`ShouldWriteCacheFile()` 仍为 true，`WriteCachedInfoBeforeRelease()` 被第二次调用

第二次调用时 `cachedInfo` 已被 `std::move` 移走，`WriteCache` 收到空数据，覆盖第一次的正确写入。

与 G-03 同源。修复 G-03（调换顺序 + 幂等性守卫）后，仍需在 Phase 0d 添加 `!cacheWritten` 守卫以防止双重写入。

**修复建议**：Phase 0d 条件改为 `if (ShouldWriteCacheFile() && !cacheWritten)`。1 行改动。

### G-06 [Medium] MaterializeCachedASTReferences 缺少幂等性守卫 — 确认，维持 Medium，P0

**裁决：确认，严重程度 Medium，但优先级 P0（与 G-03 同源，是 G-03 修复的必要组成部分）**

设计文档验证确认 `MaterializeCachedASTReferences()`（§4.5 lines 720-770）没有任何幂等性守卫。第二次调用时在空数据上执行，产生空的物化结果并覆盖第一次的正确结果。

这是 G-03 的核心组成部分。修复方案：

```cpp
void CompilerInstance::MaterializeCachedASTReferences()

    cachedInfoMaterialized = true;
    // ... 物化逻辑 ...
}
```

需要在 `CompilerInstance.h` 中新增 `bool cachedInfoMaterialized = false;` 成员变量。

## 四、G-03/G-04/G-06 根因分析与统一修复方案

### 4.1 根因

G-03、G-04、G-06 本质上是同一个根因：**ADR-009 的 Phase 0 内部执行顺序设计不当**。

具体来说：
1. `MaterializeCachedASTReferences()` 的"物化 + 清空原始数据"是破坏性操作
2. `WriteCachedInfoBeforeRelease()` 需要原始数据（`cachedInfo`、`order`、`srcPkgs[0]`）
3. Phase 0c（物化）在 Phase 0d（写入）之前执行，导致写入时原始数据已被清空
4. `WriteCachedInfoBeforeRelease()` 内部又调用了 `MaterializeCachedASTReferences()`，造成双重调用
5. `MaterializeCachedASTReferences()` 缺少幂等性守卫，第二次调用覆盖第一次结果

### 4.2 统一修复方案（3 步，约 5 行代码）

**步骤 1**：调换 Phase 0c 和 Phase 0d 的顺序（先写入，后物化）

```cpp
// ReleaseASTMemory() Phase 0 修正后的顺序：
// 0a. PrepareCodeGenInfo()           — 有守卫
// 0b. MaterializePackageDependence() — 有守卫
// 0d. WriteCachedInfoBeforeRelease() — 先写入（使用原始 AST 数据）
// 0c. MaterializeCachedASTReferences() — 后物化（为延迟写入准备）
// 0e. PerformResultsSaving()         — 有守卫
```

**步骤 2**：`WriteCachedInfoBeforeRelease()` 移除内部的 `MaterializeCachedASTReferences()` 调用

```cpp
void CompilerInstance::WriteCachedInfoBeforeRelease()
{
    // 不再调用 MaterializeCachedASTReferences()，直接使用原始 AST 数据
#ifdef CANGJIE_CODEGEN_CJNATIVE_BACKEND
    auto& pkg{*srcPkgs[0]};
    std::string path{invocation.globalOptions.GenerateCachedPathName(
        pkg.fullPackageName, CACHED_AST_EXTENSION)};
    WriteCache(pkg, std::move(cachedInfo), std::move(order), path);
#endif
}
```

**步骤 3**：添加守卫

```cpp
// MaterializeCachedASTReferences() 添加幂等性守卫
void CompilerInstance::MaterializeCachedASTReferences()
{
    if (cachedInfoMaterialized) { return; }
    cachedInfoMaterialized = true;
    // ... 物化逻辑不变 ...
}

// Phase 0d 添加 !cacheWritten 守卫
if (ShouldWriteCacheFile() && !cacheWritten) {
    WriteCachedInfoBeforeRelease();
    cacheWritten = true;
}
```

### 4.3 修复后的执行路径验证

**DefaultCI 路径**：
1. `PerformASTRelease()` → `ReleaseASTMemory()`
2. Phase 0a/0b：有守卫，正常执行
3. Phase 0d：`WriteCachedInfoBeforeRelease()` 使用原始数据写入，`cacheWritten = true`
4. Phase 0c：`MaterializeCachedASTReferences()` 物化原始数据（为 `--no-release-ast` 延迟写入准备）
5. Phase 0e：`PerformResultsSaving()` 通过虚方法分派到 DefaultCIImpl，安全执行
6. Phase 1-4：正常清理

**IncrementalCI 路径**：
1. `PerformASTRelease()` 步骤 3：`PerformResultsSaving()` + `resultsSaved = true`
2. 步骤 4：`WriteCachedInfoBeforeRelease()` 使用原始数据写入 + `cacheWritten = true`
3. `ReleaseASTMemory()` Phase 0a/0b：有守卫，跳过
4. Phase 0d：`!cacheWritten` 守卫，跳过
5. Phase 0c：`cachedInfoMaterialized` 守卫... 等等，IncrementalCI 路径中 `MaterializeCachedASTReferences()` 尚未被调用（步骤 2 中 `WriteCachedInfoBeforeRelease()` 不再内部调用），所以 Phase 0c 会正常执行物化。但此时 `cachedInfo` 已被 `std::move` 移走，物化在空数据上执行。

这里有一个微妙问题：`std::move(cachedInfo)` 后 `cachedInfo` 处于 moved-from 状态，`varAndFuncDep` 可能为空也可能不为空（取决于 `CompilationCache` 的移动构造函数实现）。但由于 `cacheWritten = true`，后续不会再有代码路径使用 `cachedInfo` 的原始数据，物化结果是否为空不影响正确性。

**结论**：修复方案正确。IncrementalCI 路径中 Phase 0c 的物化在 moved-from 数据上执行，产生空的物化结果，但这不影响功能（缓存已写入，物化结果仅供 `--no-release-ast` 延迟写入使用，而 IncrementalCI 路径已完成写入）。

## 七、最终裁决

### 裁决：有条件通过（Conditional Pass）— Phase 0c/0d 顺序修正后可直接编码

本轮发现的 2 个 P0 阻塞项（G-03/G-06）是 ADR-009 修复引入的内部时序问题，根因单一，修复方案明确（调换顺序 + 移除内部调用 + 添加守卫），约 5 行代码改动，不涉及任何架构变更。

**与迭代 4 的 Revise Required 不同**，本轮给出 Conditional Pass 而非 Revise Required，理由：
1. 修复方案极其简单（5 行代码），不需要新的设计文档章节
2. 不涉及新的数据结构、新的接口、新的架构决策
3. 修复方向无争议（攻击方和评审方对修复方案完全一致）
4. 攻击面已接近枯竭（从"找遗漏消费者"深入到"审计修复代码内部顺序"）

**通过条件**：
