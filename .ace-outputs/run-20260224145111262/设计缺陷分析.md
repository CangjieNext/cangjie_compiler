# AST 内存释放方案 — 威胁建模与设计缺陷分析报告

## 人工反馈回应

> **反馈 1 & 2**：TranslateToCHIR 执行完之后就释放，注意生命周期更长的变量保存的 AST 指针及时置空

**处理结果**：已作为本次分析的最高优先级检查项。通过全量代码搜索，发现了 **15+ 个长生命周期 AST 指针持有者**，其中 **7 个未被设计方案覆盖**。详见缺陷 D-01 至 D-04。

---

## 一、威胁分析概述

### 1.1 攻击面总结

方案 A 的核心操作是在 CHIR lowering 完成后，通过 `ReleaseASTMemory()` 释放 `srcPkgs` 和 `pkgCtxMap`。这个操作的攻击面集中在：

1. **悬空指针面**：所有在 `srcPkgs.clear()` 后仍持有 AST 指针的变量，都会变成 use-after-free 的攻击入口
2. **遗漏清理面**：设计方案只覆盖了部分 AST 指针持有者，遗漏的持有者在后续阶段被访问时会 crash
3. **时序依赖面**：释放点与 SAVE_RESULTS、CodeGen 的执行顺序存在耦合
4. **增量编译面**：物化逻辑的完备性直接影响增量编译的正确性

### 1.2 关键假设验证

| 假设 | 验证结果 | 风险 |
|------|---------|------|
| CHIR IR 节点不持有 AST 指针 | ✅ 已验证：CHIR IR 核心模块 0 个 AST 引用 | 低 |
| CodeGen 仅依赖 CHIR | ⚠️ 部分正确：CodeGen 通过 `AST::Package&` 获取 `fullPackageName` | 中 |
| AST2CHIR 是临时对象 | ✅ 已验证：栈上对象，lowering 结束自动析构 | 低 |
| CompilationCache 只有 `varAndFuncDep` 和 `semaInfo.usages` 持有 AST 指针 | ✅ 已验证：Cache 中其他字段使用 `RawMangledName` 字符串 | 低 |
| `PerformCodeGen` 不直接访问 AST | ❌ 错误：`PerformCodeGen` 调用 `GetSourcePackages()` 遍历 `srcPkgs` | **高** |

### 1.3 编译流水线数据流攻击面

```
CHIR ──► [RELEASE_AST] ──► CODEGEN ──► SAVE_RESULTS
              │                │              │
              │                │              └─ 需要 srcPkgs（CHIR 模式）
              │                └─ 需要 srcPkgs 遍历 + pkg.fullPackageName
              └─ 释放 srcPkgs、pkgCtxMap
```

**核心矛盾**：`srcPkgs.clear()` 后，`GetSourcePackages()` 返回空 vector，CodeGen 循环体不执行，编译产物丢失。

## 二、发现的设计缺陷列表（按严重程度排序）

### D-01 [Critical] PerformCodeGen 依赖 srcPkgs 遍历，释放后 CodeGen 被静默跳过

**类别**：编译器设计缺陷

**问题描述**：

`PerformCodeGen()` 的实现通过 `GetSourcePackages()` 遍历 `srcPkgs` 来驱动 CodeGen：

```cpp
// DefaultCompilerInstance.cpp:305-314
bool DefaultCIImpl::PerformCodeGen()
{
    RearrangeImportedPackageDependence();
    bool ret = true;
    for (auto& srcPkg : ci.GetSourcePackages()) {  // srcPkgs 已被清空！
        ret = ret && CodegenOnePackage(*srcPkg, false);
    }
    return ret;  // 返回 true，但实际没有生成任何代码
}
```

`GetSourcePackages()` 直接从 `srcPkgs` 构建返回值：

```cpp
// CompilerInstance.cpp:934-941
std::vector<Ptr<Package>> CompilerInstance::GetSourcePackages()
{
    std::vector<Ptr<Package>> packages;
    for (auto& srcPkg : srcPkgs) {
        packages.push_back(srcPkg.get());
    }
    return packages;
}
```

AST 释放后 `srcPkgs` 为空，`GetSourcePackages()` 返回空 vector，CodeGen 循环不执行，**编译器静默成功但不产出任何目标代码**。

**触发输入**：任何正常的仓颉源文件。

```cangjie
// test.cj
package test
func main() {
    println("hello")
}
```

**影响范围**：所有编译任务。编译器报告成功但不生成 .bc/.o 文件，用户无法链接。

**攻击场景**：这不是边界情况，而是方案 A 的必然结果。设计方案提出了 `chirPkgByName` 替换 `astPkg2chirPkgMap`，但**完全没有设计 CodeGen 如何在没有 `srcPkgs` 的情况下遍历包**。`CodegenOnePackage` 的签名是 `AST::Package&`，释放后无法调用。

**同时影响**：`RearrangeImportedPackageDependence()` 也通过 `importManager.GetAllImportedPackages()` 访问 imported packages 的 `srcPackage` 指针，这些 AST::Package 对象可能也已被释放。

**修复方向**：必须重构 CodeGen 入口，改为通过 `CHIRData::GetAllCHIRPackages()` 驱动，而非通过 `srcPkgs`。需要将 `pkg.fullPackageName` 等必要信息提前保存到 CHIR 层或独立的 metadata 结构中。

### D-02 [Critical] 7 个长生命周期 AST 指针持有者未被设计方案覆盖（人工反馈重点）

**类别**：编译器设计缺陷 — 遗漏清理

**问题描述**：

设计方案的 `ReleaseASTMemory()` 只清理了以下持有者：
- `astPkg2chirPkgMap` ✅
- `pkgs` ✅
- `srcPkgs` ✅
- `pkgCtxMap` ✅
- `typeChecker` ✅
- `gim` ✅
- `CHIRTypeCache::typeMap` ✅

但以下 CompilerInstance 成员变量**持有 AST 指针且未被清理**：

| 遗漏变量 | 类型 | 位置 |
|---------|------|------|
| `currentPkg` | `Ptr<AST::Package>` | CompilerInstance.h:453 |
| `mangledName2DeclMap` | `map<string, Ptr<AST::Decl>>` | CompilerInstance.h:497 |
| `rawMangleName2DeclMap` | `unordered_map<RawMangledName, Ptr<const AST::Decl>>` | CompilerInstance.h:514 |
| `declsWithDuplicatedRawMangleName` | `unordered_set<Ptr<const AST::Decl>>` | CompilerInstance.h:516 |
| `directExtends` | `unordered_map<RawMangledName, list<pair<Ptr<AST::ExtendDecl>, int>>>` | CompilerInstance.h:517 |
| `order` | `vector<const AST::Decl*>` | CompilerInstance.h:519 |
| `chirInfo.ccTys` | `unordered_set<Ptr<const AST::StructTy>>` | CompilerInstance.h:356 |

**触发场景**：AST 释放后，任何访问上述变量的代码路径都会触发 use-after-free。

```cangjie
// 触发 chirInfo.ccTys 悬空的场景：
// 任何包含 closure convert 的代码
package test
func apply(f: () -> Int64): Int64 { return f() }
func main() {
    let x = 42
    let result = apply({ => x })  // 触发 closure convert，ccTys 记录 StructTy
    println(result.toString())
}
```

**影响范围**：
- `currentPkg`：如果后续阶段（如错误报告）访问当前包信息，crash
- `mangledName2DeclMap` / `rawMangleName2DeclMap`：增量编译场景下可能被后续逻辑读取
- `chirInfo.ccTys`：CHIR 优化或 CodeGen 阶段如果访问 closure convert 类型信息，crash
- `order`：增量编译的声明顺序分析如果在释放后执行，crash

**修复方向**：在 `ReleaseASTMemory()` 中补充清理：

```cpp
currentPkg = nullptr;
mangledName2DeclMap.clear();
rawMangleName2DeclMap.clear();
declsWithDuplicatedRawMangleName.clear();
directExtends.clear();
order.clear();
chirInfo.ccTys.clear();
```

### D-03 [Critical] ImportManager、TypeManager、BaseMangler 持有大量 AST 指针未清理

**类别**：编译器设计缺陷 — 遗漏清理（人工反馈重点）

**问题描述**：

设计方案完全没有提及以下三个关键管理器的 AST 指针清理：

**ImportManager**（CompilerInstance 的直接成员，非指针，生命周期 = CompilerInstance）：
- `curPackage`：`Ptr<AST::Package>` — 指向已释放的源包
- 内部 `CjoManagerImpl` 持有 `importedPackages`（`vector<OwnedPtr<AST::Package>>`）— 这些是 imported 包的所有权，与 `srcPkgs` 独立

**TypeManager**（CompilerInstance 持有的指针，设计方案未提及清理）：
- `checkedTyExtendRelation`：`unordered_set<pair<Ptr<AST::Ty>, Ptr<AST::Ty>>>`
- `boxedTys`：`unordered_set<Ptr<AST::Ty>>`
- `boxUsedExtends`：`unordered_set<Ptr<AST::ExtendDecl>>`
- `tyUsedExtends`：`unordered_map<Ptr<AST::Ty>, unordered_set<Ptr<AST::ExtendDecl>>>`
- `builtinTyToExtendMap`：`unordered_map<Ptr<AST::Ty>, set<Ptr<AST::ExtendDecl>>>`
- `declToExtendMap`：`unordered_map<Ptr<const AST::InheritableDecl>, set<Ptr<AST::ExtendDecl>>>`
- `anyTy`、`ctypeTy`：`Ptr<AST::Ty>`
- 以及 10+ 个其他 AST 类型缓存

**BaseMangler**（通过 `unique_ptr<BaseMangler> mangler` 持有）：
- `manglerCtxTable` 中的 `ManglerContext` 持有：
  - `file2GlobalWildcardVar`：`map<Ptr<const AST::File>, vector<Ptr<AST::VarWithPatternDecl>>>`
  - `node2Lambda`：`map<Ptr<const AST::Node>, vector<Ptr<AST::LambdaExpr>>>`
  - `node2LocalVar`、`node2LocalFunc`、`file2ExtendDecl` 等

**触发输入**：任何正常编译。这些管理器在编译过程中必然被填充。

```cangjie
// 触发 TypeManager 缓存填充
package test
interface Printable { func show(): String }
class Foo <: Printable {
    func show(): String { "Foo" }
}
extend Int64 <: Printable {
    func show(): String { this.toString() }
}
func main() {
    let x: Printable = Foo()
    println(x.show())
}
```

**影响范围**：
- TypeManager 未被 delete（设计方案只 delete 了 typeChecker 和 gim），其内部 AST 指针全部悬空
- ImportManager 是栈成员，析构在 CompilerInstance 析构时，中间阶段其 AST 指针全部悬空
- BaseMangler 的 ManglerContext 缓存在 CHIR 后不再需要但未清理

**修复方向**：
1. `delete typeManager; typeManager = nullptr;`（或至少调用 TypeManager 的清理方法）
2. `importManager.curPackage = nullptr;`（或提供 `ImportManager::ClearASTReferences()` 方法）
3. `mangler.reset();`（或 `mangler->ClearContextCache()`）
4. 需要评估 CjoManagerImpl 的 `importedPackages` 是否也应释放

### D-04 [High] AnnotationChecker 全局变量 g_annoInfo 未清理，持有 AST 指针

**类别**：编译器设计缺陷

**问题描述**：

CHIR 阶段的 AnnotationChecker 使用多个全局静态变量持有 AST 指针：

```cpp
// AnnotationChecker.cpp:47-50
std::unordered_map<const ClassDef*, AnnotationInfo> g_annoInfo{};
std::vector<CustomAnnoInfoOnType> g_typeAnnoInfo{};
std::vector<CustomAnnoInfoOnDecl> g_valueAnnoInfo{};
```

其中 `AnnotationInfo` 包含：
```cpp
struct AnnotationInfo {
    const ClassDecl* decl;    // AST 指针
    AST::Annotation* anno;    // AST 指针（非 const，用于回写）
    std::vector<GlobalVar*> vars;
    std::vector<Func*> funcs;
};
```

`g_typeAnnoInfo` 和 `g_valueAnnoInfo` 在 annotation checking 结束后被清理，但 **`g_annoInfo` 没有被清理**。

同时，`ComputeAnnotations` 返回的 `ConstEvalResult` 包含：
```cpp
using AnnoMap = std::unordered_map<const Decl*, std::vector<AnnoInstance>>;
struct ConstEvalResult {
    AnnoMap map;  // key 是 AST::Decl*
};
```

`AnnoInstanceClassInst` 内部还持有 `const InheritableDecl* cl`（AST 指针），通过 `shared_ptr` 延长生命周期。

**触发输入**：

```cangjie
// 使用自定义注解触发 annotation factory
package test
@Annotation
open class MyAnno <: Annotation {
    let value: String
    init(value: String) { this.value = value }
}

@MyAnno("test")
func foo() { println("annotated") }

func main() { foo() }
```

**影响范围**：如果 `g_annoInfo` 在 AST 释放后被任何代码路径访问（包括错误诊断），会触发 use-after-free。`ConstEvalResult` 如果被缓存到 CHIR 阶段之后，其 `AnnoMap` 中的 AST 指针全部悬空。

**修复方向**：
1. 确保 `g_annoInfo.clear()` 在 annotation checking 完成后执行
2. 审计 `ConstEvalResult` 的生命周期，确保其在 AST 释放前被消费完毕
3. 考虑将全局变量改为 CHIR lowering 的局部状态，避免全局生命周期问题

### D-05 [High] IncrementalCompilerInstance 的 PerformResultsSaving 在 CHIR 后访问 AST

**类别**：编译器设计缺陷

**问题描述**：

设计方案只考虑了 `DefaultCompilerInstance` 的 `PerformResultsSaving` 时序问题，但 `IncrementalCompilerInstance` 有独立的实现：

```cpp
// IncrementalCompilerInstance.cpp:519-538
bool IncrementalCompilerInstance::PerformResultsSaving()
{
    if (kind == IncreKind::NO_CHANGE || kind == IncreKind::EMPTY_PKG) {
        return true;
    }
    bool ret = true;
    for (auto& srcPkg : GetSourcePackages()) {       // srcPkgs 已空！
        if (invocation.globalOptions.outputMode == GlobalOptions::OutputMode::CHIR) {
            ret = ret && SaveCjo(*srcPkg);            // 访问 AST
        }
        // ...
        ret = ret && FileUtil::WriteBufferToASTFile(
            cachedCjo, importManager.ExportASTSignature(*srcPkg));  // 访问 AST
    }
    return ret;
}
```

**关键问题**：
1. 增量编译模式下，`PerformResultsSaving` 不仅在 CHIR 模式下需要 AST，在**所有模式下**都调用 `ExportASTSignature(*srcPkg)` 来导出 AST 签名
2. 设计方案的 `DefaultCompilerInstance::PerformASTRelease()` 只处理了 CHIR 模式的提前保存，没有处理增量编译的 `ExportASTSignature`

**触发输入**：增量编译模式下的任何编译任务。

```bash
cjc --incremental test.cj  # 增量编译模式
```

**影响范围**：增量编译的 CJO 缓存写入失败，导致下次编译无法正确识别增量变化。

**修复方向**：
1. `IncrementalCompilerInstance` 必须 override `PerformASTRelease()`
2. 在释放前完成 `ExportASTSignature` 和 `SaveCjo`
3. 或者将 AST 签名信息在 CHIR lowering 阶段提前物化

### D-06 [High] DiagAdapter 持有 AST::Node 指针，CHIR/CodeGen 阶段诊断可能 crash

**类别**：编译器设计缺陷

**问题描述**：

`DiagAdapter`（CHIR 工具类）持有：
```cpp
// DiagAdapter.h
std::map<uint64_t, Ptr<AST::Node>, std::greater<>> posRange2MacroCallMap;
```

该 map 在 CHIR lowering 期间被填充，用于将诊断信息关联到宏展开的原始调用点。DiagAdapter 的诊断方法会访问这些 AST::Node 指针：

```cpp
node.curMacroCall = it->second;  // 使用 AST 指针
```

如果 DiagAdapter 实例的生命周期超过 AST 释放点（例如被 CHIR 优化 pass 或 CodeGen 阶段复用），则诊断时会访问已释放的 AST 节点。

**触发输入**：

```cangjie
// 宏展开后在 CHIR 优化阶段触发诊断
package test
@Macro
func myMacro(input: Tokens): Tokens { /* ... */ }

@myMacro
func foo() {
    // 宏展开后的代码在 CHIR 优化中触发警告
    var x: Int64 = 0  // unused variable warning in CHIR phase
}
```

**影响范围**：宏展开代码在 CHIR/CodeGen 阶段产生诊断信息时 crash。

**修复方向**：
1. 确认 DiagAdapter 实例的生命周期是否限于 AST2CHIR（如果是栈上对象则安全）
2. 如果 DiagAdapter 被 CHIR 后续阶段复用，需要在 AST 释放前清理 `posRange2MacroCallMap`

### D-07 [High] Compile() 错误恢复路径在 CHIR 部分失败后仍可能访问 AST

**类别**：编译器设计缺陷

**问题描述**：

`Compile()` 方法的错误处理逻辑：

```cpp
// CompilerInstance.cpp:183-205
bool CompilerInstance::Compile(CompileStage stage)
{
    // ...
    for (; i <= endStageNum; i++) {
        if (!performMap[static_cast<CompileStage>(i)](this)) {
            success = false;
            break;
        }
    }
    if (invocation.globalOptions.dumpToScreen) {
        DumpASTToScreen(GetSourcePackages());  // 失败后仍访问 AST！
    }
    diag.ReportErrorAndWarningCount();
    return success;
}
```

如果 CHIR 阶段部分成功（处理了部分包后失败），`RELEASE_AST` 阶段可能已经执行或部分执行。此时 `break` 跳出循环后，`DumpASTToScreen(GetSourcePackages())` 会访问已释放的 AST。

**触发输入**：

```cangjie
// 多包编译，第二个包在 CHIR 阶段失败
// pkg_a/a.cj
package pkg_a
func helper(): Int64 { return 42 }

// pkg_b/b.cj（触发 CHIR 错误）
package pkg_b
import pkg_a.*
func main() {
    // 构造一个在 CHIR lowering 阶段才暴露的错误
    let f = helper
    f()  // 某些边界情况下 CHIR lowering 可能失败
}
```

配合 `--dump-ast` 选项编译。

**影响范围**：调试场景下（`--dump-ast`），CHIR 阶段失败后的 AST dump 会 crash。

**修复方向**：
1. `DumpASTToScreen` 调用前检查 `IsASTReleased()`
2. 或者将 `RELEASE_AST` 阶段的执行放在 `Compile()` 循环之外，确保只在所有阶段成功后才释放
3. 考虑在 `RELEASE_AST` 失败时的回滚策略

### D-08 [High] CjoManagerImpl::importedPackages 的 AST::Package 所有权独立于 srcPkgs，释放策略不明

**类别**：设计未到位

**问题描述**：

`CjoManagerImpl` 持有：
```cpp
std::vector<OwnedPtr<AST::Package>> importedPackages;  // 独立的所有权！
```

这些是从 .cjo 文件反序列化加载的 imported packages，其所有权在 `CjoManagerImpl` 中，**不在 `CompilerInstance::srcPkgs` 中**。

设计方案只清理了 `srcPkgs`（源包），但 imported packages 同样是 AST 节点，占用大量内存。更关键的是：
- `ImportManager` 是 `CompilerInstance` 的直接成员（非指针），生命周期等于 `CompilerInstance`
- `ImportManager` 内部持有 `CjoManager`（通过 `OwnedPtr<CjoManager>`）
- `CjoManagerImpl::packageNameMap` 中的 `PackageInfo` 持有 `Ptr<AST::Package> pkg` 指向这些 imported packages

如果只释放 `srcPkgs` 而不释放 imported packages：
1. 内存收益大打折扣（imported packages 可能占 AST 总内存的 30-50%）
2. `RearrangeImportedPackageDependence()` 在 CodeGen 前访问 imported packages 的 `srcPackage` 指针

**触发输入**：

```cangjie
// 大量依赖外部包的项目
package myapp
import std.collection.*
import std.io.*
import std.math.*
import third_party.json.*
import third_party.http.*
// ... 大量 import
func main() { /* ... */ }
```

**影响范围**：
- 内存收益从预估的 90-95% 降低到可能只有 50-60%
- imported packages 的 AST 指针在各处被引用，不清理会留下大量悬空指针

**修复方向**：
1. 设计方案需要明确 imported packages 的释放策略
2. 如果释放，需要同步清理 `ImportManager` 和 `CjoManagerImpl` 中的所有引用
3. 如果不释放，需要在文档中说明原因和内存影响

### D-09 [Medium] CompilationCache 物化方案未覆盖 rawMangleName 为空的边界情况

**类别**：编译器设计缺陷

**问题描述**：

物化逻辑使用 `decl->rawMangledName` 作为字符串键：

```cpp
void CompilerInstance::MaterializeCachedASTReferences()
{
    for (auto& [decl, deps] : cachedInfo.varAndFuncDep) {
        depNames.push_back(dep->rawMangledName);  // 假设 rawMangledName 非空
        matDep.emplace_back(decl->rawMangledName, std::move(depNames));
    }
}
```

AST 节点中 `rawMangleName` 的定义（注意拼写差异）：
```cpp
// Node.h:940
std::string rawMangleName;  // 字段名是 rawMangleName（无 d）
```

但设计方案中使用的是 `rawMangledName`（有 d）。需要确认实际字段名。

更关键的是，`rawMangleName` 在 Parser 阶段生成，用于增量编译标识。但以下场景可能导致该字段为空：
1. 编译器内部生成的合成声明（synthetic decls）
2. 宏展开生成的声明
3. 泛型实例化生成的声明（由 GIM 创建）

如果 `rawMangleName` 为空字符串，物化后多个不同的声明会映射到同一个空字符串键，导致**增量编译的依赖关系丢失或错误合并**。

**触发输入**：

```cangjie
// 泛型实例化 + 增量编译
package test
class Container<T> {
    var items: Array<T> = Array<T>()
    func add(item: T) { items.append(item) }
}
func main() {
    let c1 = Container<Int64>()
    let c2 = Container<String>()
    c1.add(42)
    c2.add("hello")
}
```

在增量编译模式下修改 `Container` 的实现，观察依赖关系是否正确传播。

**影响范围**：增量编译的正确性。依赖关系错误可能导致应该重编译的声明被跳过。

**修复方向**：
1. 确认字段名是 `rawMangleName` 还是 `rawMangledName`，统一命名
2. 物化时对空字符串键添加断言或 fallback（如使用 `mangledName` 或节点 ID）
3. 添加物化后的完整性校验：物化前后的 entry 数量必须一致

---

### D-10 [Medium] AST_ACCESS_GUARD 宏仅在 Debug 构建生效，Release 构建无保护

**类别**：设计未到位

**问题描述**：

```cpp
#ifndef NDEBUG
#define AST_ACCESS_GUARD(ci) \
    CJC_ASSERT(!ci.IsASTReleased() && "Accessing AST after release!")
#else
#define AST_ACCESS_GUARD(ci) ((void)0)
#endif
```

在 Release 构建中，`AST_ACCESS_GUARD` 是 no-op。如果存在遗漏的 AST 访问路径（鉴于上述 D-01 到 D-08 的发现，遗漏是高概率事件），Release 构建会直接 use-after-free，表现为：
- 随机 crash（最好情况）
- 静默数据损坏（最坏情况，生成错误的目标代码）
- 安全漏洞（如果编译器处理不可信输入）

**触发输入**：任何触发遗漏路径的正常代码，在 Release 构建下编译。

**影响范围**：生产环境中的编译器稳定性。

**修复方向**：
1. 在 Release 构建中，对关键的 AST 访问入口（`GetSourcePackages()`、`GetASTContextByPackage()` 等）添加运行时检查，返回空/null 而非 crash
2. 考虑使用 `Ptr` 模板的特化版本，在 AST 释放后自动将所有 `Ptr<AST::*>` 标记为无效
3. 至少在 `GetSourcePackages()` 中添加 `if (astReleased) return {};`

---

### D-11 [Medium] 析构函数与 ReleaseASTMemory 的重复释放风险

**类别**：编译器设计缺陷

**问题描述**：

现有析构函数：
```cpp
CompilerInstance::~CompilerInstance()
{
    srcPkgs.clear();     // 释放 AST
    pkgCtxMap.clear();   // 释放 ASTContext
    delete typeChecker;
    delete typeManager;
    delete testManager;
    delete gim;
    delete packageManager;
}
```

`ReleaseASTMemory()` 也执行：
```cpp
srcPkgs.clear();
pkgCtxMap.clear();
delete typeChecker; typeChecker = nullptr;
delete gim; gim = nullptr;
```

如果 `ReleaseASTMemory()` 执行后，析构函数再次执行：
- `srcPkgs.clear()` 和 `pkgCtxMap.clear()` 是安全的（已经为空）
- `delete typeChecker` — 设计方案设置了 `nullptr`，安全
- `delete gim` — 设计方案设置了 `nullptr`，安全
- **但 `delete typeManager`、`delete testManager`、`delete packageManager` 在析构函数中执行时，它们内部的 AST 指针已经悬空**

`TypeManager` 的析构函数如果遍历其内部的 AST 指针容器（如 `allocatedTys`），可能触发对已释放 AST 节点的访问。

**触发输入**：正常编译流程结束后的 CompilerInstance 析构。

**影响范围**：编译器退出时 crash 或 ASan 报告 use-after-free。

**修复方向**：
1. 在 `ReleaseASTMemory()` 中也清理 TypeManager 的 AST 缓存（或直接 delete）
2. 确保所有管理器的析构函数不会遍历 AST 指针
3. 或者在析构函数中检查 `astReleased` 标记，跳过已释放的资源

---

### D-12 [Medium] --no-release-ast 开关缺少与增量编译模式的交互设计

**类别**：设计未到位

**问题描述**：

设计方案提出 `--no-release-ast` 作为调试回退开关，但未设计以下交互：

1. **增量编译 + AST 释放**：增量编译依赖 `CompilationCache` 中的 AST 指针进行差异分析。物化后使用字符串键，但如果物化逻辑有 bug，`--no-release-ast` 可以回退。然而，增量编译的 `WriteCache` 逻辑是否能同时处理"物化后"和"未物化"两种数据格式？

2. **CHIR 输出模式 + 非增量编译**：`PerformASTRelease()` 中的 `PerformResultsSaving()` 提前调用逻辑，在 `--no-release-ast` 时是否会导致 `PerformResultsSaving()` 被调用两次？

3. **IDE/LSP 场景**：设计方案提到 LSP 子类可以 override `ReleaseASTMemory()` 为 no-op，但 `--no-release-ast` 与 LSP 模式的优先级关系未定义。

**修复方向**：
1. 明确 `--no-release-ast` 的语义：是完全跳过 `RELEASE_AST` 阶段，还是只跳过 `srcPkgs.clear()`
2. 设计 `WriteCache` 的双格式兼容逻辑
3. 添加 `resultsSaved` 标记防止重复保存（设计方案已提出但当前代码中不存在）

---

### D-13 [Low] Ptr 模板是裸指针包装，无法检测 use-after-free

**类别**：语言设计 / 基础设施局限

**问题描述**：

`Ptr<T>` 的实现是纯粹的裸指针包装：

```cpp
template <typename T> class Ptr {
    T* ptr = nullptr;
    T& operator*() const { return *ptr; }  // 无任何有效性检查
    T* operator->() const { return ptr; }  // 无任何有效性检查
};
```

`Ptr` 不提供任何 use-after-free 检测能力。AST 释放后，所有 `Ptr<AST::*>` 变量仍然持有原始地址，解引用时直接访问已释放内存，行为未定义。

这意味着：
- 遗漏的 AST 指针清理不会在运行时被捕获（除非使用 ASan）
- 生产环境中可能产生静默的数据损坏
- 调试此类问题极其困难

**修复方向**（可优化项）：
1. 考虑在 Debug 构建中为 `Ptr` 添加 epoch-based 有效性检查
2. 或者在 AST 释放时，遍历所有已知的 `Ptr<AST::*>` 持有者并置空（但这需要注册机制）
3. 长期方案：方案 C 的 Arena 分配器可以通过 Arena epoch 检测悬空指针

## 三、设计优化建议

### O-01 [必须补全] CodeGen 入口重构 — 脱离 srcPkgs 依赖

**优先级**：P0（阻塞性问题，不解决则方案无法工作）

**现状**：CodeGen 通过 `GetSourcePackages()` → `srcPkgs` 驱动，AST 释放后无法工作。

**优化方向**：
1. 将 CodeGen 入口改为通过 `CHIRData::GetAllCHIRPackages()` 驱动
2. `CodegenOnePackage` 的签名从 `AST::Package&` 改为 `CHIR::Package&`
3. `pkg.fullPackageName` 等元信息从 CHIR::Package 获取（CHIR::Package 已有 `name` 字段）
4. `RearrangeImportedPackageDependence()` 需要重构，不再依赖 `importManager.GetAllImportedPackages()` 返回的 AST::Package 指针

**预期收益**：CodeGen 完全脱离 AST 依赖，方案 A 的核心假设才能成立。

---

### O-02 [必须补全] 完整的 AST 指针持有者清单与清理 checklist

**优先级**：P0

**现状**：设计方案只列出了 7 个需要清理的持有者，实际至少有 20+ 个。

**优化方向**：
建立完整的清理 checklist，按模块分组：

```
CompilerInstance 直接成员：
  □ srcPkgs.clear()
  □ pkgCtxMap.clear()
  □ pkgs.clear()
  □ currentPkg = nullptr
  □ mangledName2DeclMap.clear()
  □ rawMangleName2DeclMap.clear()
  □ declsWithDuplicatedRawMangleName.clear()
  □ directExtends.clear()
  □ order.clear()
  □ chirInfo.ccTys.clear()
  □ astPkg2chirPkgMap.clear()

管理器清理：
  □ delete typeChecker; typeChecker = nullptr
  □ delete gim; gim = nullptr
  □ delete typeManager; typeManager = nullptr（或 typeManager->ClearASTCaches()）
  □ mangler.reset()（或 mangler->ClearContextCache()）
  □ importManager.ClearASTReferences()
  □ testManager 内部 AST 引用审计

缓存清理：
  □ CompilationCache.varAndFuncDep 物化
  □ CompilationCache.semaInfo.usages 物化
  □ CHIRTypeCache::typeMap 清除

全局变量清理：
  □ g_annoInfo.clear()
  □ 确认 g_typeAnnoInfo / g_valueAnnoInfo 已清理
  □ ConstEvalResult 生命周期确认
```

**预期收益**：避免遗漏，提供可审计的清理完整性保证。

---

### O-03 [必须补全] IncrementalCompilerInstance 适配方案

**优先级**：P0

**现状**：设计方案只适配了 `DefaultCompilerInstance`，未提及 `IncrementalCompilerInstance`。

**优化方向**：
1. `IncrementalCompilerInstance` 必须 override `PerformASTRelease()`
2. 在释放前完成 `ExportASTSignature` 和增量编译缓存写入
3. 增量编译的 `WriteCache` 逻辑需要同时支持物化前（AST 指针）和物化后（字符串键）两种格式
4. 测试矩阵需要覆盖：全量编译 × 增量编译 × CHIR 模式 × 非 CHIR 模式

**预期收益**：增量编译场景下的正确性保证。

---

### O-04 [建议改进] 引入 ASTReleaseScope 的 RAII 模式替代手动清理

**优先级**：P1

**现状**：`ReleaseASTMemory()` 是一个大型的手动清理函数，容易遗漏。

**优化方向**：

```cpp
class ASTReleaseScope {
public:
    explicit ASTReleaseScope(CompilerInstance& ci) : ci(ci) {}

    // 注册需要清理的 AST 引用持有者
    template<typename Container>
    void RegisterForCleanup(Container& container) {
        cleanups.push_back([&container]() { container.clear(); });
    }

    void RegisterForCleanup(auto*& ptr) {
        cleanups.push_back([&ptr]() { ptr = nullptr; });
    }

    // 执行所有清理
    void Release() {
        for (auto& cleanup : cleanups) cleanup();
    }

private:
    CompilerInstance& ci;
    std::vector<std::function<void()>> cleanups;
};
```

在各模块初始化时注册清理回调，而非在 `ReleaseASTMemory()` 中硬编码所有清理逻辑。

**预期收益**：
- 新增 AST 指针持有者时，在声明处就注册清理，不会遗漏
- 清理逻辑与持有者声明在同一位置，可审计性更好

### O-05 [建议改进] 为 GetSourcePackages() 添加 AST 释放后的安全降级

**优先级**：P1

**现状**：`GetSourcePackages()` 在 AST 释放后返回空 vector，调用者无感知。

**优化方向**：

```cpp
std::vector<Ptr<Package>> CompilerInstance::GetSourcePackages()
{
    if (astReleased) {
        // Release 构建：返回空并记录警告
        CJLOG_WARN("GetSourcePackages() called after AST release");
        return {};
        // Debug 构建：断言失败
        CJC_ASSERT(false && "GetSourcePackages() called after AST release");
    }
    // ... 原有逻辑
}
```

同时为 CodeGen 提供替代 API：
```cpp
std::vector<std::string> CompilerInstance::GetSourcePackageNames() const;
// 或
std::vector<Ptr<CHIR::Package>> CompilerInstance::GetCHIRPackages() const;
```

**预期收益**：快速定位遗漏的 AST 访问路径，避免静默失败。

### O-06 [建议改进] 物化完整性的自动化验证

**优先级**：P2

**现状**：物化逻辑的正确性完全依赖人工审查。

**优化方向**：
1. 物化前后添加 entry 数量断言：`CJC_ASSERT(matDep.size() == cachedInfo.varAndFuncDep.size())`
2. 添加编译期静态检查：使用 `static_assert` 或自定义 clang-tidy 规则，检测 `CompilationCache` 中新增的 `Ptr<AST::*>` 字段是否有对应的物化逻辑
3. 在 CI 中添加 ASan + 全量测试的 pipeline，作为 AST 释放正确性的持续验证

**预期收益**：防止未来新增 AST 指针字段时遗漏物化。

## 五、总体评估

方案 A 的核心思路（CHIR lowering 后释放 AST）是正确的，关键假设"CHIR IR 不持有 AST 指针"已通过代码审计验证。但当前设计方案存在 **3 个 Critical 级别缺陷**和 **5 个 High 级别缺陷**，主要集中在：

1. **CodeGen 入口仍依赖 AST::Package 遍历**（D-01）— 这是阻塞性问题
2. **大量长生命周期 AST 指针持有者未被清理**（D-02、D-03）— 人工反馈重点关注的问题
3. **增量编译场景完全未适配**（D-05）

这些问题不是方向性错误，而是设计方案的覆盖面不足。建议在修复上述 P0 问题后重新评审。
