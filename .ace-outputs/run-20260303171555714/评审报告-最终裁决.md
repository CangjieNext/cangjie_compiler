## 三、缺陷确认/驳回列表

> 注：红队（攻击方）未提交有效攻击内容（攻击设计方案.md 仅含一行占位文本）。评审方依据代码审查和行业实践，主动识别潜在缺陷并逐条裁定。

### D-01：malloc_trim 在 macOS 上不存在，但设计文档未充分说明

**状态**：⚠️ 确认（低严重度）

**依据**：`malloc_trim` 是 Linux glibc 特有函数，macOS 不提供。Driver.cpp 已用 `#ifdef __linux__` 保护，但设计文档在描述 `mi_collect(true)` 替换时，未明确说明 macOS 路径的处理（macOS 上原本就没有 `malloc_trim`，`mi_collect` 调用范围应扩展到 macOS）。

**建议**：将 `mi_collect(true)` 的调用范围从 `__linux__ && !__ohos__` 扩展到 `(__linux__ && !__ohos__) || __APPLE__`，充分利用 mimalloc 在 macOS 上的内存归还能力。

**修复优先级**：P2（优化项，不阻塞发布）

---

### D-02：cangjie-lsp-share 动态库的 mimalloc 链接策略存在潜在符号冲突

**状态**：⚠️ 确认（中严重度）

**依据**：设计文档（05-实施路线图，第 198-200 行）建议 `cangjie-lsp-share` 链接动态 `mimalloc`，但 `cjc` 主进程已静态链接 `mimalloc-static`（MI_OVERRIDE=ON）。当 `cjc` 加载 `cangjie-lsp-share.so` 时，进程中将同时存在静态 mimalloc（来自 cjc）和动态 mimalloc（来自 lsp-share），可能导致 `mi_heap_t` 状态不共享、统计数据分裂。

**参考**：LLVM 的 mimalloc 集成文档明确指出，同一进程中混用静态/动态 mimalloc 会导致两个独立的分配器实例。

**建议**：`cangjie-lsp-share` 不应独立链接 mimalloc；在 Linux/macOS 上，主进程的全局符号覆盖已经覆盖了 lsp-share 的分配，无需额外链接。仅在 Windows 方案 B 下，lsp-share 保持使用系统分配器。

**修复优先级**：P1（需在合并前修复）

---

### D-03：ExternalProject 下载方式在离线/内网环境下会导致构建失败

**状态**：⚠️ 确认（中严重度）

**依据**：设计文档（02-技术方案设计，第 122-139 行）提供了 ExternalProject 从 GitHub 下载的备选路径。仓颉编译器的 `third_party/boundscheck` 已有类似问题（CMakeLists.txt 第 90-94 行：`git clone` 失败时无降级处理）。在 CI 离线环境或企业内网中，直接访问 `github.com/microsoft/mimalloc` 会失败。

**建议**：强制要求 mimalloc 以 git submodule 或预置 tarball 方式存在于 `third_party/mimalloc`，移除 ExternalProject 自动下载路径，或提供明确的内网镜像配置文档。

**修复优先级**：P1（需在合并前确认部署策略）

---

### D-04：Windows Release 静态链接场景下 mimalloc 与 MinGW CRT 的兼容性未验证

**状态**：⚠️ 确认（中严重度）

**依据**：`src/CMakeLists.txt` 第 149-153 行显示 Windows Release 使用 `-static` 全静态链接。mimalloc 在 MinGW 静态链接场景下有已知问题：MinGW 的 `__attribute__((constructor))` 初始化顺序与 MSVC 不同，可能导致 mimalloc 初始化早于 CRT，引发崩溃。mimalloc 官方 issue #476 有相关记录。

**建议**：在 Windows MinGW Release 构建中，增加专项测试用例，验证 mimalloc 初始化顺序。如发现问题，Windows 平台统一降级为方案 B。

**修复优先级**：P1（Windows 平台特定，需验证）

---

### D-05：性能收益数据（10-15%）缺乏基准测试支撑

**状态**：⚠️ 确认（低严重度，信息完整性问题）

**依据**：设计文档多处引用"编译时间提升 10-15%"，但未提供仓颉编译器的实测数据，仅参考了通用场景的 mimalloc 性能报告。不同编译器的内存分配模式差异显著（例如 Clang 的 BumpPtrAllocator 大量使用，实际 malloc 调用比例可能低于预期）。

**建议**：在 M1 里程碑（基础集成完成后）立即执行基准测试，以实测数据替换估算数据，作为 M2 里程碑的入场条件。

**修复优先级**：P2（不阻塞集成，但需在默认启用前完成）

---

### D-06：FrontendTool.cpp 中的 malloc.h 包含未在代码示例中处理

**状态**：⚠️ 确认（低严重度）

**依据**：探索发现 `src/FrontendTool/FrontendTool.cpp` 第 16 行也包含 `<malloc.h>`，设计文档（05-实施路线图，第 243-256 行）提到了此文件，但代码示例仅展示了头文件保护，未说明该文件是否也有 `malloc_trim` 调用需要适配。

**建议**：在实施阶段全面搜索 `malloc_trim` 和 `malloc.h` 的所有使用点，确保适配完整。

**修复优先级**：P3（实施阶段处理）

---

### D-07（驳回）：方案 A 会破坏 LLVM 内部分配器行为

**状态**：✅ 驳回

**理由**：LLVM 的 `BumpPtrAllocator` 等高层分配器内部管理内存块，底层调用 `operator new` 或 `malloc` 获取大块内存，mimalloc 替换的是这个底层调用，不影响 LLVM 的内存管理语义。LLVM 官方文档和社区实践（包括 LLVM 自身的 CMake 配置中已有 mimalloc 支持选项）均证明兼容性良好。设计文档对此的分析（04-风险评估 R-04）是正确的。

---

### D-08（驳回）：Sanitizer 互斥逻辑不完整

**状态**：✅ 驳回

**理由**：设计文档的 CMake 互斥检测覆盖了 `CANGJIE_SANITIZER_SUPPORT_ENABLED`、`CANGJIE_ENABLE_ASAN_COV`、`CANGJIE_ENABLE_COMPILER_TSAN` 三个变量，与根 CMakeLists.txt 中实际定义的 Sanitizer 变量完全对应（第 111-125 行）。逻辑完整，无遗漏。

## 六、关键决策记录（ADR 格式）

### ADR-001：选择方案 A（全局链接层替换）作为主方案

**状态**：批准（有条件）
**日期**：2026-03-03

**背景**：需要为仓颉编译器引入高性能内存分配器，提升编译速度。

**决策**：采用方案 A（全局链接层替换）作为 Linux/macOS 主方案，方案 B（new/delete 替换）作为 Windows 备选。

**理由**：
- 方案 A 覆盖所有分配路径（包括 LLVM 内部），性能收益最大化
- 代码侵入性最低，主要变更在 CMake 配置层
- 完全可逆，一个 CMake 标志即可回滚
- 与现有 `cmake/optional/CangjieCCache.cmake` 模式一致，符合项目惯例

**后果**：
- 正面：零业务代码修改，维护成本低
- 负面：Windows 平台需要额外处理（已有方案 B 兜底）
- 需要：mimalloc 源码纳入 third_party 管理

---

### ADR-002：CANGJIE_USE_MIMALLOC 默认值策略

**状态**：批准
**日期**：2026-03-03

**决策**：初始默认值为 `OFF`，经过 4 周验证（含实测性能数据）后，由团队决策是否切换为默认 `ON`。

**理由**：
- 渐进式启用降低风险
- 默认 OFF 不影响现有用户的构建流程
- 实测数据是切换默认值的必要条件（当前估算数据不足以支撑决策）

---

### ADR-003：Sanitizer 与 mimalloc 互斥策略

**状态**：批准
**日期**：2026-03-03

**决策**：在 CMake 配置阶段自动检测 Sanitizer 选项，发现冲突时自动禁用 mimalloc 并输出 WARNING，不报 FATAL_ERROR。

**理由**：
- 自动处理优于手动配置，降低用户认知负担
- WARNING 而非 FATAL_ERROR 保持构建流程连续性
- 与现有 Sanitizer 变量体系（`CANGJIE_SANITIZER_SUPPORT_ENABLED` 等）完全兼容

---

### ADR-004：mimalloc 版本锁定策略

**状态**：批准
**日期**：2026-03-03

**决策**：锁定 mimalloc v2.1.7，以 git submodule 方式管理，指向具体 commit hash 而非仅 tag。

**理由**：
- v2.1.7 是当前稳定版本，Microsoft 维护，MIT 许可证与 Apache-2.0 兼容
- Commit hash 锁定防止供应链攻击（tag 可被重新指向）
- Submodule 方式支持离线构建，符合企业内网环境需求
