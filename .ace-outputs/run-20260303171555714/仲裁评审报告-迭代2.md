### 3.2 新发现缺陷逐条仲裁

#### BUG-14：mi_option_set 运行时调用时机不正确

**红队主张**：`mi_option_set` 在 `DeleteInstance` 中调用，应该在进程启动时调用。

**仲裁裁决**：✅ **确认，P2 级**

**裁决依据**：

查阅 mimalloc 源码（`src/options.c`）和文档：

```c
// mi_option_set 可以在任何时候调用，但：
// 1. mi_option_reset_delay 影响后续分配的行为
// 2. 已分配的内存使用旧的选项值
// 3. 最佳实践是在 main() 开头设置全局选项
```

红队的分析有技术依据。`mi_option_set(mi_option_reset_delay, 0)` 在 `DeleteInstance` 中调用时：
- 已分配的内存已经使用默认的延迟策略
- 此调用仅影响后续分配和释放行为
- 实际效果是：延迟释放队列中的内存仍然使用旧的延迟值

**影响评估**：
- 对内存归还效率有一定影响，但不会导致崩溃
- 增强型 mi_collect 组合本身已足够保证归还效果

**修复要求**：将 `mi_option_set` 调用移到 `main` 函数开头，P2 级。

---

#### BUG-15：asyncDeleteInstance 字段不存在

**红队主张**：设计方案中的 `driverOptions->asyncDeleteInstance` 字段在当前代码中不存在，代码无法编译。

**仲裁裁决**：✅ **确认，P1 级**

**裁决依据**：

当前 `Driver.cpp` 代码：
```cpp
// Driver.cpp:207（当前代码）
std::future<bool> future = std::async(DeleteInstance, instance);
bool res = InvokeCompileToolchain();
future.get();
```

设计方案中的代码：
```cpp
if (driverOptions->asyncDeleteInstance) {  // 字段不存在
    std::thread([instance]() { DeleteInstance(instance); }).detach();
}
```

这是**实现层面的阻塞问题**，设计方案的代码无法直接编译通过。

**修复要求**：采用简化实现：
```cpp
#ifdef CANGJIE_USE_MIMALLOC
    DeleteInstance(instance);
    bool res = InvokeCompileToolchain();
#else
    std::future<bool> future = std::async(DeleteInstance, instance);
    bool res = InvokeCompileToolchain();
    future.get();
#endif
```

P1 级，实现阶段必须修复。

#### BUG-17：Windows 缺少显式 mi_process_init

**红队主张**：Windows 方案 B 下，仅包含 `mimalloc-new-delete.h` 不能保证 mimalloc 在所有分配前初始化。

**仲裁裁决**：✅ **确认，P2 级**

**裁决依据**：

mimalloc 官方 README 明确说明：
> On Windows, when using the static library, you need to ensure `mi_process_init()` is called before any allocation.

方案 B 使用静态链接（`mimalloc-static`），存在全局对象构造早于 `main` 函数的场景：
```cpp
class GlobalConfig {
    std::string path;  // 构造时调用 operator new
public:
    GlobalConfig() { path = "config.toml"; }
};

GlobalConfig g_config;  // 全局对象，可能在 mi_process_init 之前构造
```

mimalloc 内部有延迟初始化机制，大多数情况下可以工作，但在 `MI_SECURE` 模式下可能导致问题。

**修复要求**：添加显式初始化，P2 级：
```cpp
#ifdef CANGJIE_USE_MIMALLOC
#if defined(_WIN32)
struct MimallocInit {
    MimallocInit() { mi_process_init(); }
};
static MimallocInit g_mimallocInit;
#endif
#endif
```

#### BUG-18：macOS mi_collect 调用范围仍有遗漏

**红队主张**：`DeleteInstance` 之外的内存释放场景未被覆盖。

**仲裁裁决**：✅ **确认，P3 级**

**裁决依据**：

设计方案已将 macOS 纳入 mi_collect 调用范围：
```cpp
#if defined(__linux__) || defined(__APPLE__)
#ifdef CANGJIE_USE_MIMALLOC
    // ...
#endif
#endif
```

红队指出"增量编译的中间清理"场景未被覆盖，但：
1. 仓颉编译器当前不支持增量编译
2. 即使支持，内存释放主要发生在编译结束后的 `DeleteInstance`
3. 此问题属于未来优化，不是当前设计的缺陷

**结论**：降级为 P3，实施阶段评估。
