## 缺陷确认/驳回列表

### ✅ 确认（P0 级，阻塞合并）

**BUG-01：`mi_collect(true)` 与 `malloc_trim(0)` 语义不等价** — **确认，P0**

蓝队"语义等价"的表述是**事实错误**，非设计选择。`malloc_trim(0)` 通过 `sbrk/madvise` 立即归还堆顶内存；`mi_collect(true)` 仅收集延迟释放队列，segment 归还依赖整块空闲，大型项目编译后归还率可降低 60-80%。CI 连续编译场景 OOM 风险真实存在。

修复：采用 `mi_collect + mi_option_set(reset_delay=0) + mi_heap_collect` 组合，或改为同步调用 `DeleteInstance`。

**BUG-02：异步 `DeleteInstance` + `mi_collect` 竞态** — **确认，P0**

`mi_collect(true)` 的"跨线程收集"会扫描所有线程的 free-list，与主线程 LLVM 后端分配存在 TOCTOU 竞态窗口。mimalloc 官方文档明确建议避免在多线程场景下跨线程调用 `mi_collect`。与 BUG-01 同步修复（同步调用方案）。

---

### ✅ 确认（P1 级，合并前修复）

**BUG-03/13：Sanitizer 互斥逻辑不完整** — **确认，P1，前序评审"驳回"结论撤销**

`CANGJIE_ENABLE_ASAN`（编译器自身 ASan）与 `CANGJIE_SANITIZER_SUPPORT_ENABLED`（运行时支持）是不同的 CMake 变量。`CANGJIE_ENABLE_HWASAN` 在 OHOS/ARM 平台与 mimalloc 的 segment 地址标记机制存在 ARM MTE 标签位冲突。LeakSanitizer 通过编译标志传递，需扫描 `CMAKE_CXX_FLAGS`。前序评审报告对此问题的"驳回"结论**撤销**。

**BUG-04：`cangjie-lsp-share` 双 mimalloc 实例** — **确认，P1**

动态库静态链接 mimalloc 是经典的双实例问题：主程序实例 #1 分配的内存被 lsp-share 实例 #2 释放，必然崩溃。修复：移除 `cangjie-lsp-share` 的 mimalloc 链接，依赖主程序全局符号覆盖。

**BUG-05：Windows MinGW 初始化顺序未定义** — **确认，P1**

mimalloc 官方 README 明确说明静态库场景需显式调用 `mi_process_init()`。MinGW 全静态链接下构造函数顺序不保证在 CRT 之后。Windows 统一使用方案 B 是正确规避策略。

**BUG-08：`ExternalProject` 离线构建失败** — **确认，提升为 P1**

仓颉编译器 CI/CD 为内网隔离环境，`ExternalProject` 网络下载是**确定失败**而非"可能失败"。强制 Git submodule 是正确修复。
