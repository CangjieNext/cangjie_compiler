## 三、缺陷逐条仲裁

### 3.1 Critical 级缺陷

---

#### BUG-01：`mi_collect(true)` 与 `malloc_trim(0)` 语义不等价

**红队主张**：两者语义不等价，mimalloc 内存归还依赖 segment 完全空闲，效率降低 60-80%，CI 环境有 OOM 风险。

**仲裁裁决**：✅ **确认，P0 级，必须修复**

**裁决依据**：

红队的技术分析准确。查阅 mimalloc 源码（`src/segment.c`）可确认：

```
malloc_trim(0)：
  - glibc 实现：调用 sbrk(-n) 或 madvise(MADV_DONTNEED)
  - 立即归还所有可归还的堆顶内存
  - 时间复杂度：O(1)，同步完成

mi_collect(true)：
  - 收集所有线程的延迟释放队列（thread-local free lists）
  - 仅当整个 segment（默认 4MB）完全空闲时才归还给 OS
  - 大型项目编译后，segment 内通常有残留对象，无法归还
  - 实际归还率取决于内存碎片程度
```

蓝队设计文档中"语义等价"的表述是**错误的技术声明**，不是设计选择问题，是事实错误。

**修复要求**：采用红队建议的方案 1（`mi_collect + mi_option_set + mi_heap_collect`）或方案 2（同步调用），二选一，Week 1 内完成。

---

#### BUG-02：异步 `DeleteInstance` + `mi_collect` 存在竞态窗口

**红队主张**：`Driver.cpp:207` 异步线程调用 `mi_collect(true)` 与主线程 LLVM 后端分配存在竞争，可能导致内存损坏。

**仲裁裁决**：✅ **确认，P0 级，必须修复**

**裁决依据**：

查阅 mimalloc 文档（`include/mimalloc.h` 注释）：

> `mi_collect(force)`: Collect memory in all heaps. If `force` is true, all thread-local free lists are collected.

关键问题在于 `mi_collect(true)` 的"跨线程收集"行为：当异步线程 A 调用 `mi_collect(true)` 时，它会尝试收集**所有线程**（包括主线程）的延迟释放队列。如果主线程此时正在 `InvokeCompileToolchain` 中进行 LLVM 后端分配，存在以下竞态：

```
线程 A：mi_collect → 扫描主线程 free-list → 归还 segment
主线程：LLVM 分配 → 访问刚被归还的 segment → 崩溃
```

mimalloc 内部使用原子操作保护 free-list，但 segment 归还路径存在 TOCTOU 窗口。这是一个**已知的 mimalloc 使用模式限制**，官方文档建议在多线程场景下避免跨线程调用 `mi_collect`。

**修复要求**：采用方案 2（`#ifdef CANGJIE_USE_MIMALLOC` 下同步调用 `DeleteInstance`），与 BUG-01 同步修复，Week 1 内完成。

### 3.2 High 级缺陷

---

#### BUG-03：Sanitizer 互斥逻辑遗漏 HWASan 和 LeakSanitizer

**红队主张**：蓝队 CMake 互斥逻辑遗漏了 `CANGJIE_ENABLE_ASAN`、`CANGJIE_ENABLE_HWASAN` 和 LeakSanitizer，前序评审报告的"驳回"结论有误。

**仲裁裁决**：✅ **确认，P1 级，合并前修复**

**裁决依据**：

前序评审报告（`评审报告-最终裁决.md`）对此问题的处理不完整。蓝队设计文档仅检测了 `CANGJIE_SANITIZER_SUPPORT_ENABLED` 和 `CANGJIE_ENABLE_COMPILER_TSAN`，但：

1. `CANGJIE_ENABLE_ASAN`：仓颉编译器自身的 ASan 构建标志，与 `CANGJIE_SANITIZER_SUPPORT_ENABLED`（运行时 Sanitizer 支持）是不同的 CMake 变量
2. `CANGJIE_ENABLE_HWASAN`：OHOS 平台专用，HWASan 与 mimalloc 的 segment 地址标记机制冲突（ARM MTE 标签位冲突）
3. LeakSanitizer：通过 `-fsanitize=leak` 启用，不通过 CMake 变量传递，需要检测编译标志

**前序评审报告的"驳回"结论撤销**，红队此项发现成立。

---

#### BUG-04：`cangjie-lsp-share` 双 mimalloc 实例导致堆状态分裂

**红队主张**：`cangjie-lsp-share` 独立链接 mimalloc 静态库，与主进程形成双实例，堆状态分裂。

**仲裁裁决**：✅ **确认，P1 级，合并前修复**

**裁决依据**：

这是静态库链接的经典问题。当 `cangjie-lsp-share.so` 静态链接 mimalloc 时：

```
进程内存布局：
  cjc（主程序）→ mimalloc 实例 #1（全局符号覆盖）
  cangjie-lsp-share.so → mimalloc 实例 #2（独立静态链接）

问题：
  - 主程序用实例 #1 分配的内存，被 lsp-share 用实例 #2 释放 → 崩溃
  - 两个实例各自维护 segment 池，内存使用量翻倍
  - mi_collect 只收集当前实例的堆，统计数据失真
```

迭代改进分析（`架构迭代改进分析-迭代1.md`）已提供正确修复方案：移除 `cangjie-lsp-share` 的 mimalloc 链接，依赖主程序的全局符号覆盖。**此修复方案正确，采纳。**

---

#### BUG-05：Windows MinGW 全静态链接下 mimalloc 初始化顺序未定义

**红队主张**：Windows MinGW 全静态链接场景下，mimalloc 的 `mi_process_init` 可能在 CRT 初始化之前执行，导致启动崩溃。

**仲裁裁决**：✅ **确认，P1 级，合并前修复**

**裁决依据**：

Windows 静态链接的初始化顺序问题是已知的 C++ 静态初始化顺序问题（SIOF）的变体。mimalloc 使用 `__attribute__((constructor))` 或 `DllMain` 进行初始化，在 MinGW 全静态链接场景下，构造函数执行顺序依赖链接器，不保证在 CRT 之后。

mimalloc 官方 README 明确指出：

> On Windows, when using the static library, you need to ensure `mi_process_init()` is called before any allocation.

迭代改进分析建议 Windows 统一使用方案 B（new/delete 替换），这是正确的规避策略，**采纳。**

#### BUG-13：`CANGJIE_ENABLE_ASAN` 变量未纳入互斥检测

**仲裁裁决**：✅ **确认，与 BUG-03 合并处理，P1 级**

此问题是 BUG-03 的子集，合并修复。

### 3.3 Medium 级缺陷

---

#### BUG-06：`FrontendTool.cpp` 的 `malloc.h` 包含未适配

**红队主张**：启用 mimalloc 后，`FrontendTool.cpp` 中的 `#include <malloc.h>` 可能与 mimalloc 符号覆盖冲突。

**仲裁裁决**：⚠️ **部分确认，P2 级，默认启用前修复**

**裁决依据**：

在方案 A（全局符号覆盖）下，`malloc.h` 的包含本身不会冲突，因为 mimalloc 通过链接器符号覆盖，不修改头文件。但如果 `FrontendTool.cpp` 中有 `malloc_trim` 等 glibc 扩展函数的直接调用，则需要适配。

红队的担忧有一定依据，但严重程度被高估。降级为 P2，在默认启用前完成适配即可。

---

#### BUG-07：macOS 平台 `mi_collect` 调用范围不足

**红队主张**：设计文档中 `mi_collect` 仅在 Linux 下调用（`#if defined(__linux__) && !defined(__ohos__)`），macOS 未覆盖。

**仲裁裁决**：✅ **确认，P2 级**

**裁决依据**：

macOS 的内存管理机制（`malloc_zone`）与 Linux 不同，但 mimalloc 在 macOS 上同样支持 `mi_collect`。遗漏 macOS 的 `mi_collect` 调用会导致 macOS 上内存归还效率低于预期，但不会导致崩溃。P2 级，默认启用前修复。

---

#### BUG-08：`ExternalProject` 自动下载在离线/内网环境失败

**红队主张**：使用 `ExternalProject_Add` 自动下载 mimalloc 会在 CI/CD 内网环境失败。

**仲裁裁决**：✅ **确认，P1 级**

**裁决依据**：

仓颉编译器作为华为内部项目，CI/CD 环境通常为内网隔离环境，`ExternalProject` 的网络下载在此场景下**必然失败**。这不是"可能失败"而是"确定失败"。

迭代改进分析已提供正确修复：强制使用 Git submodule，移除 `ExternalProject` 自动下载。**此修复方案正确，采纳，提升为 P1 级。**

---

#### BUG-09：`MI_SECURE` 在 Debug 构建下引入性能开销未量化

**仲裁裁决**：⚠️ **部分确认，P2 级**

`MI_SECURE` 模式引入约 10-20% 的性能开销是已知的，但这是 Debug 构建的预期行为。主要问题是文档未说明，需要在 CMake 配置中添加说明，而非修复缺陷。

---

#### BUG-10：方案 B 的 Windows 策略无法覆盖 LLVM 动态库分配

**红队主张**：方案 B 仅替换 `operator new/delete`，LLVM 动态库内部的 `malloc` 调用不受影响。

**仲裁裁决**：✅ **确认，P3 级**

**裁决依据**：

这是方案 B 的**已知设计限制**，蓝队文档中已说明"保留 LLVM 使用系统分配器"。这不是缺陷，而是方案 B 的设计取舍。性能收益 5-8% 的估算已考虑此限制。

降级为 P3，在文档中明确说明即可。

## 六、关键决策记录（ADR 格式）

### ADR-001：mi_collect 调用策略

**状态**：决策中（待修复后确认）
**背景**：`malloc_trim(0)` 与 `mi_collect(true)` 语义不等价，需要选择替代策略
**决策**：采用同步调用 + `mi_collect + mi_option_set(reset_delay=0)` 组合
**理由**：同步调用消除竞态，`reset_delay=0` 最大化内存归还效率
**后果**：编译时间可能略有增加（同步等待析构），但消除了 OOM 和竞态风险

### ADR-002：Windows 平台统一使用方案 B

**状态**：已决策
**背景**：Windows MinGW 全静态链接下方案 A 存在初始化顺序问题
**决策**：Windows 平台统一使用方案 B（new/delete 替换），不使用方案 A
**理由**：方案 B 在 Windows 上更安全，性能收益 5-8% 仍有价值
**后果**：Windows 性能收益低于 Linux/macOS（5-8% vs 10-15%），文档需说明

### ADR-003：cangjie-lsp-share 不独立链接 mimalloc

**状态**：已决策
**背景**：独立链接导致双实例问题
**决策**：`cangjie-lsp-share` 不链接 mimalloc，依赖主程序全局符号覆盖
**理由**：动态库应依赖进程级的分配器替换，而非独立链接
**后果**：`cangjie-lsp-share` 作为独立进程运行时无 mimalloc 加速（可接受）

### ADR-004：mimalloc 版本管理使用 Git submodule

**状态**：已决策
**背景**：`ExternalProject` 在内网 CI 环境必然失败
**决策**：使用 Git submodule 管理 mimalloc 源码，锁定版本 2.1.7
**理由**：离线构建是内网 CI 的硬性要求
**后果**：仓库体积增加约 2MB，版本升级需要手动更新 submodule

### ADR-005：Sanitizer 互斥逻辑覆盖范围

**状态**：已决策（修复 BUG-03/13 后生效）
**背景**：原有互斥逻辑不完整，遗漏多个 Sanitizer 变体
**决策**：检测所有已知 Sanitizer CMake 变量 + 编译标志扫描
**理由**：任何 Sanitizer 与 mimalloc 共存都可能导致误报或崩溃
**后果**：Sanitizer 构建下无 mimalloc 加速，这是预期行为
