# 需求分析与约束梳理

## 1. 需求背景

### 1.1 核心需求
使用 mimalloc 替代普通 malloc 作为默认的内存分配器，以提升仓颉编译器的性能。

### 1.2 业务价值
- **编译性能提升**：编译器是内存密集型应用，频繁进行 AST 节点、符号表、IR 节点的分配和释放
- **多线程性能优化**：编译器支持并行编译和增量编译，mimalloc 的线程局部缓存可显著降低锁竞争
- **内存碎片优化**：长时间运行的编译任务（如大型项目构建）可减少内存碎片
- **可预测的性能**：mimalloc 提供更稳定的分配延迟，有利于编译时间的可预测性

### 1.3 mimalloc 技术特性
- **高性能**：针对现代多核处理器优化，线程局部分配无锁
- **低碎片**：使用分页和大小类（size classes）机制
- **安全性**：支持安全模式，提供 use-after-free 检测
- **兼容性**：完全兼容标准 malloc/free API
- **跨平台**：支持 Linux、Windows、macOS

## 2. 项目架构分析

### 2.1 编译器架构概览
```
仓颉编译器架构：
├── 前端（Frontend）
│   ├── Lexer（词法分析）
│   ├── Parser（语法分析）→ AST 构建
│   ├── Semantic（语义分析）→ 符号表、类型检查
│   ├── Macro（宏展开）
│   ├── CHIR（中间表示）→ IR 节点构建
│   └── CodeGen（代码生成）→ LLVM IR
├── 后端（Backend）
│   └── LLVM 工具链（opt、llc、ld）
└── 工具链
    ├── cjc（编译器主程序）
    ├── LSPMacroServer（语言服务器）
    └── chir-dis（CHIR 反汇编器）
```

### 2.2 内存分配热点识别

#### 2.2.1 AST 构建阶段
- **位置**：`src/AST/`、`src/Parse/`
- **特征**：大量小对象分配（AST 节点平均 64-256 字节）
- **频率**：每个源代码 token 对应 1-3 个 AST 节点
- **生命周期**：整个编译过程（直到代码生成完成）

#### 2.2.2 符号表与类型系统
- **位置**：`src/Sema/`
- **特征**：中等大小对象（符号表条目、类型对象）
- **频率**：每个标识符、类型声明各一次
- **生命周期**：编译全过程

#### 2.2.3 CHIR 中间表示
- **位置**：`src/CHIR/IR/`
- **特征**：大量 IR 节点分配（Expression、Value、Type）
- **频率**：AST 节点数的 1.5-3 倍（展开后）
- **生命周期**：从 AST 转换到代码生成

#### 2.2.4 自定义 Arena 分配器
- **位置**：`include/cangjie/CHIR/Interpreter/InterpreterArena.h`
- **特征**：已有自定义 Arena 实现（用于解释器）
- **策略**：Bucket-based allocation（2048 buckets × 2048 objects）

### 2.3 现有内存管理策略

#### 2.3.1 标准分配器使用
- **C++ new/delete**：AST 节点、CHIR 节点
- **std::vector/std::map**：容器类使用默认 std::allocator
- **LLVM 分配器**：LLVM 组件使用 LLVM 内部分配器

#### 2.3.2 第三方依赖
- **boundscheck**：安全函数库（已集成）
- **LLVM**：使用 LLVM 内部内存管理
- **flatbuffers**：序列化库

## 3. 技术约束与挑战

### 3.1 编译器特定约束

#### 3.1.1 多平台支持
- **必须支持**：Linux x86-64/AArch64、Windows x86-64、macOS x86/ARM64
- **开发中**：OpenHarmony（OHOS）
- **交叉编译**：支持 ohos-aarch64 目标

#### 3.1.2 构建系统
- **CMake 3.16.5+**：现有构建系统
- **外部项目**：LLVM 作为 ExternalProject 构建
- **多配置**：Debug、Release、RelWithDebInfo、MinSizeRel

#### 3.1.3 链接策略
- **静态链接**：编译器核心（cjc）
- **动态链接**：LSP 库（cangjie-lsp-share）
- **混合链接**：Windows Release 使用静态链接

### 3.2 性能与诊断约束

#### 3.2.1 性能分析支持
- **编译时性能分析**：`--profile-compile-time`（需 CANGJIE_WRITE_PROFILE）
- **内存分析**：`--profile-compile-memory`
- **约束**：mimalloc 集成不能破坏现有性能分析工具

#### 3.2.2 Sanitizer 支持
- **ASan**：地址消毒器（CANGJIE_ASAN_SUPPORT）
- **TSan**：线程消毒器（CANGJIE_TSAN_SUPPORT）
- **HWASan**：硬件辅助地址消毒器（CANGJIE_HWASAN_SUPPORT）
- **约束**：mimalloc 必须与 Sanitizer 兼容或可选择性禁用

#### 3.2.3 调试支持
- **符号信息**：Debug 构建需保留完整符号
- **内存泄漏检测**：需支持 Valgrind/LeakSanitizer
- **约束**：mimalloc 不能干扰调试工具

### 3.3 向后兼容性约束

#### 3.3.1 ABI 兼容性
- **标准库接口**：cangjie-ast-support 库对外接口不变
- **LSP 接口**：cangjie-lsp-share 动态库 ABI 稳定
- **FFI 接口**：Java/ObjC FFI 不受影响

#### 3.3.2 构建兼容性
- **现有构建脚本**：build.py 无需修改
- **IDE 集成**：不影响现有 IDE 插件
- **SDK 集成**：integration_build 流程保持不变

### 3.4 安全性约束

#### 3.4.1 内存安全
- **boundscheck 集成**：必须保持现有安全检查
- **栈保护**：CANGJIE_DISABLE_STACK_GROW_FEATURE 配置保持
- **安全编译选项**：现有 -fstack-protector 等选项保持

#### 3.4.2 供应链安全
- **第三方审计**：mimalloc 需通过安全审计
- **许可证兼容**：MIT 许可证与 Apache-2.0 兼容
- **依赖管理**：作为 third_party 子模块管理

## 4. 性能基线与目标

### 4.1 性能基线（估算）
- **小型项目**（< 1000 行）：编译时间 < 1s，内存峰值 < 50MB
- **中型项目**（1000-10000 行）：编译时间 1-10s，内存峰值 50-500MB
- **大型项目**（> 10000 行）：编译时间 > 10s，内存峰值 > 500MB

### 4.2 性能提升目标
- **编译时间**：提升 5-15%（内存分配占编译时间的 10-30%）
- **内存峰值**：降低 5-10%（减少碎片）
- **多线程扩展性**：并行编译效率提升 10-20%
- **长时间运行**：大型项目构建稳定性提升

### 4.3 性能回归红线
- **不可接受**：任何场景性能下降 > 5%
- **需优化**：特定场景性能下降 2-5%
- **可接受**：性能波动 < 2%（测量误差范围内）

## 5. 风险识别

### 5.1 技术风险
- **Sanitizer 冲突**：mimalloc 可能与 ASan/TSan 不兼容
- **调试困难**：自定义分配器可能干扰内存调试工具
- **性能回归**：特定工作负载可能不适合 mimalloc
- **平台差异**：不同平台 mimalloc 性能表现差异

### 5.2 集成风险
- **构建复杂度**：增加构建依赖和配置选项
- **测试覆盖**：需大量测试验证兼容性
- **回滚成本**：如需回滚，影响范围较大

### 5.3 维护风险
- **依赖更新**：mimalloc 版本更新需跟进
- **问题定位**：内存问题定位难度增加
- **知识传承**：团队需掌握 mimalloc 原理
