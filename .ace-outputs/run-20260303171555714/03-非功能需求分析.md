## 1. 编译性能分析

### 1.1 性能基线建立

#### 1.1.1 测试用例设计

**小型项目（< 1000 行）**
```
项目：HelloWorld + 基础库
文件数：5-10 个 .cj 文件
代码行数：500-1000 行
编译时间基线：0.5-1.5s
内存峰值基线：30-50MB
```

**中型项目（1000-10000 行）**
```
项目：标准库子集 + 应用代码
文件数：50-100 个 .cj 文件
代码行数：5000-10000 行
编译时间基线：5-15s
内存峰值基线：200-500MB
```

**大型项目（> 10000 行）**
```
项目：完整应用 + 多模块
文件数：200+ 个 .cj 文件
代码行数：20000+ 行
编译时间基线：30-120s
内存峰值基线：800MB-2GB
```

#### 1.1.2 性能指标定义

**编译时间分解**
```
总编译时间 = 词法分析 + 语法分析 + 语义分析 + CHIR生成 + 代码生成 + 链接
                (5%)      (10%)      (25%)      (20%)      (30%)    (10%)

内存分配时间占比估算：
- 词法分析：20%（Token 对象分配）
- 语法分析：40%（AST 节点分配）
- 语义分析：35%（符号表、类型对象）
- CHIR生成：45%（IR 节点分配）
- 代码生成：25%（LLVM IR 构建）

加权平均：内存分配占总编译时间的 ~30%
```

**内存使用特征**
```
峰值内存 = AST内存 + 符号表内存 + CHIR内存 + LLVM内存 + 临时对象
           (25%)     (15%)       (30%)     (20%)     (10%)

内存碎片率估算：
- 系统分配器（glibc malloc）：15-25%
- mimalloc 预期：5-10%
- 潜在内存节省：10-15%
```

### 1.2 性能提升预期

```

提升倍数：3-5x

编译时间提升计算：
假设内存分配占 30% 编译时间
分配加速 4x → 总时间减少 30% × (1 - 1/4) = 22.5%
考虑其他开销，实际提升：10-15%
```

```
并行编译场景（4核心）：
```

### 2.2 调试工具兼容性

#### 2.2.1 GDB/LLDB 调试

**潜在问题**：
- mimalloc 的内存布局可能影响内存查看
- 自定义分配器可能干扰内存断点

**验证方案**：
```bash
# 测试调试器功能

```

#### 2.2.2 Valgrind 内存检测

**已知问题**：Valgrind 默认不识别 mimalloc

**解决方案**：
```bash
# 方式1：使用 Valgrind 兼容模式
valgrind --soname-synonyms=somalloc=NONE cjc source.cj

# 方式2：编译时禁用 mimalloc
cmake -DCANGJIE_USE_MIMALLOC=OFF ..
valgrind --leak-check=full cjc source.cj
```

#### 2.2.3 AddressSanitizer (ASan)

**冲突分析**：
- ASan 需要拦截 malloc/free 进行内存标记
- mimalloc 全局替换会与 ASan 冲突

**解决方案**：
```cmake
# CMakeLists.txt 自动互斥
if(CANGJIE_USE_MIMALLOC AND CANGJIE_SANITIZER_SUPPORT_ENABLED)
    message(WARNING "Disabling mimalloc due to sanitizer conflict")
    set(CANGJIE_USE_MIMALLOC OFF)
endif()
```

**验证方案**：
```bash
# ASan 构建应该自动禁用 mimalloc
cmake -DCANGJIE_ASAN_SUPPORT=ON -DCANGJIE_USE_MIMALLOC=ON ..
# 预期：CMake 警告并禁用 mimalloc

# 验证 ASan 功能正常
./cjc use-after-free.cj  # 应该检测到错误
```

#### 2.2.4 ThreadSanitizer (TSan)

**冲突分析**：
- TSan 需要拦截内存操作检测数据竞争
- mimalloc 的线程局部缓存可能干扰 TSan

**解决方案**：同 ASan，自动互斥

```cpp
int64_t GetCurrentMemoryUsage()
{

    size_t elapsed_ms, user_ms, system_ms;
```

## 3. 增量编译支持

### 3.1 增量编译架构

```
增量编译流程：
1. 读取缓存的 AST（序列化）
2. 检测变更文件
3. 重新编译变更部分
4. 合并 CHIR
5. 增量代码生成
```

### 3.2 内存管理挑战

**问题**：
- 缓存的 AST 反序列化后需要分配内存
- 增量编译可能多次分配/释放同一数据结构
- 内存碎片在长时间 IDE 会话中累积

**mimalloc 优势**：
- 线程局部缓存减少碎片
- `mi_collect()` 可以主动归还内存
- 隔离堆（`mi_heap_t`）支持批量释放

### 3.3 适配方案

```cpp
// src/IncrementalCompilation/IncrementalCompiler.cpp
void IncrementalCompiler::CleanupAfterCompilation()
{
    // 释放本次编译的临时数据
    tempData.clear();

#ifdef CANGJIE_USE_MIMALLOC
    // 主动归还未使用内存给 OS
    mi_collect(true);
#elif defined(__linux__) && !defined(__ohos__)
    malloc_trim(0);
#endif
}
```

### 3.4 测试方案

```bash
# 增量编译性能测试
# 1. 全量编译
cjc --build project/

# 2. 修改单个文件
echo "// comment" >> project/main.cj

# 3. 增量编译（测量时间和内存）
cjc --build project/ --profile-compile-time --profile-compile-memory

# 4. 重复步骤2-3 多次，验证内存不泄漏
for i in {1..100}; do
    echo "// iteration $i" >> project/main.cj
    cjc --build project/
done
# 验证内存峰值稳定
```

## 4. 可扩展性分析

### 4.1 并行编译支持

#### 4.1.1 现有并行机制

仓颉编译器支持文件级并行编译：
```
编译器驱动（Driver）
  ├── 线程1：编译 file1.cj
  ├── 线程2：编译 file2.cj
  ├── 线程3：编译 file3.cj
  └── 线程4：编译 file4.cj
```

#### 4.1.2 内存分配竞争

**系统分配器问题**：
```
glibc malloc 使用全局 arena 锁：
- 2-8 个 arena（取决于核心数）
- 线程竞争同一 arena 时需要加锁
- 锁竞争导致并行效率下降
```

**mimalloc 优势**：
```
每个线程独立的内存缓存：
- 线程局部 heap（thread-local）
- 小对象分配完全无锁
- 大对象使用细粒度锁
- 并行扩展性接近线性
```

#### 4.1.3 性能测试

```bash
# 单线程基线
time cjc --jobs=1 project/

# 多线程测试
time cjc --jobs=2 project/
time cjc --jobs=4 project/
time cjc --jobs=8 project/

# 计算并行效率
Efficiency = (T1 / (Tn * n)) * 100%
目标：4核心效率 > 80%（mimalloc）
      vs 60-70%（系统分配器）
```

### 4.2 内存扩展性

#### 4.2.1 大型项目支持

**场景**：编译 10万+ 行代码项目
- AST 节点数：100万+
- 符号表条目：10万+
- CHIR IR 节点：300万+

**内存需求**：
```
估算：
- AST：100万节点 × 128字节 = 128MB
- 符号表：10万条目 × 256字节 = 25MB
- CHIR：300万节点 × 64字节 = 192MB
- LLVM IR：约 200MB
- 总计：~550MB（不含碎片）

加上碎片：
- 系统分配器：550MB × 1.2 = 660MB
- mimalloc：550MB × 1.08 = 594MB
- 节省：66MB（10%）
```

#### 4.2.2 内存峰值控制

**策略**：
```cpp
// 编译大型项目时分批处理
for (auto& module : modules) {
    CompileModule(module);

    // 每个模块编译完成后释放临时内存
#ifdef CANGJIE_USE_MIMALLOC
    mi_collect(false);  // 不归还给 OS，保留缓存
#endif
}

// 所有模块完成后归还内存
#ifdef CANGJIE_USE_MIMALLOC
mi_collect(true);  // 归还给 OS
#endif
```

### 4.3 长时间运行场景

#### 4.3.1 LSP 服务器

**场景**：IDE 后台 LSP 服务长时间运行
- 持续响应代码补全、诊断请求
- 内存不能无限增长
- 需要定期清理

**mimalloc 优势**：
```cpp
// src/main-macrosrv.cpp（LSPMacroServer）
void LSPServer::OnIdleTimeout()
{

    // 空闲时主动回收内存

#endif
}
```

#### 4.3.2 CI/CD 构建服务器

**场景**：持续集成服务器连续编译多个项目
- 避免内存泄漏累积
- 每次编译后清理

**验证方案**：
