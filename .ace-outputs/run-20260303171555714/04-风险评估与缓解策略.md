## 2. 严重风险详细分析

### R-01：Sanitizer 与 mimalloc 冲突

**风险描述**：
ASan/TSan/HWASan 通过拦截 malloc/free 实现内存检测。mimalloc 全局替换 malloc/free 后，Sanitizer 的拦截机制可能失效，导致：
- ASan 无法检测 use-after-free
- TSan 无法检测数据竞争
- 编译器调试能力下降

**技术根因**：
```
正常流程：
代码 → malloc → [ASan 拦截] → glibc malloc → OS

冲突流程：
代码 → malloc → [mimalloc 覆盖] → mimalloc → OS
                 ↑ ASan 拦截失效
```

**缓解策略**：

**策略1：CMake 自动互斥（主要策略）**
```cmake
# CMakeLists.txt
if(CANGJIE_USE_MIMALLOC)
    # 检查所有 Sanitizer 选项
    if(CANGJIE_SANITIZER_SUPPORT_ENABLED OR
       CANGJIE_ENABLE_ASAN_COV OR
       CANGJIE_ENABLE_COMPILER_TSAN)
        message(WARNING
            "[mimalloc] Automatically disabled: incompatible with sanitizer builds.\n"
            "  To use mimalloc, disable all sanitizer options first.")
        set(CANGJIE_USE_MIMALLOC OFF CACHE BOOL "" FORCE)
    endif()
endif()
```

**策略2：运行时检测（防御性编程）**
```cpp
// src/main.cpp
#ifdef CANGJIE_USE_MIMALLOC
// 运行时检测是否在 Sanitizer 环境中
static bool IsSanitizerActive()
{
    // ASan 会设置环境变量
    const char* asanOpts = getenv("ASAN_OPTIONS");
    const char* tsanOpts = getenv("TSAN_OPTIONS");
    return asanOpts != nullptr || tsanOpts != nullptr;
}

// 如果检测到 Sanitizer，打印警告
if (IsSanitizerActive()) {
    fprintf(stderr,
        "Warning: mimalloc is active but sanitizer environment detected.\n"
        "Memory error detection may be unreliable.\n"
        "Rebuild with -DCANGJIE_USE_MIMALLOC=OFF for sanitizer builds.\n");
}
#endif
```

**验证方案**：
```bash
# 测试1：Sanitizer 构建自动禁用 mimalloc
cmake -DCANGJIE_ASAN_SUPPORT=ON -DCANGJIE_USE_MIMALLOC=ON ..
# 预期：CMake 警告，CANGJIE_USE_MIMALLOC 被设为 OFF

# 测试2：ASan 功能正常（mimalloc 禁用后）
cmake -DCANGJIE_ASAN_SUPPORT=ON ..
./cjc use-after-free.cj  # 应该检测到错误
```

### R-02：Windows 平台兼容性问题

**风险描述**：
Windows 平台的内存分配替换机制与 Linux/macOS 不同：
- Windows 使用 DLL 边界隔离内存
- 不同 DLL 可能使用不同的 CRT（C Runtime）
- 静态链接 mimalloc 可能导致多个分配器共存

**技术根因**：
```
Windows DLL 内存模型：
┌─────────────────────────────────────────┐
│  cjc.exe                                │
│  ├── mimalloc-static（替换 malloc）      │
│  ├── cangjie-lsp.dll                    │
│  │   └── 使用自己的 CRT malloc          │  ← 不同分配器！
│  └── LLVM-15.dll                        │
│      └── 使用自己的 CRT malloc          │  ← 不同分配器！
└─────────────────────────────────────────┘

问题：跨 DLL 边界传递指针时，free 可能调用错误的分配器
```

**缓解策略**：

**策略1：Windows 使用方案 B（推荐）**
```cmake
# Windows 平台使用 operator new/delete 替换，避免 DLL 边界问题
if(WIN32)
    # 仅替换 C++ new/delete，不替换 malloc/free
    # 通过 mimalloc-new-delete.h 实现
    set(CANGJIE_MIMALLOC_STRATEGY "new-delete" CACHE STRING
        "mimalloc integration strategy: global|new-delete")
else()
    set(CANGJIE_MIMALLOC_STRATEGY "global" CACHE STRING
        "mimalloc integration strategy: global|new-delete")
endif()
```

**策略2：使用 mimalloc-redirect（Windows 专用）**
```cmake
if(WIN32 AND CANGJIE_USE_MIMALLOC)
    # mimalloc-redirect.dll 可以重定向所有 DLL 的分配
    install(FILES ${MIMALLOC_REDIRECT_DLL}
            DESTINATION bin)
    message(STATUS "mimalloc-redirect.dll will be installed alongside cjc.exe")
endif()
```

**策略3：Windows Release 静态链接**
```cmake
# Windows Release 已经使用 -static 链接
# 静态链接时 DLL 边界问题不存在
if(WIN32 AND CMAKE_BUILD_TYPE MATCHES Release)
    # 静态链接 mimalloc，安全
    target_link_libraries(cjc PRIVATE mimalloc-static)
endif()
```

**验证方案**：
```powershell
# Windows 测试
cmake -G "Visual Studio 17 2022" -DCANGJIE_USE_MIMALLOC=ON ..
cmake --build . --config Release

# 测试跨 DLL 内存传递
.\cjc.exe test.cj
# 验证无崩溃、无内存错误
```

## 3. 高风险详细分析

### R-03：性能回归（特定场景）

**风险描述**：
mimalloc 在某些特定场景可能不如系统分配器：
- 极小对象（< 8 字节）：mimalloc 有最小分配单元
- 大对象（> 512KB）：直接使用 mmap，与系统分配器相当
- 内存受限环境：mimalloc 预分配可能导致 OOM

**缓解策略**：

**策略1：性能测试门控**
```bash
# CI 中的性能回归检测
./scripts/perf_regression_check.sh \
    --threshold 5 \  # 允许 5% 以内的波动
    --baseline system \
    --compare mimalloc

# 如果任何场景性能下降 > 5%，阻止合并
```

**策略2：分场景配置**
```cmake
# 提供细粒度控制
option(CANGJIE_MIMALLOC_LARGE_OBJECTS
    "Use mimalloc for large object allocation (>512KB)"
    OFF)  # 默认禁用大对象替换

if(CANGJIE_USE_MIMALLOC AND NOT CANGJIE_MIMALLOC_LARGE_OBJECTS)
    # 配置 mimalloc 大对象阈值
    add_compile_definitions(MI_LARGE_OBJ_SIZE_MAX=524288)
endif()
```

**策略3：快速回滚机制**
```bash
# 如果发现性能问题，一键回滚
cmake -DCANGJIE_USE_MIMALLOC=OFF ..
cmake --build .
# 无需修改任何代码
```

### R-04：LLVM 内部分配器冲突

**风险描述**：
LLVM 有自己的内存管理机制（BumpPtrAllocator、SpecificBumpPtrAllocator 等），全局替换 malloc 后可能影响 LLVM 内部行为。

**技术分析**：
```
LLVM 内存管理层次：
1. LLVM 高层分配器（BumpPtrAllocator）
   └── 调用 operator new
       └── 调用 malloc  ← mimalloc 替换点

2. LLVM 直接 malloc 调用
   └── 调用 malloc  ← mimalloc 替换点

影响评估：
- BumpPtrAllocator：不受影响（内部管理内存块）
- 直接 malloc：被 mimalloc 替换，通常是正面影响
- 已知问题：无（LLVM 社区已验证 mimalloc 兼容性）
```

**缓解策略**：

**策略1：LLVM 兼容性验证**
```bash
# 运行 LLVM 相关测试
cd build && ctest -R LLVM

# 验证代码生成正确性
cjc --emit-llvm test.cj -o test.ll
llc test.ll -o test.s
# 对比 mimalloc 和系统分配器的输出
diff test_system.ll test_mimalloc.ll  # 应该完全一致
```

**策略2：方案 B 作为备选**
如果发现 LLVM 兼容性问题，切换到方案 B（仅替换 C++ new/delete），保留 LLVM 使用系统分配器。

### R-08：供应链安全风险

**风险描述**：
引入第三方库存在供应链攻击风险：
- Git 仓库被篡改
- 恶意代码注入
- 依赖版本漂移

**缓解策略**：

**策略1：版本锁定**
```cmake
# 锁定到特定 commit hash，而非 tag
ExternalProject_Add(
    mimalloc-project
    GIT_REPOSITORY https://github.com/microsoft/mimalloc.git
    GIT_TAG        v2.1.7
    # 额外锁定 commit hash
    # GIT_HASH     abc123...（实际 hash）
)
```

**策略2：本地镜像**
```bash
# 将 mimalloc 源码镜像到内部 Git 服务器
git clone https://github.com/microsoft/mimalloc.git
# 推送到内部服务器
git remote add internal https://internal.gitserver/mimalloc.git
git push internal

# CMakeLists.txt 使用内部镜像
set(MIMALLOC_REPO "https://internal.gitserver/mimalloc.git")
```

**策略3：代码审计**
```bash
# 审计 mimalloc 源码
# 重点关注：
# 1. 无网络访问
# 2. 无文件系统写入（除内存映射）
# 3. 无系统调用异常
cloc third_party/mimalloc/src/  # 代码量统计
grep -r "system\|exec\|popen" third_party/mimalloc/src/  # 危险函数检查
```

## 4. 中等风险详细分析

### R-05：调试工具兼容性

**风险描述**：
- Valgrind 默认不识别 mimalloc 的分配，可能误报内存泄漏
- GDB 内存查看可能受影响
- perf 内存分析可能不准确

**缓解策略**：

**文档说明**：
```markdown
## 使用 Valgrind 调试

当启用 mimalloc 时，需要特殊配置 Valgrind：

```bash
# 方式1：禁用 mimalloc 后使用 Valgrind
cmake -DCANGJIE_USE_MIMALLOC=OFF ..
valgrind --leak-check=full ./cjc source.cj

# 方式2：使用 Valgrind 兼容模式
valgrind --soname-synonyms=somalloc=NONE ./cjc source.cj
```
```

**构建配置**：
```cmake
# 提供专门的调试构建配置
option(CANGJIE_DEBUG_MEMORY
    "Build with memory debugging (disables mimalloc, enables Valgrind support)"
    OFF)

if(CANGJIE_DEBUG_MEMORY)
    set(CANGJIE_USE_MIMALLOC OFF CACHE BOOL "" FORCE)
    add_compile_options(-g3 -fno-omit-frame-pointer)
    message(STATUS "Memory debugging mode: mimalloc disabled, Valgrind compatible")
endif()
```

### R-06：内存泄漏引入

**风险描述**：
mimalloc 集成可能引入新的内存泄漏：
- mimalloc 自身的内存未正确释放
- 混合分配器导致 free 调用错误分配器

**缓解策略**：

**自动化检测**：
```bash
# CI 中的内存泄漏检测
# 方式1：LeakSanitizer（Linux）
cmake -DCMAKE_CXX_FLAGS="-fsanitize=leak" -DCANGJIE_USE_MIMALLOC=OFF ..
./cjc source.cj
# 预期：无泄漏报告

# 方式2：mimalloc 内置泄漏检测
export MIMALLOC_SHOW_STATS=1
./cjc source.cj
# 检查输出中的 "leaked" 统计
```

**mimalloc 统计输出**：
```cpp
// 程序退出时打印 mimalloc 统计
#ifdef CANGJIE_USE_MIMALLOC
#ifdef NDEBUG
// Release 构建：仅在 MIMALLOC_SHOW_STATS=1 时输出
#else
// Debug 构建：始终输出统计
mi_stats_print(nullptr);
#endif
#endif
```

## 5. 低风险详细分析

### R-07：构建系统复杂度增加

**风险描述**：
新增 CMake 选项和第三方依赖增加构建系统复杂度。

**缓解策略**：

**封装 CMake 模块**：
```cmake
# cmake/optional/CangjieMemalloc.cmake（新建）
# 封装所有 mimalloc 相关配置

macro(cangjie_configure_mimalloc)
    if(NOT CANGJIE_USE_MIMALLOC)
        return()
    endif()

    # 检查互斥条件
    cangjie_check_mimalloc_conflicts()

    # 查找或构建 mimalloc
    cangjie_find_or_build_mimalloc()

    # 导出变量
    set(CANGJIE_MIMALLOC_LIBS mimalloc-static PARENT_SCOPE)
    set(CANGJIE_MIMALLOC_INCLUDE_DIRS ${MIMALLOC_INCLUDE_DIR} PARENT_SCOPE)
endmacro()
```

**清晰的文档**：
```markdown
## 构建选项

### CANGJIE_USE_MIMALLOC（默认：OFF）

启用 mimalloc 高性能内存分配器。

**注意事项**：
- 与 Sanitizer 选项互斥（自动禁用）
- Windows 平台使用 new/delete 替换策略
- 需要 CMake 3.16.5+

**使用方法**：
```bash
cmake -DCANGJIE_USE_MIMALLOC=ON ..
```
```

### R-09：跨平台行为差异

**风险描述**：
mimalloc 在不同平台的行为可能有差异：
- Linux：使用 mmap + brk
- macOS：使用 mmap（不支持 brk）
- Windows：使用 VirtualAlloc

**缓解策略**：

**全平台 CI 测试**：
```yaml
# .github/workflows/ci.yml（示例）
jobs:
  test-mimalloc:
    strategy:
      matrix:
        os: [ubuntu-22.04, macos-12, windows-2022]
        build_type: [Debug, Release]
    runs-on: ${{ matrix.os }}
    steps:
      - name: Build with mimalloc
        run: |
          cmake -DCANGJIE_USE_MIMALLOC=ON \
                -DCMAKE_BUILD_TYPE=${{ matrix.build_type }} ..
          cmake --build .
      - name: Run tests
        run: ctest --output-on-failure
```

## 6. 风险监控与应急预案

### 6.1 监控指标

**性能监控**：
```bash
# 每次 CI 构建记录性能数据
./scripts/record_perf.sh >> perf_history.csv

# 格式：
# date,commit,project,time_system,time_mimalloc,speedup
# 2026-03-03,abc123,small,1.2,1.1,8.3%
```

**内存监控**：
```bash
# 监控内存峰值趋势
./scripts/record_memory.sh >> memory_history.csv
```

**告警阈值**：
- 性能下降 > 5%：触发告警，暂停合并
- 内存增长 > 10%：触发告警，调查原因
- 测试失败率 > 0%：立即回滚

### 6.2 应急预案

**P0 级别（立即回滚）**：
- 编译器崩溃
- 生成代码错误
- 内存损坏

```bash
# 紧急回滚命令
cmake -DCANGJIE_USE_MIMALLOC=OFF ..
cmake --build .
# 无需修改代码，5分钟内完成回滚
```

**P1 级别（24小时内修复）**：
- 性能下降 > 10%
- 特定平台构建失败
- 内存泄漏

**P2 级别（1周内修复）**：
- 性能下降 5-10%
- 调试工具兼容性问题
- 文档不完整

### 6.3 回滚决策树

```
发现问题
    │
    ├─ 是否影响正确性？
    │   ├─ 是 → 立即回滚（P0）
    │   └─ 否 ↓
    │
    ├─ 是否影响性能 > 10%？
    │   ├─ 是 → 24小时内修复或回滚（P1）
    │   └─ 否 ↓
    │
    ├─ 是否影响特定平台？
    │   ├─ 是 → 该平台禁用 mimalloc，其他平台继续
    │   └─ 否 ↓
    │
    └─ 记录问题，计划修复（P2）
```

## 7. 总结

### 7.1 风险可接受性评估

**整体风险评估**：中等偏低

**主要风险已有明确缓解策略**：
- Sanitizer 冲突：CMake 自动互斥，完全可控
- Windows 兼容性：方案 B 备选，有成熟解决方案
- 性能回归：测试门控，可快速回滚

**残余风险**：
- 未知的平台特定问题（概率低）
- 极端工作负载下的性能差异（可接受）

### 7.2 风险接受建议

建议按以下顺序推进：
1. **先在 Linux 平台验证**（风险最低）
2. **再扩展到 macOS**（类似 Linux）
3. **最后处理 Windows**（使用方案 B）
4. **逐步默认启用**（从 OFF 到 ON）

这种渐进式策略将风险控制在可接受范围内，同时确保性能收益的实现。
