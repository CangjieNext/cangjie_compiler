## 二、P3 级问题分析与优化

### 2.1 BUG-21：多入口点初始化一致性（P3）

#### 问题分析

设计方案要求所有入口点（main.cpp、main-frontend.cpp、main-macrosrv.cpp、main-chir-dis.cpp）都需要相同的初始化配置：

```cpp
// 每个入口点都需要重复的代码
#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc.h>
#if defined(_WIN32)
#include <mimalloc-new-delete.h>
struct MimallocInit { MimallocInit() { mi_process_init(); } };
static MimallocInit g_mimallocInit;
#endif
static void InitMimallocOptions() { ... }
#endif
```

**问题**：
- 代码重复，维护成本高
- 新增入口点时可能遗漏
- 不同入口点配置可能不一致

#### 优化方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **方案 1**：抽取共享头文件 | 创建 `MimallocInit.h` 统一管理 | 集中管理，易维护 | 新增文件 |
| **方案 2**：保持现状 | 在文档中明确要求 | 无需修改代码 | 依赖人工检查 |

**推荐方案**：方案 1（抽取共享头文件）

#### 优化实现

```cpp
// src/cangjie/Utils/MimallocInit.h
#pragma once

#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc.h>

#if defined(_WIN32)
#include <mimalloc-new-delete.h>

// Windows 平台显式初始化
// 使用编译器属性确保初始化顺序优先级
#  if defined(__GNUC__) || defined(__clang__)
struct __attribute__((init_priority(101))) MimallocInit {
    MimallocInit() { mi_process_init(); }
};
#  else
struct MimallocInit {
    MimallocInit() { mi_process_init(); }
};
#  endif
static MimallocInit g_mimallocInit;
#endif

/**
 * @brief 初始化 mimalloc 运行时选项
 *
 * 必须在 main 函数开头调用，确保选项在首次分配前生效。
 * 这些选项影响内存归还行为和性能特性。
 */
static inline void InitMimallocOptions()
{
    mi_option_set(mi_option_reset_delay, 0);        // 立即归还延迟释放的内存
    mi_option_set(mi_option_eager_commit_delay, 0); // 减少提交延迟
}

/**
 * @brief 检查 mimalloc 初始化状态
 *
 * 用于诊断初始化问题，可在启动时调用。
 */
static inline void CheckMimallocInit()
{
    void* test = mi_malloc(16);
    if (!test) {
        fprintf(stderr,
            "Warning: mimalloc initialization failed. "
            "This may cause allocation failures.\n");
    } else {
        mi_free(test);
    }
}

#endif // CANGJIE_USE_MIMALLOC
```

**入口点简化**：

```cpp
// src/main.cpp 及其他入口点

#include "cangjie/Utils/MimallocInit.h"

int main(int argc, const char** argv, const char** envp)
{
#ifdef CANGJIE_USE_MIMALLOC
    InitMimallocOptions();
    CheckMimallocInit();
#endif
    // ... 主程序逻辑
}
```

### 2.2 BUG-19：MimallocInit 静态对象构造顺序不确定（P3）

#### 问题分析

C++ 标准不保证同一翻译单元内静态对象的构造顺序。如果有另一个静态对象在构造时使用 mimalloc 分配内存，可能发生在 `g_mimallocInit` 构造之前。

#### 风险评估

**实际风险较低**，原因：
1. `mi_process_init` 在 mimalloc 静态库内部已有自动初始化机制
2. `mimalloc-new-delete.h` 中的 `operator new` 实现会自动初始化
3. 仓颉编译器代码中全局对象较少，且多为简单初始化

#### 优化方案

使用编译器属性确保初始化顺序优先级：

```cpp
// GCC/Clang 使用 init_priority 属性
#if defined(__GNUC__) || defined(__clang__)
struct __attribute__((init_priority(101))) MimallocInit {
    MimallocInit() { mi_process_init(); }
};
#else
struct MimallocInit {
    MimallocInit() { mi_process_init(); }
};
#endif
```

**说明**：`init_priority(101)` 确保此静态对象在优先级 101（高于默认的 65535）时构造，从而在大多数其他静态对象之前完成初始化。

### 2.3 BUG-20：InitMimallocOptions 与首次分配的竞态（P4）

#### 问题分析

`InitMimallocOptions` 在 `main` 函数开头调用，但全局对象的构造函数在 `main` 之前执行。如果全局对象构造时发生内存分配，此时 `mi_option_set` 尚未调用。

#### 风险评估

**实际风险很低**：
1. `mi_option_set` 设置的是 `reset_delay` 和 `eager_commit_delay`，这些选项仅影响内存归还行为，不影响正确性
2. 即使在 `main` 之后设置，对后续分配仍然有效
3. 仓颉编译器的全局对象很少，且分配量小

#### 优化方案

此问题为 P4 级，可忽略。当前方案已经足够好。如果需要进一步优化，可将选项设置移到静态初始化阶段：

```cpp
// 可选：在静态初始化阶段设置选项
static struct MimallocOptions {
    MimallocOptions() {
        mi_option_set(mi_option_reset_delay, 0);
        mi_option_set(mi_option_eager_commit_delay, 0);
    }
} g_mimallocOptions;
```

## 四、决策记录

### ADR-008：共享初始化头文件

**状态**：已决策
**背景**：多入口点初始化代码重复，维护成本高
**决策**：创建共享头文件 `MimallocInit.h` 统一管理初始化逻辑
**理由**：
- 集中管理，减少代码重复
- 新增入口点时只需包含一个头文件
- 配置变更只需修改一处
**后果**：新增一个头文件，但大幅提升可维护性

### ADR-009：静态初始化顺序优化

**状态**：已决策
**背景**：静态对象构造顺序不确定可能导致问题
**决策**：使用 `init_priority` 属性确保 `MimallocInit` 优先构造
**理由**：
- GCC/Clang 支持 `init_priority` 属性
- 优先级 101 确保在大多数静态对象之前初始化
- 提供额外的安全保障
**后果**：仅在 GCC/Clang 平台生效，其他平台保持原有行为
