# mimalloc 集成技术方案设计

## 方案概述

基于对仓颉编译器架构的深入分析，提出以下三个差异化备选方案：

| 维度 | 方案 A：全局替换 | 方案 B：编译器进程级替换 | 方案 C：选择性 STL 分配器 |
|------|----------------|----------------------|------------------------|
| 替换范围 | 全局 malloc/free | 编译器进程 new/delete | 热点容器 allocator |
| 侵入程度 | 最低（链接层） | 低（入口点） | 中（代码修改） |
| 性能收益 | 最高 | 高 | 中等 |
| 风险等级 | 中 | 低 | 低 |
| 实施复杂度 | 低 | 低 | 高 |
| 可回滚性 | 好 | 好 | 差 |

---

## 方案 A：全局链接层替换（推荐）

### A.1 方案概述

通过链接器符号覆盖机制，在链接阶段将 `malloc`/`free`/`realloc`/`calloc` 等标准分配函数替换为 mimalloc 实现。无需修改任何业务代码，通过 CMake 配置控制。

### A.2 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                    仓颉编译器进程                              │
│                                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │  Lexer   │  │  Parser  │  │   Sema   │  │  CHIR    │   │
│  │  new/del │  │  new/del │  │  new/del │  │  new/del │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
│       │              │              │              │         │
│       └──────────────┴──────────────┴──────────────┘        │
│                              │                              │
│                    ┌─────────▼──────────┐                   │
│                    │  C++ 运行时 new/del │                   │
│                    │  (operator new)    │                   │
│                    └─────────┬──────────┘                   │
│                              │                              │
│                    ┌─────────▼──────────┐                   │
│                    │   mimalloc 库       │  ← 链接层替换      │
│                    │  mi_malloc/mi_free  │                   │
│                    │  (覆盖 malloc/free) │                   │
│                    └─────────┬──────────┘                   │
│                              │                              │
│                    ┌─────────▼──────────┐                   │
│                    │    操作系统内存      │                   │
│                    │  mmap/VirtualAlloc  │                   │
│                    └────────────────────┘                   │
└─────────────────────────────────────────────────────────────┘
```

### A.3 实现机制

#### A.3.1 Linux/macOS：LD_PRELOAD 或静态链接覆盖

mimalloc 提供两种全局替换方式：

**方式 1：静态链接 mimalloc-override（推荐用于编译器）**
```cmake
# 链接 mimalloc-override 静态库，自动覆盖 malloc/free
target_link_libraries(cjc mimalloc-static)
# 或使用 override 版本（更彻底的替换）
target_link_libraries(cjc mimalloc-override-static)
```

**方式 2：动态链接 + LD_PRELOAD（用于测试）**
```bash
LD_PRELOAD=/path/to/libmimalloc.so cjc source.cj
```

#### A.3.2 Windows：DLL 替换

```cmake
if(WIN32)
    # Windows 使用 mimalloc-redirect 机制
    target_link_libraries(cjc mimalloc-static)
    # 需要 mimalloc-redirect.dll 在同目录
endif()
```

#### A.3.3 malloc_trim 兼容处理

当前代码在 Linux 上调用 `malloc_trim(0)` 来归还内存给 OS：

```cpp
// src/Driver/Driver.cpp:89
(void)malloc_trim(0);
```

mimalloc 提供等价函数：
```cpp
// 替换方案：mimalloc 提供 malloc_trim 兼容实现
// 当链接 mimalloc-override 时，malloc_trim 自动被覆盖
// 或显式调用：
mi_collect(true); // 等价于 malloc_trim(0)
```

```cmake
# third_party/cmake/Mimalloc.cmake（新建）

set(MIMALLOC_SOURCE_DIR ${CMAKE_SOURCE_DIR}/third_party/mimalloc)

if(EXISTS ${MIMALLOC_SOURCE_DIR})
    # 本地源码构建
    add_subdirectory(${MIMALLOC_SOURCE_DIR} ${CMAKE_BINARY_DIR}/mimalloc)

    # ExternalProject 下载构建
    ExternalProject_Add(
        mimalloc-project
        GIT_REPOSITORY https://github.com/microsoft/mimalloc.git
        GIT_TAG        v${MIMALLOC_VERSION}
        CMAKE_ARGS
            -DCMAKE_BUILD_TYPE=${CMAKE_BUILD_TYPE}
            -DCMAKE_C_COMPILER=${CMAKE_C_COMPILER}
            -DCMAKE_CXX_COMPILER=${CMAKE_CXX_COMPILER}
            -DMI_BUILD_SHARED=OFF
            -DMI_BUILD_STATIC=ON
            -DMI_BUILD_OBJECT=ON
            -DMI_OVERRIDE=ON          # 覆盖 malloc/free
            -DMI_BUILD_TESTS=OFF
            -DCMAKE_INSTALL_PREFIX=${CMAKE_BINARY_DIR}/mimalloc

endif()

# 导出目标
set(MIMALLOC_INCLUDE_DIR ${CMAKE_BINARY_DIR}/mimalloc/include)
set(MIMALLOC_STATIC_LIB ${CMAKE_BINARY_DIR}/mimalloc/lib/libmimalloc.a)
```

### A.6 优劣分析

#### 优势
- **零侵入**：无需修改任何业务逻辑代码
- **覆盖全面**：所有 malloc/new/free/delete 均被替换，包括 LLVM 内部分配
- **性能最优**：全局替换收益最大化
- **实施简单**：主要是 CMake 配置变更
- **可回滚**：关闭 `CANGJIE_USE_MIMALLOC` 即可回滚

#### 劣势
- **LLVM 内部分配也被替换**：可能影响 LLVM 组件行为（通常是正面的）
- **Windows 复杂度**：Windows 平台需要额外的 DLL 重定向机制
- **调试工具兼容性**：Valgrind 需要特殊配置（`--soname-synonyms=somalloc=NONE`）

#### 适用场景
- **生产环境**：追求最大性能提升
- **CI/CD 构建**：大型项目编译加速
- **IDE 后台服务**：LSP 服务长时间运行场景

## 方案 B：编译器进程级 new/delete 替换（保守方案）

### B.1 方案概述

仅替换 C++ `operator new`/`operator delete`，不替换底层 `malloc`/`free`。通过在编译器入口点（`main.cpp`）包含 mimalloc 头文件触发替换，保留 LLVM 使用系统分配器的行为。

### B.2 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                    仓颉编译器进程                              │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              仓颉前端（C++ new/delete）                │   │
│  │  Lexer │ Parser │ Sema │ CHIR │ CodeGen               │   │
│  │    ↓        ↓       ↓      ↓       ↓                  │   │
│  │         mimalloc operator new/delete                  │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              LLVM 后端（保持系统分配器）               │   │
│  │  LLVMCore │ LLVMSupport │ LLVMCodeGen                 │   │
│  │    ↓           ↓             ↓                        │   │
│  │              系统 malloc/free                         │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              操作系统内存管理                          │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### B.3 实现机制

#### B.3.1 入口点注入

mimalloc 提供 `mimalloc-new-delete.h`，包含该头文件即可替换 `operator new`/`operator delete`：

```cpp
// src/main.cpp 修改
#ifdef CANGJIE_USE_MIMALLOC
// 包含此头文件会定义 operator new/delete 的 mimalloc 实现
// 必须在所有其他头文件之前包含
#include <mimalloc-new-delete.h>
#endif

#include "cangjie/Driver/Driver.h"
// ...
```

#### B.3.2 多入口点处理

仓颉编译器有多个可执行文件入口：

```
src/main.cpp          → cjc
src/main-frontend.cpp → cjc-frontend (Windows Release)
src/main-macrosrv.cpp → LSPMacroServer
src/main-chir-dis.cpp → chir-dis
```

每个入口点都需要包含 mimalloc 头文件：

```cpp
// 统一处理：创建 src/MimallocInit.h
#pragma once
#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc-new-delete.h>
#endif
```

```cpp
// 每个 main.cpp 文件首行添加
#include "MimallocInit.h"
```

#### B.3.3 CMake 配置

```cmake
# src/CMakeLists.txt
if(CANGJIE_USE_MIMALLOC)
    # 仅链接基础 mimalloc（不使用 override 版本）
    target_link_libraries(cjc PRIVATE mimalloc-static)
    target_link_libraries(LSPMacroServer PRIVATE mimalloc-static)
    target_link_libraries(chir-dis PRIVATE mimalloc-static)

    # 不替换 cangjie-lsp-share（动态库，避免符号冲突）
    # LSP 动态库通过 LSPMacroServer 间接使用 mimalloc
endif()
```

### B.4 优劣分析

#### 优势
- **风险可控**：LLVM 内部分配不受影响，避免潜在兼容性问题
- **调试友好**：可以区分仓颉前端和 LLVM 的内存使用
- **Windows 简单**：不需要 DLL 重定向机制
- **Sanitizer 兼容**：更容易与 ASan 共存（仅前端部分）

#### 劣势
- **收益有限**：LLVM 分配（约占总分配的 30-40%）不受益
- **多入口点**：需要修改多个 main.cpp 文件
- **不一致性**：同一进程中存在两个分配器，可能导致内存统计不准确

#### 适用场景
- **保守迁移**：对 LLVM 兼容性有顾虑的场景
- **调试阶段**：需要精确区分前端/后端内存使用
- **Windows 平台**：避免 Windows 平台的 DLL 重定向复杂性

## 方案 C：选择性 STL 分配器替换（精细化方案）

### C.1 方案概述

为编译器中的热点数据结构（AST 节点容器、符号表、CHIR IR 节点）提供自定义 STL 分配器，使用 mimalloc 的 `mi_heap_t` 实现隔离的内存池，支持批量释放。

### C.2 架构图

```

│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  编译单元（CompilationUnit）                          │   │
│  │                                                     │   │
│  │  ┌──────────────┐  ┌──────────────┐                 │   │
```

### C.3 实现机制

#### C.3.1 自定义 STL 分配器

```cpp
// include/cangjie/Utils/MimallocAllocator.h（新建）
#pragma once

#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc.h>

namespace Cangjie {

/**
 * @brief STL 兼容的 mimalloc 分配器
 *
 * 使用 mimalloc 的线程局部堆，提供高性能的 STL 容器分配。
 *
 * 用法：
 *   using ASTNodeVec = std::vector<ASTNode*, MimallocAllocator<ASTNode*>>;
 */
template <typename T>
class MimallocAllocator {
public:
    using value_type = T;
    using pointer = T*;
    using const_pointer = const T*;
    using size_type = std::size_t;
    using difference_type = std::ptrdiff_t;

    template <typename U>
    struct rebind {
        using other = MimallocAllocator<U>;
    };

    MimallocAllocator() noexcept = default;

    template <typename U>
    MimallocAllocator(const MimallocAllocator<U>&) noexcept {}

    T* allocate(std::size_t n)
    {
        if (n > std::numeric_limits<std::size_t>::max() / sizeof(T)) {
            throw std::bad_alloc();
        }
        void* ptr = mi_malloc(n * sizeof(T));
        if (!ptr) {
            throw std::bad_alloc();
        }
        return static_cast<T*>(ptr);
    }

    void deallocate(T* ptr, std::size_t) noexcept
    {
        mi_free(ptr);
    }

    template <typename U>
    bool operator==(const MimallocAllocator<U>&) const noexcept { return true; }

    template <typename U>
    bool operator!=(const MimallocAllocator<U>&) const noexcept { return false; }
};

/**
 * @brief 基于 mi_heap_t 的隔离堆分配器
 *
 * 适用于编译单元级别的内存管理，支持批量释放。
 * 编译完成后调用 mi_heap_delete() 一次性释放所有内存。
 */
template <typename T>
class MimallocHeapAllocator {
public:
    using value_type = T;

    explicit MimallocHeapAllocator(mi_heap_t* heap) noexcept : heap_(heap) {}

    template <typename U>
    MimallocHeapAllocator(const MimallocHeapAllocator<U>& other) noexcept
        : heap_(other.heap_) {}

    T* allocate(std::size_t n)
    {
        void* ptr = mi_heap_malloc(heap_, n * sizeof(T));
        if (!ptr) throw std::bad_alloc();
        return static_cast<T*>(ptr);
    }

    void deallocate(T* ptr, std::size_t) noexcept
    {
        mi_free(ptr);
    }

    mi_heap_t* heap_;
};

} // namespace Cangjie

#else // !CANGJIE_USE_MIMALLOC

namespace Cangjie {
// 降级为标准分配器
template <typename T>
using MimallocAllocator = std::allocator<T>;

} // namespace Cangjie

#endif // CANGJIE_USE_MIMALLOC
```

### C.4 优劣分析

#### 优势
- **精细控制**：可以针对特定数据结构优化
- **隔离堆**：支持编译单元级别的批量内存释放
- **调试友好**：可以精确追踪特定组件的内存使用
- **Sanitizer 完全兼容**：不影响全局分配器

#### 劣势
- **代码侵入性高**：需要修改大量数据结构定义
- **维护成本高**：新增数据结构需要手动选择分配器
- **收益有限**：只有显式使用 MimallocAllocator 的容器受益
- **类型复杂**：模板参数增加，代码可读性下降
- **不完整**：裸 new/delete 分配的对象不受益

#### 适用场景
- **特定优化**：已知某个数据结构是性能瓶颈
- **内存隔离**：需要精确控制特定组件的内存生命周期
- **渐进式迁移**：作为方案 A/B 的补充，针对特定热点

## 方案对比与推荐

### 综合评分矩阵

| 评估维度 | 权重 | 方案 A | 方案 B | 方案 C |
|---------|------|--------|--------|--------|
| 性能提升幅度 | 30% | 9/10 | 6/10 | 4/10 |
| 实施复杂度（低=好） | 20% | 8/10 | 7/10 | 3/10 |
| 风险等级（低=好） | 20% | 6/10 | 8/10 | 9/10 |
| 可维护性 | 15% | 9/10 | 8/10 | 4/10 |
| 可回滚性 | 10% | 9/10 | 8/10 | 4/10 |
| 跨平台兼容性 | 5% | 7/10 | 9/10 | 10/10 |
| **加权总分** | 100% | **8.0** | **7.2** | **4.9** |

### 推荐策略

**推荐方案 A（全局链接层替换）作为主方案**，理由：
1. 性能收益最大化，覆盖所有分配路径
2. 代码侵入性最低，维护成本最小
3. 通过 CMake 选项可随时回滚
4. 业界成熟实践（LLVM 本身也支持 mimalloc 集成）

**方案 B 作为 Windows 平台的备选**，理由：
1. Windows 平台的全局替换需要额外的 DLL 重定向
2. 方案 B 在 Windows 上更简单可靠

**方案 C 作为未来优化方向**，理由：
1. 在方案 A 基础上，针对特定热点进行精细化优化
2. 隔离堆特性对增量编译场景有额外价值
