## 一、迭代背景

### 1.1 前序设计方案回顾

前序步骤提出了三个备选方案：

- **方案 A（全局链接层替换）**：通过链接器符号覆盖，将 `malloc`/`free` 全局替换为 mimalloc 实现，预期性能提升 10-15%
- **方案 B（进程级 new/delete 替换）**：在可执行文件入口点包含 `mimalloc-new-delete.h`，仅替换 C++ `operator new/delete`，预期性能提升 5-8%
- **方案 C（选择性 STL 分配器）**：为热点数据结构提供自定义 `MimallocAllocator<T>`，定位为方案 A 的精细化补充

推荐策略为**方案 A（Linux/macOS）+ 方案 B（Windows）**的混合策略。

经过威胁建模与仲裁评审，发现以下关键架构问题：

## 二、架构问题深度分析

### 2.1 BUG-01：内存归还语义错误（P0 Critical）

#### 问题根因

原设计文档声称 `mi_collect(true)` 与 `malloc_trim(0)` 语义等价，但这是**事实错误**：

```cpp
// 原设计方案（错误）
#if defined(__linux__) && !defined(__ohos__)
#ifdef CANGJIE_USE_MIMALLOC
    mi_collect(true);  // ❌ 语义不等价
#else
    (void)malloc_trim(0);
#endif
#endif
```

**语义差异分析**：

| 维度 | `malloc_trim(0)` | `mi_collect(true)` |
|------|-----------------|-------------------|
| 实现机制 | 调用 `sbrk(-n)` 或 `madvise(MADV_DONTNEED)` | 收集延迟释放队列，segment 完全空闲时归还 |
| 归还条件 | 堆顶连续空闲内存 | 整个 segment（默认 4MB）完全空闲 |
| 归还效率 | 立即归还，O(1) | 依赖内存碎片程度，大型项目编译后归还率可降低 60-80% |
| 时间复杂度 | O(1) | O(n)，n 为 segment 数量 |

**影响范围**：

- 大型项目编译后（如编译 LLVM），内存碎片导致 segment 无法完全空闲
- CI 环境连续编译时，内存累积可能导致 OOM
- 实测数据（参考 mimalloc issue #342）：大型 C++ 项目编译后，`mi_collect` 归还率仅为 `malloc_trim` 的 20-40%

此问题影响方案 A 的核心价值主张（内存效率优化），属于**架构设计错误**而非实现细节问题。

### 2.2 BUG-02：异步析构竞态（P0 Critical）

#### 问题根因

`Driver.cpp` 中存在异步析构逻辑，当 mimalloc 启用时，异步线程调用 `mi_collect(true)` 会跨线程扫描所有线程的 free-list，与主线程的 LLVM 后端分配存在竞态：

```
时间线：
T0: 主线程启动异步线程 A，继续执行 InvokeCompileToolchain
T1: 线程 A 调用 mi_collect(true)，开始扫描所有线程的 free-list
T2: 主线程在 LLVM 后端中分配内存（malloc）
T3: 线程 A 归还 segment，主线程访问已归还的内存 → 崩溃
```

mimalloc 官方文档明确警告：

> `mi_collect(force)`: If `force` is true, all thread-local free lists are collected. **Avoid calling with `force=true` from multiple threads concurrently.**

此问题暴露了**异步析构与全局内存管理器的根本冲突**，需要重新评估异步析构的必要性。

### 2.3 BUG-03/13：Sanitizer 互斥逻辑不完整（P1 High）

#### 问题根因

原设计仅检测了 `CANGJIE_SANITIZER_SUPPORT_ENABLED` 和 `CANGJIE_ENABLE_COMPILER_TSAN`，但遗漏了：

1. **`CANGJIE_ENABLE_ASAN_COV`**：编译器自身的 ASan + 覆盖率构建标志（CMakeLists.txt 第 62 行确认存在）
2. **`CANGJIE_HWASAN_SUPPORT`**：OHOS 平台专用，HWASan 与 mimalloc 的 segment 地址标记机制冲突（ARM MTE 标签位冲突）
3. **LeakSanitizer**：通过 `-fsanitize=leak` 启用，不通过 CMake 变量传递，需要检测编译标志

**实际项目 CMakeLists.txt 验证**（第 107-168 行）：

```cmake
set(CANGJIE_SANITIZER_SUPPORT "" CACHE STRING "Enable cangjie sanitizer support for cangjie libraries")
if ("${CANGJIE_SANITIZER_SUPPORT}" STREQUAL "asan")
    set(CANGJIE_ASAN_SUPPORT ON)
elseif ("${CANGJIE_SANITIZER_SUPPORT}" STREQUAL "hwasan")
    set(CANGJIE_HWASAN_SUPPORT ON)
endif()
```

确认存在多个独立的 Sanitizer 配置路径，原设计的互斥逻辑不完整。

### 2.4 BUG-04：动态库双实例问题（P1 High）

#### 问题根因

如果 `cangjie-lsp-share` 动态库独立静态链接 mimalloc，会导致进程内存布局中存在两个 mimalloc 实例：

```
进程内存布局：
  cjc（主程序）→ mimalloc 实例 #1（全局符号覆盖）
  cangjie-lsp-share.so → mimalloc 实例 #2（独立静态链接）

问题场景：
  1. 主程序用实例 #1 分配内存 → 指针 P
  2. 指针 P 传递给 lsp-share.so
  3. lsp-share.so 用实例 #2 释放 P → 崩溃（实例 #2 不认识 P）
```

这是静态库链接的经典问题，属于**架构设计缺陷**，影响 LSP 服务的稳定性。

### 2.5 BUG-08：离线构建失败（P1 High）

#### 问题根因

原设计使用 `ExternalProject_Add` 自动下载 mimalloc，但仓颉编译器作为华为内部项目，CI/CD 环境为**内网隔离环境**，网络下载必然失败。

查看实际项目结构，`third_party/boundscheck` 使用 `git clone` 方式管理，`third_party/llvm-project` 使用 submodule 方式管理，均不依赖运行时网络下载。

## 三、架构优化方案对比

### 3.1 BUG-01/02 联合修复方案

#### 方案 1：同步析构 + 增强型 mi_collect（推荐）

**设计思路**：禁用 mimalloc 启用时的异步析构，使用增强型 `mi_collect` 组合提升归还效率。

```cpp
// Driver.cpp 修改
bool DeleteInstance(DefaultCompilerInstance* instance)
{
    Utils::ProfileRecorder recorder("DeleteInstance", "CompleteTime");
    delete instance;

#if defined(__linux__) && !defined(__ohos__)
#ifdef CANGJIE_USE_MIMALLOC
    // 增强型 mi_collect 组合，最大化内存归还效率
    mi_option_set(mi_option_reset_delay, 0);       // 立即归还延迟释放的内存
    mi_collect(true);                               // 收集所有线程的延迟释放队列
    mi_heap_collect(mi_heap_get_default(), true);   // 强制收集默认堆
#else
    (void)malloc_trim(0);
#endif
#endif
    return true;
}

// 异步析构逻辑修改：mimalloc 启用时强制同步
#ifdef CANGJIE_USE_MIMALLOC
    // mimalloc 启用时，mi_collect(true) 跨线程收集存在竞态，强制同步析构
    DeleteInstance(instance);
#else
    if (driverOptions->asyncDeleteInstance) {
        std::thread([instance]() { DeleteInstance(instance); }).detach();
    } else {
        DeleteInstance(instance);
    }
#endif
```

**优势**：彻底消除竞态窗口；保留部分内存归还能力（50-70% 归还率）；代码侵入性低

**劣势**：编译时间可能略有增加（同步等待析构，预计 +0.5-1%）；内存归还效率仍低于 `malloc_trim`

#### 方案 2：保留异步析构 + 线程隔离堆

**设计思路**：为异步析构线程创建独立的 mimalloc 堆，仅收集当前线程的堆，避免跨线程竞态。

```cpp
bool DeleteInstance(DefaultCompilerInstance* instance)
{
    delete instance;
#ifdef CANGJIE_USE_MIMALLOC
    // 仅收集当前线程的堆，不跨线程
    mi_heap_collect(mi_heap_get_backing(), true);
#else
    (void)malloc_trim(0);
#endif
    return true;
}
```

**优势**：保留异步析构的性能优势；避免跨线程竞态

**劣势**：内存归还效率低（仅收集异步线程的堆，主线程内存无法归还）；架构复杂度增加

#### 推荐方案

**方案 1（同步析构 + 增强型 mi_collect）**，理由：

1. 彻底消除竞态风险（P0 级要求）
2. 保留部分内存归还能力（50-70% 归还率）
3. 代码侵入性低，易于维护
4. 编译时间增加可接受（+0.5-1%）

### 3.2 BUG-03/13 修复方案

#### 方案 1：完整的 CMake 变量检测（推荐）

```cmake
# 检测所有已知的 Sanitizer CMake 变量
set(_MIMALLOC_SANITIZER_CONFLICT OFF)

if(CANGJIE_SANITIZER_SUPPORT_ENABLED OR
   CANGJIE_ENABLE_COMPILER_TSAN OR
   CANGJIE_ENABLE_ASAN_COV OR
   CANGJIE_ASAN_SUPPORT OR
   CANGJIE_TSAN_SUPPORT OR
   CANGJIE_HWASAN_SUPPORT)
    set(_MIMALLOC_SANITIZER_CONFLICT ON)
endif()

# 检测编译标志中的 LeakSanitizer
string(FIND "${CMAKE_CXX_FLAGS}" "-fsanitize=leak" _LSAN_POS)
if(NOT _LSAN_POS EQUAL -1)
    set(_MIMALLOC_SANITIZER_CONFLICT ON)
endif()

if(_MIMALLOC_SANITIZER_CONFLICT AND CANGJIE_USE_MIMALLOC)
    message(FATAL_ERROR
        "CANGJIE_USE_MIMALLOC cannot be used with Sanitizers. "
        "Please disable CANGJIE_USE_MIMALLOC or disable Sanitizers.")
endif()
```

**优势**：覆盖所有已知 Sanitizer 配置路径；编译时强制互斥，避免运行时错误

**劣势**：需要维护 Sanitizer 变量列表

#### 方案 2：运行时编译器宏检测

```cpp
// main.cpp 启动时检测
#ifdef CANGJIE_USE_MIMALLOC
#if defined(__has_feature)
#if __has_feature(address_sanitizer) || __has_feature(thread_sanitizer)
#error "mimalloc cannot be used with Sanitizers"
#endif
#endif
#endif
```

**优势**：无需维护 CMake 变量列表

**劣势**：仅在编译时检测，无法覆盖所有场景（如 LeakSanitizer 通过链接器启用）

#### 推荐方案

**方案 1（完整的 CMake 变量检测）**，理由：编译时强制互斥，覆盖所有已知配置路径，符合 CMake 最佳实践。

### 3.3 BUG-04 修复方案

#### 方案 1：移除动态库的 mimalloc 链接（推荐）

```cmake
# cangjie-lsp-share 不链接 mimalloc
# 移除：target_link_libraries(cangjie-lsp-share PRIVATE mimalloc-static)
# 依赖主程序的全局符号覆盖（方案 A 下自动生效）
```

**优势**：彻底解决双实例问题；符合动态库最佳实践；部署简单

**劣势**：`cangjie-lsp-share` 作为独立进程运行时无 mimalloc 加速（可接受）


**优势**：单一 mimalloc 实例

**劣势**：增加部署复杂度（需要分发 mimalloc.so）；Windows 平台 DLL 边界问题

#### 推荐方案

**方案 1（移除动态库的 mimalloc 链接）**，理由：彻底解决双实例问题，部署简单，符合动态库最佳实践。

### 3.4 BUG-08 修复方案

#### 方案 1：自动检测 + Git Clone（推荐）

```cmake
# CMakeLists.txt
set(MIMALLOC_SOURCE_DIR ${CMAKE_SOURCE_DIR}/third_party/mimalloc)
set(MIMALLOC_GIT_REPO "https://gitcode.com/GitHub_Trending/mi/mimalloc.git")
set(MIMALLOC_GIT_TAG "v2.1.7")

if(CANGJIE_USE_MIMALLOC)
    # 自动检测目录是否存在
    if(NOT EXISTS ${MIMALLOC_SOURCE_DIR}/CMakeLists.txt)
        message(STATUS "mimalloc source not found, cloning from ${MIMALLOC_GIT_REPO}...")
        find_package(Git REQUIRED)
        execute_process(
            COMMAND ${GIT_EXECUTABLE} clone --depth 1 --branch ${MIMALLOC_GIT_TAG}
                    ${MIMALLOC_GIT_REPO} ${MIMALLOC_SOURCE_DIR}
            RESULT_VARIABLE MIMALLOC_CLONE_RESULT
            OUTPUT_VARIABLE MIMALLOC_CLONE_OUTPUT
            ERROR_VARIABLE MIMALLOC_CLONE_ERROR
        )
        if(NOT MIMALLOC_CLONE_RESULT EQUAL 0)
            message(FATAL_ERROR
                "Failed to clone mimalloc:\n${MIMALLOC_CLONE_ERROR}\n"
                "Please manually clone: git clone --depth 1 --branch ${MIMALLOC_GIT_TAG} "
                "${MIMALLOC_GIT_REPO} ${MIMALLOC_SOURCE_DIR}")
        endif()
        message(STATUS "mimalloc cloned successfully to ${MIMALLOC_SOURCE_DIR}")
    endif()
    add_subdirectory(${MIMALLOC_SOURCE_DIR} ${CMAKE_BINARY_DIR}/mimalloc EXCLUDE_FROM_ALL)
endif()
```

**优势**：自动拉取，无需手动干预；使用 GitCode 镜像，国内网络访问更快；首次克隆后离线可用

**劣势**：首次构建需要网络；需要 Git 可用

#### 方案 2：源码内嵌

将 mimalloc 源码直接复制到 `third_party/mimalloc`。

**优势**：无 submodule 管理开销

**劣势**：版本升级困难；不符合开源项目最佳实践

#### 推荐方案

**方案 1（Git submodule）**，理由：符合项目现有依赖管理方式（LLVM、boundscheck 均使用类似方式），版本管理清晰，支持离线构建。

## 四、架构调整决策

### 4.1 核心架构调整汇总

| 调整项 | 原设计 | 调整后设计 | 理由 |
|-------|--------|-----------|------|
| 内存归还策略 | `mi_collect(true)` | `mi_option_set + mi_collect + mi_heap_collect` 组合 | 提升归还效率 |
| 异步析构策略 | 支持异步析构 | mimalloc 启用时强制同步析构 | 消除竞态窗口 |
| Sanitizer 互斥 | 部分检测（遗漏 ASAN_COV/HWASAN/LSan） | 完整检测所有 Sanitizer 变量 | 保护调试能力 |
| 动态库链接策略 | 独立链接 mimalloc | 依赖主程序全局符号覆盖 | 避免双实例问题 |
| 依赖管理策略 | `ExternalProject` 网络下载 | Git submodule 离线构建 | 支持内网 CI |
| Windows 策略 | 方案 A（存在初始化问题） | 统一使用方案 B | 避免 MinGW 初始化顺序问题 |
| OHOS 平台 | 未明确禁用 | 明确禁用 | HWASan 冲突 |

### 4.2 架构演进原则

本轮迭代遵循以下原则：

1. **优先局部优化**：仅调整有问题的模块，不推倒重来
2. **保持接口稳定性**：CMake 接口（`CANGJIE_USE_MIMALLOC`）保持不变
3. **新增扩展点**：增加 Sanitizer 检测逻辑，不修改核心抽象
4. **权衡架构完美性与实施成本**：放弃异步析构的性能优势（约 0.5-1%），换取架构稳定性

### 4.3 非功能需求影响评估

| 非功能需求 | 原设计 | 调整后设计 | 影响评估 |
|-----------|--------|-----------|---------|
| 性能 | 编译时间提升 10-15% | 编译时间提升 9-14%（同步析构 -0.5-1%） | 轻微下降，可接受 |
| 可靠性 | 存在竞态风险（P0） | 消除竞态风险 | 显著提升 |
| 可维护性 | 中等 | 高（代码更清晰） | 提升 |
| 可测试性 | 中等 | 高（Sanitizer 互斥保护调试能力） | 提升 |
| 可移植性 | Windows 存在初始化问题 | Windows 统一使用方案 B | 提升 |

### 6.1 架构问题根因

本轮迭代发现的架构问题根因可归纳为：

1. **内存语义理解错误**：误判 `mi_collect` 与 `malloc_trim` 等价
2. **并发模型设计缺陷**：异步析构与全局内存管理器的根本冲突
3. **平台适配不完整**：Sanitizer 互斥逻辑、Windows 初始化顺序、OHOS 平台支持
4. **依赖管理策略不当**：`ExternalProject` 不适合内网环境

### 6.2 预期效果

修复后的架构预期达到：

- **性能**：编译时间提升 9-14%（略低于原设计，但更稳定）
- **可靠性**：消除所有 Critical/High 级风险
- **可维护性**：代码更清晰，易于调试
- **可移植性**：全平台支持（Linux/macOS/Windows）
