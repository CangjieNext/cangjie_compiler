## 二、架构问题深度分析

### 2.1 BUG-15：asyncDeleteInstance 字段不存在（P1）

#### 问题根因

迭代 1 设计方案中的同步析构代码引用了不存在的字段：

```cpp
// 迭代 1 设计方案（问题代码）
#else
    if (driverOptions->asyncDeleteInstance) {  // ❌ 字段不存在
        std::thread([instance]() { DeleteInstance(instance); }).detach();
    } else {
        DeleteInstance(instance);
    }
#endif
```

当前 `Driver.cpp` 实际代码：

```cpp
// Driver.cpp:207（当前代码）
std::future<bool> future = std::async(DeleteInstance, instance);
bool res = InvokeCompileToolchain();
future.get();
```

**根因分析**：设计方案假设存在一个控制异步析构的配置字段，但实际代码中不存在。当前实现始终使用 `std::async` 进行异步析构，没有开关控制。

#### 影响范围

- **场景**：实现阶段
- **影响程度**：代码无法编译，属于**实现阻塞问题**

#### 解决方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **方案 1**：简化实现，直接使用 #ifdef 分支 | 无需新增字段，实现简单 | 失去运行时配置灵活性 | |
| **方案 2**：新增 asyncDeleteInstance 字段 | 保留运行时配置灵活性 | 需修改多处代码，增加复杂度 | |

**推荐方案**：方案 1（简化实现）

**理由**：
1. mimalloc 启用时必须同步析构，这是硬性要求，不需要运行时配置
2. 简化实现减少代码改动，降低出错风险
3. 符合"最小改动"原则

```cpp
// 简化后的实现
#ifdef CANGJIE_USE_MIMALLOC
    // mimalloc 启用时：同步析构
    DeleteInstance(instance);
    bool res = InvokeCompileToolchain();
#else
    // 默认行为：异步析构
    std::future<bool> future = std::async(DeleteInstance, instance);
    bool res = InvokeCompileToolchain();
    future.get();
#endif
```

### 2.2 BUG-14：mi_option_set 调用时机不正确（P2）

#### 问题根因

迭代 1 设计方案在 `DeleteInstance` 中调用 `mi_option_set`：

```cpp
// DeleteInstance 中的调用（问题代码）
mi_option_set(mi_option_reset_delay, 0);
mi_option_set(mi_option_eager_commit_delay, 0);
mi_collect(true);
```

**根因分析**：

根据 mimalloc 源码（`src/options.c`）：
- `mi_option_set` 可以在任何时候调用
- 但已分配的内存使用旧的选项值
- `mi_option_reset_delay` 影响的是后续分配和释放行为
- 最佳实践是在 `main()` 开头设置全局选项

**时序问题**：

```cpp
int main() {
    // 此时 mi_option_reset_delay 使用默认值（可能有延迟）
    void* p = malloc(1024);  // 使用默认选项

    // ... 编译过程 ...

    // DeleteInstance 中设置选项
    mi_option_set(mi_option_reset_delay, 0);  // 仅影响后续分配

    // 之前的分配可能仍然使用旧的延迟策略
}
```

#### 影响范围

- **场景**：所有使用 mimalloc 的编译
- **影响程度**：内存归还效率可能未达预期，但不会导致崩溃

#### 解决方案

将 `mi_option_set` 调用移到 `main` 函数开头：

```cpp
// src/main.cpp
#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc.h>

static void InitMimallocOptions()
{
    mi_option_set(mi_option_reset_delay, 0);
    mi_option_set(mi_option_eager_commit_delay, 0);
}
#endif

int main(int argc, const char** argv, const char** envp)
{
#ifdef CANGJIE_USE_MIMALLOC
    InitMimallocOptions();  // 进程启动时设置
#endif
    // ...
}
```

### 2.3 BUG-17：Windows 缺少显式 mi_process_init（P2）

#### 问题根因

迭代 1 设计方案的 Windows 入口点配置：

```cpp
#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc-new-delete.h>  // 仅替换 operator new/delete
#endif
```

**根因分析**：

mimalloc 官方 README 明确说明：
> On Windows, when using the static library, you need to ensure `mi_process_init()` is called before any allocation.

方案 B 使用静态链接（`mimalloc-static`），存在全局对象构造早于 `main` 函数的场景：

```cpp
class GlobalConfig {
    std::string path;  // 构造时调用 operator new
public:
    GlobalConfig() { path = "config.toml"; }
};

GlobalConfig g_config;  // 全局对象，可能在 mi_process_init 之前构造
```

#### 影响范围

- **平台**：Windows（方案 B）
- **场景**：有全局对象的编译
- **影响程度**：潜在初始化顺序问题，在 `MI_SECURE` 模式下可能导致问题

#### 解决方案

添加静态初始化对象确保 `mi_process_init` 在所有分配前调用：

```cpp
// src/main.cpp
#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc.h>
#include <mimalloc-new-delete.h>

#if defined(_WIN32)
struct MimallocInit {
    MimallocInit() { mi_process_init(); }
};
static MimallocInit g_mimallocInit;  // 静态对象，在 main 前构造
#endif
#endif
```

### 2.4 BUG-16：首次构建必须联网（P2）

#### 问题根因

当前依赖获取策略：

```cmake
if(NOT EXISTS ${MIMALLOC_SOURCE_DIR}/CMakeLists.txt)
    execute_process(
        COMMAND ${GIT_EXECUTABLE} clone --depth 1 --branch ${MIMALLOC_GIT_TAG}
                ${MIMALLOC_GIT_REPO} ${MIMALLOC_SOURCE_DIR}
        ...
    )
endif()
```

**根因分析**：

迭代 1 仲裁要求"离线构建是内网 CI 的硬性要求"，但此方案在首次构建时必须联网。

#### 解决方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **方案 1**：保持自动克隆 + 文档说明 | 支持首次联网，后续离线 | 内网需预置目录 | |
| **方案 2**：回退到 Git submodule | 完全离线 | 增加仓库体积，版本升级复杂 | |

**推荐方案**：方案 1（保持自动克隆 + 文档说明）

**仲裁裁决**：自动克隆 + 手动预置提示是**可接受的折中方案**，理由：
1. Git submodule 会增加仓库体积（约 2MB）
2. 当前方案支持"首次联网，后续离线"
3. 内网 CI 可通过预置 `third_party/mimalloc` 目录解决

**修复要求**：在文档中明确说明内网环境预置步骤。

#ifdef CANGJIE_USE_MIMALLOC
#include <mimalloc.h>
#endif

bool DeleteInstance(DefaultCompilerInstance* instance)
{
    Utils::ProfileRecorder recorder("DeleteInstance", "CompleteTime");
    delete instance;

#if defined(__linux__) || defined(__APPLE__)

#endif
    return true;

    // mimalloc 启用时：同步析构

## 五、决策记录

### ADR-006：同步析构简化实现

**状态**：已决策
**背景**：`driverOptions->asyncDeleteInstance` 字段不存在，需要调整实现
**决策**：采用 `#ifdef` 分支简化实现，不新增字段
**理由**：mimalloc 启用时同步析构是硬性要求，无需运行时配置
**后果**：失去运行时配置灵活性，但符合实际需求

### ADR-007：mi_option_set 调用位置

**状态**：已决策
**背景**：`mi_option_set` 在 `DeleteInstance` 中调用可能无效
**决策**：将 `mi_option_set` 移到 `main` 函数开头
**理由**：确保选项在首次分配前生效，最大化内存归还效率
**后果**：选项全局生效，影响所有分配行为

### ADR-008：Windows 显式初始化

**状态**：已决策
**背景**：方案 B 静态链接下全局对象构造时序不确定
**决策**：添加静态初始化对象调用 `mi_process_init`
**理由**：mimalloc 官方文档要求，避免初始化顺序问题
**后果**：确保 Windows 平台稳定性

### ADR-009：离线构建策略

**状态**：已决策（确认迭代 1 方案）
**背景**：迭代 1 仲裁要求离线构建支持
**决策**：保持自动克隆 + 文档预置说明，不强制 Git submodule
**理由**：折中方案可接受，内网可通过预置目录解决
**后果**：需要在文档中明确说明内网环境预置步骤
